# Quran for iOS (quran/quran-ios) - Feature Design Analysis

> Index document for the feature-analysis set under `docs/research/quran_ios/features/`.
> Sources read from a shallow clone of `github.com/quran/quran-ios` @ main, cloned **2026-08-23**. Repo-relative paths cited throughout.

## 1. Intro

Quran for iOS is the official open-source iPhone/iPad app behind quran.com. What makes it unusual is its packaging: nearly the entire product ships as a Swift Package Manager multi-target library called **QuranEngine** (`Package.swift`), and `Example/QuranEngineApp` (AppDelegate / SceneDelegate / `Container.swift`) is just one possible composition of those targets into a runnable app. The README states the intent explicitly — other consumers can embed individual targets (say, only the mushaf reader, or only translation mode), which is why every screen is its own small, strictly-layered SPM target.

Scope of this analysis: **17 feature deep-dives** covering the complete reading experience (page-image mushaf, translation mode, word-by-word popover, edition selector, appearance controls), audio (recitation playback, download manager), personal data (bookmarks/collections/highlights, notes, last-page tracking), navigation (sura/juz index, search), infrastructure surfaces (settings hub, upgrade migration, what's-new announcements, verse sharing), and the optional quran.com cloud sync. Each dive cites implementing files read directly from the clone; the machine-readable summary lives in `docs/research/quran_ios/features.json`.

Two structural facts frame everything else. First, the mushaf is **pre-rendered page images plus parallel geometry/timing SQLite databases**, not typeset text — fidelity to printed pages is non-negotiable, so highlighting, hit-testing and scroll-targeting are all reconstructed from rectangle databases. Second, the repo builds two products from one source tree: an **open-source example build** (`#if QURAN_SYNC` off) and the production build with the closed-source Kotlin-Multiplatform MobileSync binary wired in.

## 2. Architecture overview

**Module layout** follows the README's layering, enforced by SPM target boundaries:

| Layer | Contents |
|---|---|
| `Core/` | Generic infrastructure: Analytics, Caching, Preferences (UserDefaults-backed), QueuePlayer (audio engine primitives), Localization, SystemDependencies, Crashing/VLogging, AppMigrator |
| `Model/` | Plain entities: `QuranKit` (sura/ayah/page/juz/quarter), QuranAnnotations, QuranAudio, QuranGeometry |
| `Data/` | GRDB SQLite persistence (verse text, translations, word frames, word text, audio timings, line-page metrics, download state), CoreData (notes, page bookmarks, last pages), NetworkSupport, BatchDownloader, AuthenticationClient protocol |
| `Domain/` | Business services: QuranAudioKit, AudioTimingService, ReciterService, TranslationService, ReadingService, AnnotationsService, ImageService, WordTextService, WordFrameService, AudioUpdater |
| `UI/NoorUI/` | The Noor design system (NoorFont, UIx, ViewConstrainer) incl. `ThemeService` with light/dark/auto |
| `Features/` | One SPM target per screen, plus `AppDependencies` (the cross-feature seam) and `AppStructureFeature` (tab root) |

**State & DI.** There is no DI framework. Each feature has a `Builder` struct that constructs its interactor/view model via initializer injection — `Features/AppStructureFeature/Sources/App/AppBuilder.swift` builds an `AppInteractor` over five tab builders (Home, Notes, Bookmarks, Search, Settings). Cross-cutting dependencies are declared once in the `AppDependencies` protocol (`Features/AppDependencies/Sources/AppDependencies.swift`) and implemented by the example app's `Container.swift`; factory extensions like `lastPageService()` / `noteService()` are where backend selection happens. Global mutable state is confined to UserDefaults-backed preference singletons (`ReadingPreferences.shared`, `AudioPreferences.shared`, `QuranContentStatePreferences.shared`, …) whose `$reading`-style publishers act as an app-wide event bus.

**Concurrency.** Swift end-to-end: view models and interactors are `@MainActor`; the dominant idiom is a `start()` method fanning out concurrent observation loops (`async let` or multiple `Task`s) that consume service `AsyncSequence`s and wholesale-replace `@Published` snapshots. Combine survives mainly as bridges (`PublishedBinding`, `.values()`, `.assign(to:)`). Cancellation is explicit: re-checking inputs after awaits, staleness guards before applying results, generation counters, and per-event cancellable tasks.

**Navigation & UI mix.** Navigation stays UIKit by stated policy (README): each tab is a TabBuilder/TabInteractor/TabViewController trio pushing `UINavigationController`. Screens mix legacy VIPER-style Builder/Interactor/ViewController shells with SwiftUI content driven by `ObservableObject` view models. Several deliberate UIKit islands exist inside SwiftUI screens: `PageViewController` wrapped for paging, the hand-built word-pointer overlay, and UIKit form-sheet shells used to escape `UISheetPresentationController`/SwiftUI conflicts.

**Data layers.** Bundled `quran.db` holds Uthmani Arabic text; each downloaded translation is its own SQLite db (GRDB); separate dbs hold word-by-word text, word-frame geometry (`ayahinfo_<width>.db`), line-page metrics, and audio timings. Download state persists in `GRDBDownloadsPersistence`; notes/page-bookmarks/last-pages live in CoreData; settings live in Preferences. Networking is `NetworkSupport`'s NetworkManager against configurable hosts plus `BatchDownloader` (`Data/BatchDownloader/Sources/Downloader/`: DownloadManager, DownloadSessionDelegate, DownloadsObserver) — a persisted batch engine for recitation sets, mushaf image sets and translation packs, backed by a background URLSession.

**Sync.** Only when compiled with `QURAN_SYNC` does `Package.swift` pull the closed-source `mobile-sync-spm` Kotlin-Multiplatform package; iOS wraps its auth surface as the actor `AuthenticationClientMobileSyncImpl`, and `#if QURAN_SYNC` gates every touchpoint (Bookmarks tab layout, note colors, settings account card, service factory swaps).

## 3. Cross-cutting design patterns

| Pattern | Where seen | Significance |
|---|---|---|
| Constructor-injected Builders, no DI framework | `AppBuilder` + five TabBuilders; `SettingsRootViewModel` receives child Builders (settings-support-hub); `BookmarkCollectionsBuilder` vs flat fallback (bookmarks-collections-highlights); AudioDownloadsBuilder | Because each screen is an independently consumable SPM target, any feature can be omitted by a downstream consumer without breaking compilation; Settings stays compilable even when whole sub-features are absent. |
| `@MainActor start()` fanning out concurrent AsyncSequence observation loops | `HomeViewModel.start()` (sura-juz-index-navigation), `BookmarkCollectionsViewModel.start()` four concurrent jobs (bookmarks-collections-highlights), `SearchViewModel.start()` four loops (search), `AudioDownloadsViewModel.start()` three observers (downloads-manager) | One canonical data-flow idiom replaces delegates/notifications/KVO: services emit snapshots, view models replace `@Published` state wholesale — no local merge/diff logic exists anywhere. |
| UserDefaults-backed preference singletons as a reactive state bus | `ReadingPreferences.shared.$reading` re-drives image loading (mushaf-image-reading), edition resources (mushaf-edition-selector), Home lists (sura-juz-index-navigation), notes re-subscription (notes-journaling); more-menu write-through shims into FontSize/QuranContentState prefs (reading-appearance-controls) | A one-line write (`showReading`) triggers app-wide declarative reaction; every observer rebuilds per mushaf change without explicit event wiring. |
| Stale-result guards and cancellation discipline around async loads | Re-check `ReadingPreferences.shared.reading` before AND after awaiting image load + `Task.checkCancellation()` (mushaf-image-reading); `if searchTerm == term` staleness guard (search); `AsyncStream.bufferingNewest(1)` + generation counter collapsing rapid page flips to one write (continue-reading-last-pages); `panningTask?.cancel()` per pan event (word-by-word-popover) | The UI flips faster than storage answers; correctness depends on discarding late results rather than serializing them. |
| Optimistic mutation with precise rollback / identity-guarded undo | `NotesViewModel.deleteItem` restores at original index on failure with `pendingDeletionIDs` (notes-journaling); `deleteReciterFiles` cancels batch then deletes with optimistic hiding (downloads-manager); undo toasts guard on current `bookmark` identity before re-applying (continue-reading-last-pages) | Mutations never block the UI on disk/service; failures self-heal against fresh stream emissions, and stale toasts can't clobber newer state (including sync-driven changes). |
| `#if QURAN_SYNC` dual-build split at factory seams | `AppDependencies` swaps `MobileSyncLastPageService` vs `PersistenceLastPageService` etc.; `BookmarksBuilder` picks collections UI vs flat list; `SettingsRootViewModel` declares two initializers; note editor hides colors (quran-com-cloud-sync, bookmarks-collections-highlights, notes-journaling, settings-support-hub) | The closed-source KMP sync binary stays out of the OSS example build while the same feature targets compile both ways; features never know which backend exists — they call `lastPageService()`. |
| Persistence-backed resilience across process death | `DownloadManager` re-attaches batches at launch via `getOnGoingDownloads()` (downloads-manager); running audio downloads re-observed at launch, stored reciter ID falls back silently (audio-recitation); `AppMigrator` stamps version only after the whole idempotent batch succeeds (app-upgrade-migration) | Multi-hundred-MB asset sets and schema moves survive crashes and background termination; launch always reconciles with on-disk truth. |
| Domain encoded as data, rendering code generic | 7 mushaf editions as pure data in `Model/QuranKit/Sources/Reading.swift` (widths, page-model mapping, metric-dB requirements, inversion flags) (mushaf-edition-selector); `MoreMenuControlsState` `.alwaysOn/.alwaysOff/.conditional` per control (reading-appearance-controls); `SurahSortOrder` ±1 sign-multiplied into comparators (sura-juz-index-navigation); repetition primitives (`Runs.finite/.indefinite`, VerseDelay) live in QueuePlayer not the view model (audio-recitation) | Behavior changes are configuration, not code paths: edition-free renderers, host-consumers configuring menus, one comparator serving three sort axes. |

## 5. Notable observations

**Clever tricks**
- **Text is pixels; geometry is the interface.** Because mushaf pages are pre-rendered images, everything interactive is rebuilt from sidecar databases: `WordFrameProcessor.processWordTiles` post-processing makes `wordAtLocation` a linear scan of scaled rects (word-by-word-popover), highlights are overlay rectangles from `wordFramesForVerse` rather than image manipulation (mushaf-image-reading), and scroll-to-verse resolves through line frames. No text engine, no layout, ever.
- **Editions are asset swaps.** Five Hafs prints map onto just three shared page grids, so changing edition can avoid re-downloading verse text entirely; `removePreviouslyDownloadedResources(exclude:)` keeps exactly one mushaf set on disk.
- **Sign-multiplication sorting:** one persisted ±1 flag drives ascending/descending for suras, juz sections and quarters via `surahSortOrder.rawValue * (a - b) < 0` — no duplicated comparators (sura-juz-index-navigation).
- **Throttled writes done right:** rapid page flips collapse to the newest write through `AsyncStream` `.bufferingNewest(1)` plus a generation counter, instead of queuing I/O (continue-reading-last-pages); download size stats re-scan only when `floor(progress × 2000)` advances (downloads-manager).
- **Same pipeline reused at smaller scale:** the single-verse sheet embeds a full `ContentTranslationViewModel` with a no-op highlights service (translation-reading-mode), and share/copy share one composition path including a copy-pasted-wrong error reason string (share-verses).

**Divergences between similar features**
- **Two reading-position models coexist deliberately:** capped-at-3 offline CoreData `LastPage` history vs the single synced `ReadingPositionBookmark` that exists only under `QURAN_SYNC` (continue-reading-last-pages).
- **Highlights have two representations:** first-class `(verse, color)` entities in sync builds vs CoreData notes with nil text and an Int-encoded color in legacy builds — and the editor hides colors entirely when sync is on (notes-journaling, bookmarks-collections-highlights).
- **WhatsNew marks seen on construction, not dismissal** — reaching the item list counts as seen; dismissing earlier leaves it unseen (whats-new-announcements). Meanwhile search auto-enables a translation when you tap its result (search): similar "state committed as a side effect of navigation," opposite timing philosophies.

**Engineering warnings**
- `try!` twice decoding `whats-new.plist` (force-unwrapped bundle URL + forced decode) — safe only because the resource ships in the same target as the decoder (whats-new-announcements).
- Silent error swallowing with a demonstrably wrong reason string: the share path's `crasher.recordError` says 'Failed to update highlights' (share-verses); image-load errors log directory diagnostics but user-facing display remains a `TODO` (`ContentImageViewModel.swift:106`) (mushaf-image-reading).
- An in-code comment documents that iOS 15's SwiftUI `List` emits invalid UITableView batch updates when every row moves, forcing whole-snapshot `.id(...)` rebuilds for sort toggles (sura-juz-index-navigation); a `UISheetPresentationController`/SwiftUI relayout conflict forced a UIKit form-sheet shell for theme settings (reading-appearance-controls). Both are recorded workarounds worth preserving in any reimplementation.
- Diagnostics export trades privacy for debuggability: sharing logs zips the entire Logs directory plus a recursive JSON dump of all of `UserDefaults.standard` and copies of every SQLite database (settings-support-hub).

**Absent capabilities (verified nowhere in the repo):** no WidgetKit widgets, no Siri/AppIntents shortcuts, no share extension, no share-as-image rendering, and no khatma/streak reading tracker. Sharing is delegated entirely to the system sheet; announcements ship as a bundled plist with no remote config. Reciter folder paths were migrated to Android-compatible slugs ("18" → "sa3d_alghamidi") for path parity across the quran.com app family (app-upgrade-migration).
