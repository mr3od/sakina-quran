# Sura / Juz index navigation
> How **Quran for iOS (github.com/quran/quran-ios)** implements this feature. Sources read from a shallow clone @ main (2026-08-23); repo-relative paths cited throughout.

## 1. What the user sees
The Home tab is a grouped index list. Above the index sits a "Recent pages" section (last-read pages with relative timestamps). A segmented control switches the index between two `HomeViewType` modes: `.suras` (all 114 suras) and `.juzs` (all 240 quarters/hizb). In `.juzs` mode every row previews its first ayah's Arabic text in the current mushaf font (`rightSubtitle: "\(quran: item.ayahText, ...)"` in `Features/HomeFeature/Sources/HomeView.swift`, `quarterView(_:)`) next to the quarter's localized name, ayah reference and starting page number. Sections are juzs; each is expandable/collapsed inline. A toolbar sort button flips the whole list between ascending and descending revelation order.

## 2. Architecture & key files
- `Features/HomeFeature/Sources/HomeViewModel.swift` — `@MainActor` `ObservableObject`; owns `HomeViewType`, `SurahSortOrder` (`ascending = 1`, `descending = -1`), `@Published suras/quarters/lastPages/collapsedJuzs`.
- `Features/HomeFeature/Sources/QuarterItem.swift` — tiny `Identifiable` struct pairing a `Quarter` with its pre-fetched `ayahText: QuranText`.
- `Features/HomeFeature/Sources/HomePreferences.swift` — singleton persisting `surahSortOrder` as a `@TransformedPreference(... transformer: .rawRepresentable(defaultValue: .ascending))` over key `"surahSortOrder"`.
- `Features/HomeFeature/Sources/HomeView.swift` — SwiftUI `HomeViewUI`; generic `sectionsView(items:groupBy:listItem:)` does grouping + sorting + collapsible `NoorSection`s.
- `Features/HomeFeature/Sources/HomeViewController.swift`/`HomeBuilder.swift` wrap it for the UIKit nav stack used by `HomeTabBuilder`.

## 3. Data flow
`HomeViewModel.start()` fans out concurrent `async let` tasks: `loadLastPages()`, `loadSuras()`, `loadQuarters()` (plus `loadReadingBookmark()` only under `#if QURAN_SYNC`). Suras need no I/O — `loadSuras()` just assigns `reading.quran.suras` from the static `QuranKit` model. Quarters do need text: `textForQuarters(_:)` calls `textRetriever.textForVerses(quarters.map(\.firstVerse), translations: [])` (Arabic-only, from the bundled verse DB), then `cleanUpText` strips the hizb marker glyph `"۞"` so previews don't show a stray symbol. All three loaders observe `ReadingPreferences.shared.$reading` (`.prepend(current).values()`), so changing mushaf (e.g. Hafs→Warsh) rebuilds the lists. Sorting lives in the view: `sectionsView` groups by `\ .page.startJuz` (suras) or `\ .quarter.juz` (quarters) and sorts both section keys and items with `surahSortOrder.rawValue * (a - b) < 0` — multiplying the difference by ±1 makes one flag drive both directions without duplicated comparators. Juz expansion state (`collapsedJuzs: Set<Juz>`, default expanded) stays in memory only; selection calls back through injected closures `navigateToPage`/`navigateToAyah(sura.firstVerse / quarter.firstVerse)`.

## 4. Storage & network
No network at all. Inputs are the compiled-in `QuranKit` geometry (suras/juzs/quarters/pages), the bundled `quran.db` verse text via `QuranTextDataService` for quarter previews, and `LastPageService.lastPages(quran:)` (an `AsyncSequence` over the GRDB `last_pages.db`). The only persisted UI state is the sort order integer in UserDefaults via `Core/Preferences`. Under `QURAN_SYNC`, an extra synced reading-position bookmark row appears above Recent Pages.

## 5. Why it is built this way ON THIS PLATFORM
Because the app ships as the composable `QuranEngine` SPM package, Home must work with zero services configured: sura/juz data comes from the pure-model `QuranKit` target, and only the quarter-preview text touches persistence — deliberately fetched once per mushaf change rather than lazily per row, since a `List` row's async fetch would flicker. The `ConfigState`-free, closure-based navigation (`navigateToPage/navigateToAyah` passed at init) keeps the feature decoupled from any specific reader screen, matching the constructor-injection-without-framework DI style. One notable UIKit interop detail: after toggling sort order the code replaces the whole list snapshot with `.id(surahSortOrder.rawValue)` because, per the in-code comment, "iOS 15's SwiftUI List produces invalid UITableView batch updates when every section and row moves at once."

## 6. Edge cases & offline behavior
Fully offline-capable: if the verse-text retrieval fails, `textForQuarters` records the error via `crasher.recordError(..., reason: "Failed to retrieve quarters text")` and returns an empty dictionary, so quarter rows render with blank Arabic previews but remain navigable. Quarter text cleanup also guards against the marker appearing mid-string. Observers cancel prior `AsyncSequence` tasks when the reading changes (`observationTask?.cancel()` plus `Task.isCancelled` checks) preventing stale mushaf rows. Pervasive `crashContext.recordListUpdate(owner:reason:rowsBefore:rowsAfter:generation:)` telemetry logs every mutation reason (`sort_order_changed`, `mode_changed`, `section_expansion_changed`, …) to reproduce table-view crashes in production.
