# Mushaf page-image reading
> How **Quran for iOS (github.com/quran/quran-ios)** implements this feature. Sources read from a shallow clone @ main (2026-08-23); repo-relative paths cited throughout.

## 1. What the user sees
The full 604-page Madani mushaf reproduced pixel-for-pixel: each screen is one (or two, in landscape) scanned/vector page images with authentic Uthmani typography, framed by a header showing sura names and the juz' quarter (`QuranPageHeader`) and a footer with the page number (`QuranPageFooter`, both composed in `Features/QuranImageFeature/Sources/ContentImageView.swift`). The user swipes horizontally right-to-left through pages, pinch-zooms inside `AdaptiveImageScrollView`, and sees colored overlays drawn over verse rectangles (audio/recitation highlights, bookmarks, selection) plus a small marker when a verse is being scrolled to. Sura header ornaments and ayah-end numbers are rendered as separate floating decorations layered on the image, not baked into it.

## 2. Architecture & key files
- `Features/QuranPagesFeature/Sources/QuranPaginationView.swift` — generic pager. `PagingStrategy` is `.singlePage` or `.doublePage`; both wrap a UIKit `PageViewController` (UIPageViewController, `.scroll` transition) exposed to SwiftUI. The whole pager forces `.environment(\.layoutDirection, .rightToLeft)` so swipes match mushaf direction; `Page` is made `Identifiable` via `@retroactive` on `pageNumber`.
- Double-page mode pairs pages with `stride(from:to:by:2)` into `DoublePage(first:second:)` rows laid out in an `HStack` with `QuranSeparators.PageSideSeparator/PageMiddleSeparator` simulating the book gutter; single-page mode inserts only the outer side separator depending on `page.isRightSide`.
- Selection is a `Binding<[Page]>` bridged internally to single-page (`selection[0]`) or double-page bindings, guarded against redundant writes.
- `Features/QuranImageFeature/Sources/ContentImageView.swift` + `ContentImageViewModel.swift` render one page: `AdaptiveImageScrollView` hosts the `UIImage`, decorations, header/footer, and `.quranScrolling(scrollToValue:)` auto-scroll support.
- Host wiring: `Features/QuranContentFeature/Sources/PagesView.swift` chooses the strategy (portrait → single page; landscape only if `TwoPagesUtils.hasEnoughHorizontalSpace()`), and per page builds `imageDataSourceBuilder.build(at: page)` when `quranMode == .arabic`. `.id(viewModel.quranMode)` rebuilds the entire pager on mode switch.

## 3. Data flow
`ContentImageViewModel.loadImagePage()` (async, called from `.task`) asks `ImageDataService.imageForPage(_:)` for an `ImagePage(image:wordFrames:startAyah:)`. Before *and* after the await it checks `ReadingPreferences.shared.reading == reading` and calls `Task.checkCancellation()` — if the user switched reading mode mid-load the result is discarded. Highlights arrive reactively: the constructor sinks `highlightsService.$highlights` and `.scrolling` publishers into `@Published` state. The `decorations` computed property converts verse-level highlights into per-word rectangle colors via `imagePage.wordFrames.wordFramesForVerse(ayah)` and adds the pointer-highlighted word (`wordFrameForWord`). Sura headers/ayah numbers are fetched only for `reading == .hafs_1421`. Scroll-to-verse resolves a target through `lineFramesVerVerse(_:).first`.

## 4. Storage & network
Page images are not bundled; they are downloaded per recitation/width set (paths under `<reading>/images/<width>/`, see the `logFiles` diagnostics in `Domain/ImageService/Sources/ImageDataService.swift`) via the BatchDownloader machinery, then read synchronously off disk with `UIImage(contentsOfFile:)`. A missing file throws `ImageDataServiceError.imageNotFound(page:url:)` after dumping directory listings to logs. Word-frame rectangles come from the GRDB "ayah info" database through `GRDBWordFramePersistence` (`Data/WordFramePersistence`), post-processed by `WordFrameProcessor.processWordFrames` (`Domain/WordFrameService/Sources/WordFrameProcessor.swift`). Per-page bookmarks are Core Data entities surfaced through `PageBookmarkService`; `Features/QuranViewFeature/Sources/QuranInteractor.swift` observes `pageBookmarkService.pageBookmarks(quran:)` and toggles state with `insertPageBookmark`/`removePageBookmark`.

## 5. Why it is built this way ON THIS PLATFORM
Pre-baked page images are the only way to guarantee typographic fidelity of a 1400-year-old script tradition (letter stretching, diacritic stacking, end-of-ayah ornaments) that no iOS text engine can typeset; the trade-off is that text becomes pixels, so every interaction (highlighting, hit-testing, scroll targeting) must be reconstructed from the parallel geometry database shipped alongside the images. UIKit remains deliberately in charge of paging (`README` keeps navigation UIKit) because UIPageViewController gives free physics-based swipe, while SwiftUI handles chrome. Dark mode avoids shipping duplicate assets: `imageRenderingMode` picks `.invertInDarkMode` or `.tinted` based on `reading.usesInvertedQuranImageRenderingInDarkMode` (`ContentImageViewModel.swift:54`). The two-page landscape strategy mirrors holding a real printed mushaf.

## 6. Edge cases & offline behavior
Once a page set is downloaded everything works offline — images load from disk and frames from the bundled/downloaded SQLite db; only the initial download needs network. Stale-load races are explicitly guarded (reading-preference recheck + `Task.checkCancellation`), and failures are routed to `crasher.recordError` (user-facing error display is still a `TODO` in `ContentImageViewModel.swift:106`). Empty `wordFrames` degrade gracefully to an empty `WordFrameCollection` so the page still renders without overlays. The double-page pairing assumes an even page count and indexes `pages[$0 + 1]`, and rotation repositions nothing here because the pager owns layout per orientation change.
