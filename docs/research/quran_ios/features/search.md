# Search across Quran and translations
> How **Quran for iOS (github.com/quran/quran-ios)** implements this feature. Sources read from a shallow clone @ main (2026-08-23); repo-relative paths cited throughout.

## 1. What the user sees
The Search tab (built by `SearchTabBuilder` in `Features/SearchFeature/Sources/SearchBuilder.swift`) opens in an "entry" state showing recent searches and a fixed list of popular terms (`SearchRecentsService.popularTerms`, `Domain/QuranTextKit/Sources/Search/Recents/SearchRecentsService.swift:33`). As the user types, an autocomplete list appears after ~300 ms of idle. Executing a search yields results grouped under section headers per source — the Arabic Quran first, then one section per downloaded translation. Special queries work too: typing "2:255" jumps straight to that verse; a bare number resolves to matching sura/juz/hizb/page. Tapping a translation result switches the app into translation mode, enables that translation if it wasn't selected, and navigates to the ayah.

## 2. Architecture & key files
- UI layer: `Features/SearchFeature/Sources/SearchViewModel.swift` is a `@MainActor ObservableObject` with `@Published` state (`searchTerm`, `autocompletions`, `searchState`, `uiState`, `recents`) rendered by SwiftUI `SearchView.swift`; navigation out of search is a single injected closure `navigateTo: (AyahNumber) -> Void`.
- Engine layer: `Domain/QuranTextKit/Sources/Search/Searchers/CompositeSearcher.swift` composes four `Searcher` implementations behind one protocol (`Domain/QuranTextKit/Sources/Search/Searchers/Searcher.swift`): `NumberSearcher`, `SuraSearcher`, `PersistenceSearcher<QuranText>` (Arabic verses), and `TranslationSearcher`.
- The first three run as `simpleSearchers`; `TranslationSearcher` runs conditionally via `shouldPerformTranslationSearch`.

## 3. Data flow
`start()` launches four concurrent observation loops (`SearchViewModel.start()`): reading-mode changes (which reset `searchTerm`), throttled autocomplete, recents observation, and search execution. Typing mutates `$searchTerm`, which is throttled 300 ms on the main queue and fed to `CompositeSearcher.autocomplete(term:quran:)`. Submitting sets `uiState = .search(term)`; the `$uiState.values()` loop in `observeSearchChanges()` performs the search and applies results only `if searchTerm == term`, a staleness guard against racing queries. Errors are caught into `Result(catching:)`, stored in `@Published error`, and rendered as an empty result set. A successful search calls `recentsService.addToRecents(term)` and logs analytics events (`SearchTerm`, `SearchSections`, `SearchSource`, `SearchResultsCount`).

## 4. Storage & network
Search is entirely local/offline — no network code exists in this path. Arabic text comes from the bundled uthmani database through `GRDBQuranVerseTextPersistence(fileURL: quranFileURL)`; each downloaded translation is opened as its own SQLite file via `GRDBTranslationVerseTextPersistence(fileURL: translation.localPath.url)`, discovered by `LocalTranslationsRetriever` from `Domain/TranslationService`. Only downloaded translations are searchable; there is no remote fallback. Recents/popular terms live in `SearchRecentsService` (its backing store was not inspected within budget).

## 5. Why it is built this way ON THIS PLATFORM
Because the mushaf ships as pre-rendered page images, all searchable text lives in SQLite databases rather than in any text layout, so full-text search reduces to SQL scans over GRDB-backed persistence. The engine sits in Domain (`QuranTextKit`), not the feature target, because the repo distributes itself as an SPM library where consumers compose individual targets — search must be reusable without the Search screen. Translation search is deliberately gated by `shouldPerformTranslationSearch(simpleSearchResults:term:)`: it runs only when simple searches found nothing, or when the query contains no Arabic and isn't only numbers — keeping Arabic queries fast against one bundled db instead of N translation dbs. Results are regrouped per source in `groupedResults` so the UI shows one section per corpus.

## 6. Edge cases & offline behavior
`SearchTerm` (`Domain/QuranTextKit/Sources/Search/Searchers/SearchTerm.swift`) normalizes input aggressively before anything else: it trims/collapses Unicode separators, strips marks/punctuation/symbols/control characters plus tatweel, and builds an Arabic similarity regex mapping hamza/alef/ta-marbuta/ha/ya variants onto each other, so diacritic-insensitive matching is free. Empty or fully-invalid queries return `nil` → empty results. `NumberSearcher.search` parses integer arrays: two components mean sura:ayah (`parseVerseResult`), one component fans out to sura/juz/hizb/page matches. If no autocompletion equals the raw term, the term itself is inserted at index 0 as `.plain`. Changing reading mode (mushaf layout) clears the query since the underlying `quran` object changed. With no translations downloaded, only Quran/sura/number sections appear; nothing degrades or errors.
