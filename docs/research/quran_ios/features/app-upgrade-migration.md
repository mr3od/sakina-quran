# Upgrade migration experience
> How **Quran for iOS (github.com/quran/quran-ios)** implements this feature. Sources read from a shallow clone @ main (2026-08-23); repo-relative paths cited throughout.

## 1. What the user sees
On first launch after an app update that changed on-disk layouts, the window's root view controller is replaced by a full-screen blocking screen: a system spinner above one or more centered lines of explanatory text ("update.filesystem.title" localized string), nothing else — no cancel, no skip. When migration finishes the app UI cross-dissolves in (`transition(to:duration:options: .transitionCrossDissolve)` in `LaunchStartup.showApp(window:)`).

## 2. Architecture & key files
- `Core/AppMigrator/Sources/AppMigrator.swift` — the engine: `Migrator` protocol (`blocksUI: Bool`, `uiTitle: String?`, `execute(update:) async`), `MigrationStatus` (`.noMigration` | `.migrate(blocksUI:titles: Set<String>)`), and `AppMigrator` with `register(migrator:for version: AppVersion)`, `migrationStatus()`, `migrate()`.
- `Core/AppMigrator/Sources/AppVersionUpdater.swift` — persists the last-run version and reports `LaunchVersionUpdate` (`sameVersion`, `firstLaunch`, `update(from:to:)`); `commitUpdates()` stamps the new version only after migration succeeds.
- `Features/AppMigrationFeature/Sources/MigrationView.swift` + `MigrationViewController.swift` — SwiftUI spinner/text view embedded as a full-screen child of a `BaseViewController`; `MigrationViewModel.setTitles` filters empties and sorts alphabetically.
- `Features/AppMigrationFeature/Sources/FileSystemMigrator.swift` and `RecitersPathMigrator.swift` — the two concrete `Migrator`s, both `blocksUI = true`, both titled `l("update.filesystem.title")`.
- `Features/AppStructureFeature/Sources/Launch/LaunchStartup.swift` — registers them (`registerMigrators()`: `fileSystemMigrator` for `"1.16.0"`, `recitersPathMigrator` for `"1.19.1"`) and gates app startup on the result.

## 3. Data flow
`LaunchStartup.upgradeIfNeeded(window:)` runs after protected-data availability is settled (it can wait on `UIApplication.protectedDataDidBecomeAvailableNotification` via `waitForProtectedData`). It calls `appMigrator.migrationStatus()`, which compares the stored version against each registered version using `version.compare($0.0, options: .numeric) == .orderedAscending` — so a fresh install at version N still runs every migrator registered above the shipped baseline. If any pending migrator has `blocksUI`, `window.rootViewController` becomes `MigrationViewController` with the union of `uiTitle`s and `window.makeKeyAndVisible()`; then `await appMigrator.migrate()` runs all pending migrators concurrently inside `withTaskGroup(of: Void.self)`, followed by `updater.commitUpdates()`, and only then `showApp(window:)` builds the real tab bar. `FileSystemMigrator.execute` moves `last_pages.db` and `bookmarks.db` from `FileManager.documentsPath` into the shared `databasesURL` and relocates each reciter's audio folder to `reciter.localFolder()` (reciters fetched from `ReciterDataRetriever.getReciters()`). `RecitersPathMigrator` renames legacy audio directories to Android-compatible slugs (`"18"` → `"sa3d_alghamidi"`, `"mishari_alafasy_cali"` → `"mishari_cali"`, etc.).

## 4. Storage & network
Everything is filesystem surgery on previously downloaded user data: SQLite user DBs (last pages, bookmarks) and multi-hundred-MB gapless recitation archives. `move(_ source:to:)` creates intermediate destination directories then `try? fileManager.moveItem(...)` — same-volume moves are instant renames, so no copying of large audio sets occurs. No network is used; migration is entirely local and idempotent by construction (a missing source fails silently, `commitUpdates` prevents re-runs). The version marker itself lives in UserDefaults via `AppVersionUpdater`.

## 5. Why it is built this way ON THIS PLATFORM
The migrators are version-keyed and registered by the app shell, not the library, because `QuranEngine` is an SPM package: Core provides the generic version-comparison engine while the example app decides which historical layouts exist. Titles are a `Set<String>` so multiple pending migrators deduplicate into one message instead of a list of near-identical strings. Blocking the UI is the honest choice for this app: recitation folders and DBs are moved (not copied) and the reader, audio player and downloads UI all assume the new paths, so letting users in mid-move would surface half-migrated state. Aligning reciter folder names with the Android app's slugs (`RecitersPathMigrator`) keeps the two clients' download caches and server-side path conventions identical. Running migrators concurrently in a task group matters because each is I/O-bound and independent.

## 6. Edge cases & offline behavior
Migration is deferred until `isProtectedDataAvailable` — critical because a device rebooting locked cannot read the Documents directory, and `ProtectedDataStartupState` prevents migrating against unreadable files. `migrationStatus()` short-circuits to `.noMigration` (committing immediately) when no migrators apply, so the common launch path costs nothing. `try?` on every move means a partially-completed prior attempt (crash mid-migration) resumes cleanly: already-moved files fail silently and the rest proceed; the version is only stamped after all migrators finish, so a crash re-runs the whole batch next launch. `firstLaunch` and `sameVersion` both route through `updaters(for:)`, and the migration phase is reported to crash telemetry via `crashContext.setStartupPhase("migrating")` plus a `logger.notice("Performing long upgrade task: \(titles)")`, so stuck upgrades are observable in production. The `MigrationView` itself is deliberately non-animated and text-free of progress percentages because `FileManager.moveItem` offers no progress callback.
