# Quran.com account cloud sync
> How **Quran for iOS (github.com/quran/quran-ios)** implements this feature. Sources read from a shallow clone @ main (2026-08-23); repo-relative paths cited throughout.

## 1. What the user sees
In Settings, an account card (`Features/SettingsFeature/Sources/QuranComAccountCard.swift`) shows sign-in when logged out and, when authenticated, the account email plus actions: open the Quran.com web profile (an `SFSafariViewController` over `quranProfileURL`, `SettingsRootViewModel.openQuranComProfile()`) and sign out. The Bookmarks tab offers a second entry point: `BookmarkCollectionsView.swift:40` wires `signInAction` to `BookmarkCollectionsViewModel.loginToQuranCom()` (`Features/BookmarksFeature/Sources/BookmarkCollectionsViewModel.swift:115`). After signing in on one device, bookmarks, highlights, notes, and last-read position appear on other devices.

## 2. Architecture & key files
- Abstraction: `AuthenticationClient` protocol in `Data/AuthenticationClient/Sources/AuthenticationClient.swift` (login/logout/restoreState/authenticationState/loggedInUser/`authenticate(request:)`/`getAuthenticationHeaders()`).
- Sync implementation: the actor `AuthenticationClientMobileSyncImpl` (`Data/AuthenticationClient/Sources/AuthenticationClientMobileSyncImpl.swift`), entire file wrapped in `#if QURAN_SYNC`, delegating to MobileSync's `SyncAuthService` (`signInWithReauthentication`, `refreshAuthentication`, `signOut`, `authenticationHeaders`).
- Wiring: `Features/AppDependencies/Sources/AppDependencies.swift` exposes `authenticationClient` and `quranDataService` under `#if QURAN_SYNC` and swaps service factories — `lastPageService()` returns `MobileSyncLastPageService` vs `PersistenceLastPageService`; sync builds also gain `readingBookmarkService()`, `mobileSyncNoteService()`, `ayahBookmarkCollectionService()`, `ayahHighlightService()`.

## 3. Data flow
Sign-in from Settings: `SettingsRootViewModel.loginToQuranCom()` logs analytics (`analytics.quranSyncSignIn(from: .settings)`), calls `authenticationClient.login(on: viewController)`, then refreshes `@Published isAuthenticated` / `loggedInUser`. Login UI itself is produced by the closed-source MobileSync KMP framework (`signInWithReauthentication`), not by app code. On the reading side, `QuranInteractor.start()` (`Features/QuranViewFeature/Sources/QuranInteractor.swift:122`) starts dedicated observers — `QuranReadingBookmarkObserver.swift`, `QuranSyncedHighlightsObserver.swift`, `QuranSyncedCollectionsObserver.swift`, `QuranNotesObserver.swift` — each of which spawns its own `Task` in `start()` and keeps mushaf UI in step with remote changes through the `quranDataService`. The internal stream/polling mechanism inside MobileSync was not inspected within budget; the app-side contract is "start a task, consume updates."

## 4. Storage & network
When sync is enabled, bookmarks/highlights/notes/reading position are served by MobileSync-backed services over the network to Quran.com's API rather than local CoreData: auth tokens are attached via `getAuthenticationHeaders()` / `authenticate(request:)`, which inject headers into outgoing `URLRequest`s and throw `.notAuthenticated` if empty. `restoreState()` refreshes credentials at startup; Settings uses `await authenticationClient.safelyRestoreState()` so failures don't surface as errors. In non-sync builds the same features read/write local CoreData persistence (`notePersistence`, `pageBookmarkPersistence`, `lastPagePersistence`). The dependency itself is conditional in `Package.swift`: the `QURAN_SYNC` env var (any value except "0"/empty) defines the compilation flag, and `mobile-sync-spm` is pulled from `https://github.com/quran/mobile-sync-spm.git` (from 0.1.20) or a local checkout via `MOBILE_SYNC_SPM_PATH`.

## 5. Why it is built this way ON THIS PLATFORM
The sync engine is Kotlin Multiplatform shared with quran-android, so iOS wraps it behind a thin Swift actor rather than reimplementing protocol logic. Because that binary is closed-source while the app ships as an open-source SPM library, every touchpoint is gated by `#if QURAN_SYNC` — even `SettingsRootViewModel` declares two distinct initializers, and `AyahMenuViewModel` swaps note/bookmark actions per flag — keeping the OSS example build compiling with zero sync code. Constructor injection plus the `AppDependencies` factory extensions mean feature targets never know which backend exists; they just call `lastPageService()`. This is also why UIKit navigation matters here: `login(on: UIViewController)` hands a presenting view controller to the KMP framework, which presents its own UI.

## 6. Edge cases & offline behavior
Cancellation is a first-class outcome: `SettingsRootViewModel.loginToQuranCom()` catches `AuthenticationClientError.cancelled` separately and logs without setting `error`, so dismissing the login sheet is not treated as failure. `AuthenticationClientError` maps `MobileSyncAuthenticationError` cases (.cancelled/.networkFailure/.authenticationFailed) one-to-one. Logout errors leave `isAuthenticated` untouched and populate `@Published error` for the card to display. Offline users still get full local functionality because the non-sync fallbacks (CoreData notes, page bookmarks, last-page persistence) remain the data path whenever the flag is off or the network is down; remote convergence resumes when observers' tasks receive fresh state.
