# Settings and support hub
> How **Quran for iOS (github.com/quran/quran-ios)** implements this feature. Sources read from a shallow clone @ main (2026-08-23); repo-relative paths cited throughout.

## 1. What the user sees
The Settings tab is a grouped list: a reading-selector row ("Reading" preferences), an audio section (download/play amount selector, streaming toggle, audio manager), a translations row, a support section (Donate, Share the app, Write a review, Contact us) and a Diagnostics row. Under `QURAN_SYNC` a Quran.com account card with login/logout and a profile link appears too.

## 2. Architecture & key files
- `Features/SettingsFeature/Sources/SettingsRootViewModel.swift` — `@MainActor ObservableObject`; constructor-injected with `AnalyticsLibrary`, `ReviewService`, `AudioDownloadsBuilder`, `TranslationsListBuilder`, `ReadingSelectorBuilder`, `DiagnosticsBuilder` and the owning `UINavigationController`.
- `Features/SettingsFeature/Sources/SettingsRootView.swift` — SwiftUI list of `NoorBasicSection`s binding `$streamingEnabled`/`$appearanceMode` and calling the view-model navigation methods.
- `Features/SettingsFeature/Sources/Diagnostics/DiagnosticsViewModel.swift`, `DiagnosticsService.swift`, `DiagnosticsView.swift`, `DiagnosticsBuilder.swift` — the debug-logs sub-feature; `DiagnosticsPreferences` persists `enableDebugLogging` under UserDefaults key `"enableDebugLogging"`.
- `Features/SettingsFeature/Sources/ContactUsService.swift`, `UIViewController+Share.swift`, `QuranComAccountCard.swift` — mail-compose, share-sheet helper and the sync-gated account UI.

## 3. Data flow
The view model is a thin navigation coordinator over feature builders: `navigateToAudioManager()`, `navigateToTranslationsList()`, `navigateToReadingSelectors()` and `navigateToDiagnotics()` each call `builder.build()` (or `build(navigationController:)` for diagnostics) and push the returned `UIViewController` — the same Builder pattern every other screen uses, keeping Settings free of child-feature logic. Two-way settings bindings are explicit: `@Published streamingEnabled`/`appearanceMode` write through in `didSet` to `AudioPreferences.shared` and `ThemeService.shared`, while the init also subscribes `themeService.appearanceModePublisher.assign(to: &$appearanceMode)` so external theme changes reflect back. The download/play-amount row pushes a generic `SingleChoiceSelector` (`showSingleChoiceSelector(title:sections:selected:itemText:onSelection:)`) over `[AudioEnd.juz, .sura, .page, .quran]`, writing `audioPreferences.audioEnd` and popping on selection. External actions: `shareApp()` shares the App Store URL `id1118663303` via `navigationController.share`, `donate()` presents `SFSafariViewController` on `https://give.quran.foundation/ios`, `writeReview()` delegates to `ReviewService.openAppReview()`, `contactUs()` presents the mail controller from `ContactUsService`. Diagnostics: toggling the switch writes `DiagnosticsPreferences.shared.enableDebugLogging`; "share logs" calls `DiagnosticsViewModel.shareLogs()`, which builds a zip and presents it on the share sheet, deleting the temp file in the share-sheet completion (`cleanUp`).

## 4. Storage & network
All toggles live in UserDefaults via `Core/Preferences` singletons (`AudioPreferences.shared.audioEnd/streamingEnabled`). The diagnostics zip (`DiagnosticsService.buildDiagnosticsZip()`) is the one place user data leaves the device, and only on explicit action: it creates a temp `<UUID>.zip` of the whole `logsDirectory`, first dropping an `extras/` folder inside it containing `UserDefaultsData.json` — the entire `UserDefaults.standard.dictionaryRepresentation()` recursively JSON-serialized (Data → base64, Date → ISO8601) — plus copies of every file in `databasesDirectory` (verse/translation/last-page SQLite DBs), then `Zip.zipFiles(paths: [logsDirectory], ...)`. Network use is limited to StoreKit review prompts, mail and the donation Safari page; no settings value is fetched remotely.

## 5. Why it is built this way ON THIS PLATFORM
Because the package is consumed piecemeal, Settings cannot hard-reference child screens: it receives Builders, so a consumer can omit translations or audio downloads entirely. The `#if QURAN_SYNC` split in the same file shows the open-source build shipping without account features while the production binary adds `AuthenticationClient` login/logout (`loginToQuranCom()`/`logoutFromQuranCom()` with `analytics.quranSyncSignIn(from: .settings)`) and a profile URL injected at construction. Navigation stays on `UINavigationController` (per the repo's UIKit-navigation rule) even though the screen content is SwiftUI, and every action is `logger.info`-instrumented with the same "Settings: …" prefix used across features. Bundling the full UserDefaults dump + databases into the log zip trades privacy for debuggability — acceptable because it is user-initiated share-sheet egress, not silent upload.

## 6. Edge cases & offline behavior
Everything except review/donate/mail works offline. Diagnostics failures surface as `@Published error` rather than crashes; `try?`-guarded copies mean a locked or missing database file just omits it from the zip. The `extras` directory is created inside the logs dir and removed in a `defer`, and the zip itself is cleaned up in the share completion, so no temp data lingers if the share sheet is cancelled. `streamingEnabled`'s `didSet` guards against redundant writes (`guard streamingEnabled != audioPreferences.streamingEnabled`), avoiding feedback loops with the preference publisher. Login errors are caught into `self.error` with cancellation handled separately (`AuthenticationClientError.cancelled`).
