# Verse-by-verse translation mode
> How **Quran for iOS (github.com/quran/quran-ios)** implements this feature. Sources read from a shallow clone @ main (2026-08-23); repo-relative paths cited throughout.

## 1. What the user sees
A segmented control in the "more" menu flips the whole reading surface between `Arabic` (mushaf images) and `Translation` (a scrolling list). In translation mode each verse renders as: Arabic Uthmani text with Arabic-Indic verse numeral, then the text of every selected translation in order, translator attribution when more than one is selected, and separators between verses; sura-name banners appear at sura boundaries and a page header/footer bookend the list. Long translations collapse behind a "read more" link, footnote superscripts open a footnote popup, and tapping a verse opens a focused single-verse sheet with previous/next toolbar chevrons.

## 2. Architecture & key files
- `Features/MoreMenuFeature/Sources/views/MoreMenuModeSelector.swift` — SwiftUI segmented `Picker` over `QuranMode` (`.arabic`/`.translation`); `MoreMenuViewModel` persists the choice to `preferences.quranMode`.
- `Features/QuranContentFeature/Sources/PagesView.swift` — the same `QuranPaginationView` hosts both modes: `switch viewModel.quranMode { case .arabic: imageDataSourceBuilder... case .translation: translationDataSourceBuilder... }`, with `.id(viewModel.quranMode)` forcing a full pager rebuild on toggle.
- `Features/QuranTranslationFeature/Sources/ContentTranslationViewModel.swift` + `ContentTranslationView.swift` — list state and item assembly (`items(quranFont:)` producing a flat `[TranslationItem]`: `.suraName`, `.arabicText`, `.translationTextChunk`, `.translationReferenceVerse`, `.translatorText`, `.verseSeparator`, page header/footer).
- `Features/TranslationVerseFeature/` — the single-verse sheet: `TranslationVerseViewController` (UIKit navigation bar with close, overflow, and RTL-aware next/prev `UIBarButtonItem`s) hosting an embedded `ContentTranslationView`.

## 3. Data flow
`ContentTranslationViewModel.load()` resolves selected IDs through `LocalTranslationsRetriever.getLocalTranslations()`, then fetches Arabic plus all translations in one call — `dataService.textForVerses(requestedVerses, translations:)` (`Domain/QuranTextKit`). It re-checks `verses == requestedVerses && selectedTranslations == requestedTranslationIds` after awaiting and discards stale results. The view model subscribes to four preference streams (`SelectedTranslationsPreferences.$selectedTranslationIds`, both `FontSizePreferences` sizes, `ReadingPreferences.$reading`) so settings changes re-render live. `items(quranFont:)` derives rows on demand; truncation splits any string over `maxChunkSize = 800` chars at the last space, marks the last chunk `.readMore = true`, and `openURL(.readMore)` stores expanded ranges in `expandedTranslations[AyahNumber: [Translation: [Range<String.Index>]]]`. Footnote taps route through `TranslationURL.footnote(translationId:sura:ayah:footnoteIndex)` to set the published `footnote`. Every mutation funnels through `recordListUpdate(reason:)` which logs row-count deltas to `crashContext.recordListUpdate(owner: "quran_translation", ...)`.

## 4. Storage & network
Arabic verse text lives in the bundled `quran.db`; each downloaded translation is its own SQLite database opened by `GRDBTranslationVerseTextPersistence` (wired alongside `GRDBQuranVerseTextPersistence` per `Domain/QuranTextKit/Sources/Search/Searchers/CompositeSearcher.swift`). Translation packs are discovered/downloaded via the Translations screen and BatchDownloader; once present, reading is fully offline. Selections and font sizes persist in the UserDefaults-backed `Core/Preferences` singletons.

## 5. Why it is built this way ON THIS PLATFORM
The mode switch is deliberately destructive (`.id(quranMode)` rebuilds the pager) because the two modes have irreconcilable layout models — fixed page images versus flowing text — so sharing scroll position would be meaningless. Reusing one `ContentTranslationViewModel` inside the single-verse sheet (with a no-op `QuranHighlightsService` injected in `TranslationVerseViewModel.init`) avoids a second rendering pipeline: the sheet is literally the same list constrained to `[currentVerse]`, with `showHeaderAndFooter = false`. The chunked-text design (800-char chunks as separate list items) exists for UIKit/SwiftUI cell recycling performance — huge attributed strings in one cell stall scrolling. Presentation stays UIKit (`presenter?.presentTranslatedVerse` in `Features/QuranViewFeature/Sources/QuranInteractor.swift`), consistent with the repo's UIKit-for-navigation rule, while `actions.updateCurrentVerseTo` closes the loop back into SwiftUI by calling `contentViewModel.highlightTranslationVerse(verse)`.

## 6. Edge cases & offline behavior
Missing translation databases are filtered out by the `compactMap` on installed translations, so deleting a pack never crashes the list. Cancellation between the two awaits prevents ghost content after fast page changes. Next/previous buttons disable at sura boundaries via `AyahNumber.next/previous` nil checks (`TranslationVerseViewModel.next()`), and opening the sheet dismisses any already-presented controller first (`dismissPresentedViewController`). Highlight sync uses `firstScrollingVerse()` deferred one runloop via `DispatchQueue.main.async`. Errors are recorded with `crasher.recordError` but user-visible error UI remains a `TODO` (`ContentTranslationViewModel.swift:268`); audio-driven auto-scroll targets items by matching `item.id.ayah`.
