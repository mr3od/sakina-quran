# Bookmark backup import/export
> How **Quran for Android (github.com/quran/quran_android)** implements this feature. Sources read from a shallow clone @ main (2026-08-23); repo-relative paths cited throughout.

## 1. What the user sees

All entry points live under **Settings → Advanced Settings** (`ui/fragment/QuranSettingsFragment.kt` routes the `key_prefs_advanced` row to `QuranAdvancedPreferenceActivity`, which hosts `QuranAdvancedSettingsFragment`). The rows are declared in `app/src/main/res/xml/quran_advanced_preferences.xml` with keys `importKey`, `exportKey`, `exportKeyCSV` (`app/.../data/Constants.kt:80-82`) and titles "Import", "Export", "Export CSV" (`app/src/main/res/values/strings.xml:223-228`, summaries "Import bookmarks and tags" / "Export a copy of bookmarks and tags" / "... in CSV").

- **Export (JSON)**: tapping Export gathers all tags + ayah bookmarks + recent pages + last-read bookmark and writes a fixed-name file `Android/data/<pkg>/files/backups/quran_android.backup`. A system share sheet (`ACTION_SEND`, MIME `application/json`) then offers to send it anywhere. If exactly one activity can handle the share — i.e. only Quran itself, via its own `QuranImportActivity` intent filter — no chooser is shown; instead a toast says "Data exported to <path>" (`onBookmarkExportSuccess`, QuranAdvancedSettingsFragment.kt:233-253).
- **Export CSV**: same pipeline but writes `quran_android.backup.csv`; a spreadsheet-friendly one-way dump (never re-imported). Same share-or-toast outcome.
- **Import**: tapping Import opens the system document picker (`ACTION_GET_CONTENT`, type `*/*` narrowed by `EXTRA_MIME_TYPES = ["application/*", "text/*"]`, QuranAdvancedSettingsFragment.kt:128-137). The picked URI is handed to a dedicated translucent flow: `QuranImportActivity` parses the file off-thread, then shows a confirmation dialog — "If you import this file, it will add %1$d bookmark(s) and %2$d tag(s) to your current data. Import?" (`showImportConfirmationDialog`, strings.xml `import_data_and_merge`) — and on success shows an "Import Successful" toast and finishes.
- **External entry points into import** (no settings navigation needed): `QuranImportActivity` is `android:exported="true"` in `app/src/main/AndroidManifest.xml:144-168` with an `ACTION_SEND` filter for `application/json` (share a backup straight from Gmail/Drive into the app) and `ACTION_VIEW` filters matching `file://...*.backup` path patterns (tap a backup file in a file manager).

There is no progress UI beyond the dialog/toast cycle, no scheduling of backups, and no restore-from-cloud option — cloud sync exists separately in `feature/sync`.

## 2. Architecture & key files

- `app/.../ui/fragment/QuranAdvancedSettingsFragment.kt` → `PreferenceFragmentCompat` hosting the three rows; field-injected with `BookmarkImportExportModel` via `(applicationContext as QuranApplication).applicationComponent.inject(this)`; owns the Rx `Disposable`s and the share-intent logic.
- `app/.../QuranImportActivity.java` → headless-ish `AppCompatActivity` implementing the view side of import: confirmation dialog, error dialogs ("Invalid backup file...", permissions error), result toast. Implements `OnRequestPermissionsResultCallback` and forwards to the presenter.
- `app/.../presenter/QuranImportPresenter.kt` → classic MVP presenter, `@SingleIn(AppScope)` Metro scope, bound/unbound from `onResume`/`onPause`. Owns URI parsing strategy, permission dance, and subscription lifecycle. Depends on `ContentResolverOps` (`presenter/ContentResolverOps.kt`), a small interface over `ContentResolver` (`openInputStream` / `openFileDescriptor`) that exists purely so Robolectric tests can fake resolver behavior.
- `app/.../model/bookmark/BookmarkImportExportModel.kt` → the feature's domain model. Rx3 façade (`Single<Uri>` exports, `Observable<Boolean>` import, `Single<BookmarkData>` parse) that internally bridges to suspend DAO calls via `runBlocking` inside `Schedulers.io()` callables.
- `app/.../model/bookmark/BookmarkJsonModel.kt` → Moshi serialization boundary: one `JsonAdapter<BookmarkData>` used for both directions, plus a top-level `toCSV(sink, BookmarkData)` extension delegating to `BookmarkCSVAdapter.kt`.
- `app/.../model/bookmark/BookmarkCSVAdapter.kt` → 18-line CSV writer; export-only.
- `common/data/.../model/bookmark/BookmarkData.kt` → the wire schema (`@JsonClass(generateAdapter = true)` Moshi data class): `tags: List<Tag>`, `bookmarks: List<Bookmark>`, `recentPages: List<RecentPage>`, `readingBookmark: BackupReadingBookmark?`, `pageType: String?`. Companion models `Tag(id,name)`, `Bookmark(id,sura?,ayah?,page,timestamp,tags,ayahText?)`, `RecentPage(page,timestamp)`, `BackupReadingBookmark(type:"ayah"/"page",...)` live beside it and each carry a `getCommaSeparatedValues()` helper feeding the CSV path.
- `common/bookmark/.../importdata/BookmarkBackupImportNormalizer.kt` → pure-Kotlin transform from legacy `BookmarkData` shape to the mobile-sync import shape (`MobileSyncImportData`); this is where dedup, timestamp normalization, page→ayah conversion and tag-name merging happen.
- `common/bookmark/.../importdata/MobileSyncImporter.kt` → interface + `MobileSyncImporterImpl` (`@SingleIn(AppScope)`, `@ContributesBinding`) that maps `MobileSyncImportData` → KMP-library types (`PersistenceImportData`, `ImportAyahBookmark`, `ImportCollection`, ...) and calls `com.quran.shared.persistence.repository.importdata.PersistenceImportRepositoryImpl` (external dependency `com.quran:mobile-sync`, pinned in `gradle/libs.versions.toml:147`).
- `common/bookmark/.../di/MobileSyncDatabase.kt` → wraps the shared multiplatform SQLDelight `QuranDatabase(DriverFactory(context))` — the actual sink of an import, and also the live store behind bookmarks today.
- `common/bookmark/.../model/ReadingBookmarkPageMapper.kt` → mushaf-layout seam: translates pages between the backup's `pageType` (madani/warsh/...) and canonical storage numbering using per-pageType `PageProvider` → `QuranInfo` caches; also validates sura/ayah ranges.
- `app/.../model/bookmark/LegacyBookmarksMigrator.kt` → sibling consumer of the *same* `MobileSyncImporter` (with `LegacyBookmarkMigrationNormalizer`) for the silent DB-to-mobile-sync migration; backup import is deliberately routed through the identical funnel.

Seams worth noting: `ContentResolverOps` (testability of SAF), `BookmarksDao`/`RecentPagesDao`/`ReadingBookmarksDao`/`Settings` (`common/data/dao`), the `pageType` string embedded in the payload as forward-compatibility for non-madani mushafs, and the `MobileSyncImporter` interface which decouples app-side parsing from the shared KMP persistence library.

## 3. Data flow

**Export (JSON or CSV):**
1. Row click → `bookmarkImportExportModel.exportBookmarksObservable()` (or `exportBookmarksCSVObservable()`); fragment guards against double-fire with a single reusable `exportSubscription` field (QuranAdvancedSettingsFragment.kt:139-179).
2. `bookmarkDataWithRecentsObservable()` runs `runBlocking { ... }` on `Schedulers.io()`: reads `bookmarksDao.tags()`, `bookmarksDao.bookmarks(BookmarkSortOrder.SORT_DATE_ADDED)` filtered by `filterNot { it.isPageBookmark() }` (legacy whole-page bookmarks are intentionally excluded from modern exports — they get reconstructed at import time instead), `recentPagesDao.recentPages()`, and `readingBookmarksDao.readingBookmark()`, which is converted via `BackupReadingBookmark.fromReadingBookmark(...)` resolving the ayah's page through `pageMapper.suraAyahToPage(sura, ayah, pageMapper.currentPageType())`. The current `pageType` string is stamped into the payload.
3. `exportBookmarks(data)` writes to `<getExternalFilesDir(null)>/backups/quran_android.backup` via okio (`file.sink().buffer()` → `jsonModel.toJson(sink, data)`), then wraps the file in a `FileProvider` content URI using authority `<applicationId>.fileprovider` — the `file_authority` string resource is generated per-variant in `app/build.gradle.kts:139` and backed by `res/xml/file_paths.xml` mapping only `external-files-path backups/`.
4. Back on `AndroidSchedulers.mainThread()`, `createShareIntent(uri)` builds `ACTION_SEND` + `FLAG_GRANT_READ_URI_PERMISSION` + type `application/json`; the chooser-vs-toast branch described above runs. Errors surface as toast `export_data_error` guarded by `isAdded`.

**Import:**
1. Picker result → `onActivityResult` starts `QuranImportActivity` with `intent.data = pickedUri`; alternatively the OS launches it directly via SEND/VIEW.
2. `QuranImportPresenter.bind()` → `handleIntent()` extracts `intent.data` or `EXTRA_STREAM`. `parseIntentUri(uri)` first tries `parseUri` (`openFileDescriptor` → `FileInputStream(fd).source().buffer()`); if that yields nothing or throws, `handleExternalStorageFile(uri)` requests legacy `WRITE_EXTERNAL_STORAGE` and retries through `parseExternalFile` (`openInputStream`) — the fallback for raw `file://` URIs from old devices.
3. Either source feeds `getBookmarkDataObservable`: `readBookmarks(source)` defers `jsonModel.fromJson(source)` onto `Schedulers.io()`. Success → `showImportConfirmationDialog(bookmarkData)` (dialog reports `bookmarks.size` / `tags.size`); parse error/completion → error dialog. Cancel finishes the activity; OK → `presenter.importData(data)`.
4. `importBookmarksObservable(data)` wraps `importBookmarks` in `Observable.fromCallable(...).subscribeOn(Schedulers.io()).cache()` — `.cache()` means a configuration change re-subscribes to the completed observable instead of importing twice. Inside, still via `runBlocking`: `backupImportNormalizer.normalize(data)` produces `MobileSyncImportData`, skipped entirely if `isEmpty()`, then `mobileSyncImporter.importData(importData, deleteExisting = false)` merges it into the shared `QuranDatabase`. Result flows back as `true` → `showImportComplete()`.

**Normalization detail (BookmarkBackupImportNormalizer.normalize):**
- Tags become `ImportCollection`s keyed by *name*, not backup id: blank names dropped, duplicate names merged to one collection (`CollectionState.from`), stable sort by numeric legacy id first. Backup tag ids are used only as lookup keys to link bookmarks to collections (`importIdForBackupTagId`), never reused as local ids; synthetic collection importIds are `"backup-collection-N"`, collision-checked against reserved ids.
- Each bookmark: legacy page bookmarks (sura/ayah null) are converted to an ayah bookmark at the *first ayah of the page* (`sourcePageToSuraAyah(page, sourcePageType)`) and additionally linked to an auto-created collection named "Old Page Bookmarks" (`R.string.old_page_bookmarks`, created once per import). Ayah bookmarks with null or out-of-range sura/ayah (`isValidSuraAyah` against the storage `QuranInfo`) are silently dropped. Bookmarks sharing a `SuraAyah` merge into one `BookmarkState`, keeping max timestamps per collection link.
- Timestamps pass through `Long.legacyTimestampMillis()` (`common/bookmark/.../time/LegacyTimestamp.kt`): values above 10_000_000_000 are already millis, otherwise seconds×1000 — old backups stored seconds.
- Recent pages collapse to one reading session per `SuraAyah` keeping the newest timestamp; `BackupReadingBookmark` becomes either an `Ayah` or `Page` reading bookmark, with pages remapped `sourcePageToStoragePage` using the payload's `pageType` (falling back to the device's current page type when absent).

## 4. Storage & network

- **Backup JSON schema** (Moshi generated adapters, field names as declared): `{"tags":[{"id","name"}], "bookmarks":[{"id","sura","ayah","page","timestamp","tags":[tagId...],"ayahText"?}], "recentPages":[{"page","timestamp"}], "readingBookmark":{"type":"ayah"|"page","sura"?,"ayah"?,"page"?,"timestamp"}, "pageType":"madani"|...}`. IDs are strings today; `LegacyBackupStringAdapter` (registered `JsonAdapter<String>` in `BookmarkJsonModel.init`) accepts bare numbers so pre-migration backups like `{"id":1,...}` (see `TAGS_JSON` in `BookmarkImportExportModelTest.kt:571-573`) still parse.
- **Files written**: `Android/data/<pkg>/files/backups/quran_android.backup` and `quran_android.backup.csv` — fixed names, overwritten each export (no versioning/timestamps in the filename). Exposed only through FileProvider authority `<applicationId>.fileprovider` scoped to `backups/`. No cleanup job removes stale backups.
- **CSV layout** (one-way): header line copied from the first bookmark's column list `type, sura, ayah, page, timestamp, tags`; rows `bookmark, 2, 255, 50, <millis>, Tag1|Tag2|` (tags pipe-separated, trailing delimiter quirk in `Bookmark.getSemiColonSeparatedTags`), `recent,,, 12, 1000`, `reading_bookmark, 2, 255, <page>, 999`. With zero bookmarks the header degenerates to literal `null` because of `firstOrNull()?.getCommaSeparatedNames()` string interpolation (`BookmarkCSVAdapter.toCSV`). Verified expectations in `BookmarkImportExportModelTest.testExportBookmarksCsv*`.
- **Destination database**: imports land in the shared multiplatform SQLDelight `QuranDatabase` (`MobileSyncDatabase`), the same store `BookmarksDaoImpl` now fronts through `com.quran.shared.persistence` repositories — meaning an imported backup is immediately visible to the quran.com cloud sync stack, not just the UI. The legacy `Bookmark.sq`/`Tag.sq`/`BookmarkTag.sq`/`LastPage.sq` schemas still exist under `common/bookmark/src/main/sqldelight` but the DAO layer has moved to the shared repositories. `deleteExisting=false` makes import additive/merge-only.
- **Network**: none. The entire feature is offline; the only OS-level interprocess surface is FileProvider shares and SAF picks.

## 5. Why it is built this way ON THIS PLATFORM

- **Scoped storage drove the FileProvider design.** Since Android 10/11 the app cannot write arbitrary shared storage, so the backup goes to app-specific external storage (`getExternalFilesDir`) — writable without any runtime permission — and leaves the device via `FileProvider` + `ACTION_SEND`. The remaining `WRITE_EXTERNAL_STORAGE` code path in `QuranImportPresenter.handleExternalStorageFile` survives only as a fallback for `file://` URIs that old `ACTION_VIEW` launches produce; SAF content URIs need no permission at all. Contrast with the neighboring storage-move feature in the same fragment, which still juggles KitKat/scoped-storage warning dialogs because it touches real shared paths.
- **The picker/share-sheet model outsources filesystem UI.** Rather than building a file browser, import delegates to `ACTION_GET_CONTENT` and export to the share sheet — consistent with Android's storage UX and with the exported `QuranImportActivity` intent filters that make `.backup` files one tap away from any file manager or email attachment.
- **Fixed-path, fixed-name backups suit a background-free design.** Export is a single short-lived Rx chain on `Schedulers.io()` within the foreground fragment/presenter lifecycle; there's no WorkManager job, no foreground service, no notification — a bookmark JSON is kilobytes, so process-death risk during the write is negligible. The `.cache()`d import observable plus an app-scoped `@SingleIn(AppScope)` presenter is the cheap insurance for rotation instead of a worker.
- **The import pipeline was retargeted at the sync database.** Historically import wrote straight into the local bookmarks SQLite tables; today `BookmarkBackupImportNormalizer` + `MobileSyncImporter` translate the legacy payload into the shared KMP persistence model (`PersistenceImportData`) that quran.com sync consumes. That buys one normalizer shared by two producers (backup files and `LegacyBookmarksMigrator`'s one-time DB migration) and makes imported data sync-ready. It also explains the odd Rx-outside/coroutines-inside shape: the app shell is still Rx3 MVP here while everything below the model boundary is suspend functions over SQLDelight, bridged with `runBlocking` inside IO schedulers.
- **`pageType` in the payload is a multi-flavor constraint.** The app ships madani/warsh/qaloon/naskh mushafs with different page counts, so a page number alone is ambiguous. Stamping the exporting device's page type and running every page through `ReadingBookmarkPageMapper` (per-type cached `QuranInfo`) lets a warsh backup restore onto a madani install without corruption. A web/desktop port would sidestep all of this by storing sura:ayah coordinates canonically and treating pages purely as render-time derivations.
- **JSON vs CSV split reflects platform share mechanics**: JSON round-trips through the app (and now the sync engine); CSV exists because Android users commonly want spreadsheets, and `ACTION_SEND` with a plain text MIME reaches editors directly.

## 6. Edge cases & offline behavior

- **Corrupt/foreign input**: malformed JSON raises `IOException`/Moshi exceptions inside `readBookmarks` (`testReadInvalidBookmarks` asserts an error terminal event), surfaced as the dialog "Invalid backup file (or unable to read backup file)". An empty-but-valid document would hit `jsonAdapter.fromJson(...)!!` NPE and land in the same handler. Non-backup files picked from the wildcard picker therefore fail safely before any write occurs.
- **Partial/legacy payloads**: missing fields default via Kotlin defaults (`emptyList()` etc.) thanks to `@JvmOverloads` constructors; numeric IDs from pre-string-era backups are coerced by `LegacyBackupStringAdapter`; second-vs-millisecond timestamps are auto-detected by the 10^10 threshold; unknown `readingBookmark.type` values normalize to null and are skipped.
- **Bad rows, not bad files**: individual invalid bookmarks (null sura/ayah on a non-page bookmark, out-of-range ayah counts, invalid pages) are dropped row-by-row rather than failing the import; blank tag names are dropped; duplicate tag names collapse into one collection so re-importing the same backup twice doesn't fork tags.
- **No destructive restores**: `deleteExisting=false` always merges; the confirmation dialog frames it as "add". There is no "replace all" mode exposed.
- **Interruption/rotation**: import work continues in the app-scoped presenter after the activity unbinds; rebind resubscribes to the `.cache()`d observable and shows the completion toast once. Export uses a nullable-subscription guard so a double-tap can't spawn parallel exports; `onDestroy` disposes both subscriptions and dismisses any lingering dialog.
- **Permissions edge**: denied `WRITE_EXTERNAL_STORAGE` in the fallback path shows a distinct `import_data_permissions_error` dialog and aborts; `canRequestWriteExternalStoragePermission` avoids spamming permanently-denied apps. Modern SAF picks bypass this entirely. The presenter also flags `requestingPermissions` so a `bind()` after grant doesn't re-parse prematurely.
- **First-run vs upgrade**: fresh installs have empty DAOs, so exports contain recents/reading bookmark only; upgrades are handled by `LegacyBookmarksMigrator.migrateIfNeeded()` (mutex + settings flag `haveMigratedLegacyBookmarksToMobileSync`), which funnels the old DB through the same importer so subsequent backups use the new format. Old page-only bookmarks never appear verbatim again — they re-enter as ayah bookmarks under a generated "Old Page Bookmarks" collection.
- **Locale/i18n**: the special collection name is resolved via `appContext.getString(R.string.old_page_bookmarks)` at import time and matched by name against existing collections, so a name-collision across locales merges rather than duplicates; Arabic-heavy content lives in data, not UI strings, so RTL concerns don't touch this feature. Accessibility relies entirely on standard `Preference` rows and framework dialogs — nothing custom is rendered.
