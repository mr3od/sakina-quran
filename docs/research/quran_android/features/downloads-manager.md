# Download manager with progress notifications
> How **Quran for Android (github.com/quran/quran_android)** implements this feature. Sources read from a shallow clone @ main (2026-08-23); repo-relative paths cited throughout.

## 1. What the user sees
A single Android notification ("Downloading…") appears the moment any download starts — page-image zips, recitation audio, translation databases, or the Arabic search DB — with a determinate progress bar, per-file counters ("file 3 of 115"), and a cancel action (`app/src/main/java/com/quran/labs/androidquran/service/util/QuranDownloadNotifierImpl.java`, `Constants.DOWNLOAD_CHANNEL`). In-screen surfaces (download manager, translation manager, search) mirror the same state live because the service also broadcasts progress locally. Failures surface typed messages (no network, insufficient disk space, corrupt download, permissions) with retry affordances; transient failures show "will retry".

## 2. Architecture & key files
One foreground `Service` fans out into pluggable per-shape strategies:
- `service/QuranDownloadService.kt` — `IntentService`-style core: a dedicated `HandlerThread` + inner `ServiceHandler` serializes download intents; `START_NOT_STICKY`; Metro injection in `onCreate` (`applicationComponent.inject(this)`); holds a `WifiManager.WifiLock`.
- `service/download/DownloadStrategy.kt` — tiny interface (`fileCount(): Int`, `downloadFiles(): Boolean`) with three impls: `SingleFileDownloadStrategy` (translations, DBs, patches), `GaplessDownloadStrategy` (one MP3 per sura plus optional timing database, counted as `suras + db`), `GappedDownloadStrategy` (one file per ayah into `sura/ayah.ext` folders, `+1` for basmallah). Each receives a `downloaderLambda` back into the service, so strategies own layout math but not transport.
- `service/util/QuranDownloadNotifier.java` / `QuranDownloadNotifierImpl.java` — dual-channel reporting: system notifications *and* `LocalBroadcastManager` intents (`ProgressIntent.INTENT_NAME`) carrying `STATE_DOWNLOADING/PROCESSING/SUCCESS/ERROR/ERROR_WILL_RETRY`.
- `common/download/` — the newer seam: `Downloader` interface, sealed `DownloadInfo` events, and `DownloadInfoStreams` (`MutableSharedFlow`, DROP_OLDEST) explicitly commented as the broadcast replacement. The app binds `service/util/DownloadStarter.kt` via `@ContributesBinding(AppScope.class)`; `feature/downloadmanager`'s `SheikhAudioPresenter` calls it, never the service directly.

## 3. Data flow
Callers build plain start intents via `ServiceIntentHelper.getDownloadIntent(...)` (`EXTRA_URL/DESTINATION/DOWNLOAD_KEY/DOWNLOAD_TYPE`). `onStartCommand` immediately calls `notifier.notifyDownloadStarting()` so the service is foreground before any queueing, then routes: verse range or `EXTRA_AUDIO_BATCH` selects gapless vs gapped (from `EXTRA_IS_GAPLESS`), otherwise single-file. `onHandleIntent` short-circuits on cached successes (`successfulZippedDownloads`) and replays `recentlyFailedDownloads` when `EXTRA_REPEAT_LAST_ERROR` is set. Each file flows through `downloadFileWrapper` -> `startDownload` -> `downloadUrl`. Every notifier call stores `lastSentIntent`, which `ACTION_RECONNECT` rebroadcasts so a UI returning to the foreground resyncs without polling (`QuranDataActivity.onResume` sends reconnect after a 100 ms `Single.timer`). Cancellation flips a `@Volatile isDownloadCanceled` flag checked between network reads; `ACTION_CANCEL_DOWNLOADS` additionally clears the handler queue.

## 4. Storage & network
Transport is raw OkHttp streaming to `<destination>/<filename>.part`, flushed every 8 KB chunk; on completion the partial is renamed onto the final name, giving crash-safe resume via an HTTP `Range: bytes=<len>-` header rebuilt from the existing `.part` (`downloadUrl`). Zips are extracted in-place by `ZipUtils.unzipFile` (the service implements `ZipListener`, forwarding extraction progress as `notifyDownloadProcessing`) and the archive deleted. Retry policy lives in `downloadFileWrapper`: up to `RETRY_COUNT = 3` attempts, second attempt onwards swaps in `urlUtil.fallbackUrl(url)` and sleeps `WAIT_TIME = 15 s`; success on a fallback permanently promotes it via the static `fallbackByDefault`; `ERROR_INVALID_DOWNLOAD` earns exactly one extra attempt; disk-space and permissions abort instantly as fatal. Space is pre-checked with `StatFs` — notably against `Environment.getExternalStorageDirectory()`, with a code-commented TODO admitting it may be the wrong volume. Fatal errors persist to prefs via `quranSettings.setLastDownloadError`.

## 5. Why it is built this way ON THIS PLATFORM
The payload profile dictates everything: mushaf pages are pre-rendered PNGs bucketed per screen width (tens of MB zipped), and a gapless qari is 114 full-surah MP3s plus a SQLite timing DB — far too big to bundle, too slow to fetch casually. A foreground `Service` keeps multi-hundred-MB transfers alive across activity death and satisfies Android's foreground-service expectations for long work with visible progress. Serializing requests on one `HandlerThread` avoids interleaved writes into shared directories and makes "cancel everything" trivial. The strategy pattern cleanly encodes the domain difference between gapless (surah-granular, needs its DB) and gapped (ayah-granular, needs basmallah deduplication across sura boundaries). `START_NOT_STICKY` plus explicit `.part` resume means process death degrades gracefully instead of replaying stale intents. Wi-Fi is *not* enforced here — a discrepancy with how this feature is often described: the service only checks `QuranUtils.haveInternet` and holds a WifiLock for radio performance; metered-network decisions happen upstream (e.g. `PagerActivity` checks `QuranUtils.isOnWifiNetwork`, WorkManager workers use `NetworkType.CONNECTED`).

## 6. Edge cases & offline behavior
- Already-downloaded files short-circuit (`file.exists()` checks in every strategy; size-match check inside `downloadUrl` skips redundant re-downloads).
- HTTP 416 (range past EOF) deletes the stale `.part` and restarts recursively.
- Zip double-counting: `isSpaceAvailable(size + downloadedAmount + size)` reserves room for both archive and extracted contents.
- Repeated identical zip requests are deduped in-memory per service lifetime; failed requests remember their error intent for exact replay.
- Offline: immediate `ERROR_NETWORK` before any bytes move; the `.part` survives so a later attempt resumes rather than restarts.
- `currentOperations` AtomicInteger ensures the service stops itself only after the last queued job drains; UI-side, receivers unregister in `onPause` while the notification remains the source of truth.
