# Mushaf variants and page type selection
> How **Quran for Android (github.com/quran/quran_android)** implements this feature. Sources read from a shallow clone @ main (2026-08-23); repo-relative paths cited throughout.

## 1. What the user sees
A "Page Type" row under Settings > Reading opens `PageSelectActivity`, a full-screen horizontal pager of cards — one per installed mushaf rendering — each with a preview snippet image, title, and description. Tapping a card switches the whole app to that mushaf and bounces the user back through `QuranDataActivity` so first-run/missing-image checks re-run for the new page pack. In the open-source build the map of providers contains only "madani", and `QuranSettingsFragment` removes the Page Type row entirely when fewer than two providers exist (`if (pageTypes.size < 2 ...) removePreference(pageChangePref)`) — the picker only materializes when extra page types are compiled in.

## 2. Architecture & key files
- `pages/madani/src/main/java/com/quran/data/page/provider/QuranDataModule.kt` — Metro `@BindingContainer` contributing `@IntoMap @StringKey("madani") provideMadaniPageSet(): PageProvider`, plus `@Named(FALLBACK_PAGE_TYPE) = "madani"`, an empty `Set<ImageDrawHelper>`, `IdentityAyahMapper`, and no-op data/preference upgrades.
- `app/.../ui/fragment/QuranSettingsFragment.kt` (:34) injects `pageTypes: Map<String, PageProvider>`; `onPreferenceTreeClick` routes `Constants.PREF_PAGE_TYPE` to `PageSelectActivity`.
- `app/.../pageselect/PageSelectActivity.kt` + `PageSelectPresenter.kt` — ViewPager UI and an RxJava presenter that builds `List<PageTypeItem>` from the injected map.
- `common/data/src/main/java/com/quran/data/dao/Settings.kt` — `suspend fun setPageType(pageType: String)`; consumers read `quranSettings.pageType`.
- `feature/linebyline/...` (`QuranLineByLineWrapperView.kt`, `QuranLineByLineFragment.kt`, `presenter/QuranLineByLinePresenter.kt`) with renderers in `common/linebyline/ui/src/main/java/com/quran/mobile/linebyline/ui/renderer/composable/` — an alternate, Compose-drawn page implementation.
- Warsh support libraries exist at `pages/data/warsh/.../WarshDataSource.kt` (extends `MadaniDataSource`) and `pages/common/warsh/.../WarshPageSizeCalculator.kt`.

## 3. Data flow
The graph aggregates every module's `@IntoMap @StringKey(...) PageProvider` contribution into one `Map<String, PageProvider>` available app-wide. `PageSelectPresenter.generateData()` iterates it, downloading a preview PNG per key from `https://quran.app/data/pagetypes/snips/<key>.png` into internal storage `pagetypes/snips/` (with a `.nomedia` sentinel) and retrying once on failure before giving up silently. On selection, `PageSelectActivity.onPageTypeSelected` compares against the current type, persists the new value, then launches `QuranDataActivity` with `FLAG_ACTIVITY_CLEAR_TASK | FLAG_ACTIVITY_NEW_TASK` — a deliberate cold restart because every downstream consumer (`TabletFragment.onCreate` → `providePageViewFactory(pageType)`, `MadaniPageProvider`'s width-bucket URLs, ayah-coordinate DB suffixes) is derived from the setting. A code comment records that bookmarks need no page-number migration since they are backed by mobile-sync ayah records.

## 4. Storage & network
Each mushaf is a separate downloaded asset pack: images bucketed by device width plus per-width SQLite ayah-coordinate databases, fetched by `service/QuranDownloadService`. The provider abstraction (`com.quran.data.source.PageProvider`) supplies URLs/page counts/width parameters, while `AyahMapper` translations (identity for Madani) reconcile ayah ranges between numbering schemes. Preview snippets are the only page-type-specific network traffic in the picker itself. Note a discrepancy with the common description of this feature: at main there are **no qaloon/naskh product flavors** — `app/build.gradle.kts` declares a single `productFlavors { create("madani") }` with no flavor dimension — and nothing in the OSS repo binds `@StringKey("warsh")`; the warsh modules ship as reusable libraries whose binding container lives outside this repository.

## 5. Why it is built this way ON THIS PLATFORM
Because pages are pre-rendered bitmaps rather than flowing text, changing mushafs means swapping an entire binary corpus, not a font — so the variant choice is modeled as a pluggable *provider* keyed by string, resolved through DI multibindings instead of hard dependencies. That lets closed or experimental packs (warsh, qaloon-style layouts, line-by-line) be added by shipping one extra `@BindingContainer` without touching app code, and explains why the settings row hides itself when only one provider exists. Line-by-line is the proof of the seam: `TabletFragment` asks `pageViewFactory?.providePage(page, pageMode)` first and falls back to its own image fragments when null, so a Compose-rendered page can occupy the same pager slot while still receiving ayah-selection events.

## 6. Edge cases & offline behavior
Preview thumbnails degrade gracefully offline (cached file shown, else card appears without image). Selecting the already-active type just finishes the activity. `QuranLineByLineWrapperView` tracks `didRequestFallback` and throws/handles `MissingLineByLineImagesException` (`model/MissingLineByLineImagesException.kt`) when its pre-rendered line images aren't downloaded, falling back to the standard image page rather than showing a blank screen. Because the task-clearing relaunch re-enters `QuranDataActivity`, missing images for the newly chosen pack trigger the normal download prompt; if the user cancels, the app stays on the new page type without local images and retries via the existing download-error overlay.
