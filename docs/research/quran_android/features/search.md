# Full-text Quran & translation search
> How **Quran for Android (github.com/quran/quran_android)** implements this feature. Sources read from a shallow clone @ main (2026-08-23); repo-relative paths cited throughout.

## 1. What the user sees

**Entry points** (all funnel into `app/src/main/java/com/quran/labs/androidquran/SearchActivity.kt`):
- **Toolbar SearchView in every major screen**: `QuranActivity.onCreateOptionsMenu` inflates `res/menu/home_menu.xml` (item `R.id.search`, `androidx.appcompat.widget.SearchView` action view), and `ui/PagerActivity.kt` (`onCreateOptionsMenu`, inflates `res/menu/quran_menu.xml`) does the same. Both call `SearchManager.getSearchableInfo(ComponentName(this, SearchActivity::class.java))`, so typing + submit fires `Intent.ACTION_SEARCH` at `SearchActivity`. The reader's search item lives in `PagerActivity` even though it is defined in `quran_menu.xml`.
- **Home-screen widget**: `widget/SearchWidget.kt` wires a button via `PendingIntent.getActivity(context, 0, Intent(context, SearchActivity::class.java), FLAG_IMMUTABLE)` on `R.layout.search_widget`.
- **System/global search (Quick Search Box)**: `AndroidManifest.xml` marks `.SearchActivity` with `<meta-data android:name="android.app.searchable" android:resource="@xml/searchable"/>`, plus an app-wide `<meta-data android:name="android.app.default_searchable" android:value=".SearchActivity"/>`; long-press Home typing "quran" surfaces verse suggestions from the ContentProvider.
- **ShortcutsActivity / QuranForwarderActivity** deep links resolve to pages, not search; search is only reached through the above paths.

**Interactions inside `SearchActivity`**:
- Toolbar contains its own `SearchView` (`res/menu/search_menu.xml`) bound to the same searchable info; if launched with no action the action view is auto-expanded so the keyboard is up immediately (`onCreateOptionsMenu`: `searchItem.expandActionView()` when `intent.action == null`); after a submitted search it calls `clearFocus()`.
- Results render in a `ListView` (`R.id.results_list`) via inner class `ResultAdapter : CursorAdapter`, inflating `res/layout/search_result.xml`. Each row shows the verse text with the match highlighted (`Html.fromHtml(text)` — the highlight is a `<font color="@color/translation_highlight">…</font>` span injected by the query itself, see section 3) and metadata line `found_in_sura` = "Found in Surah (%1$d) %2$s: %3$d (page %4$d)".
- A header `TextView` (`R.id.search_area`) shows quantity-aware "One result for \"x\"" / "%2$d results for \"%1$s\"" from `<plurals name="search_results">`, or `no_results` ("No results found for \"%s\"").
- **Missing-data prompts**: a second `TextView` (`R.id.search_warning`, text `no_arabic_search_available`) and a `Button` (`btnGetTranslations`). The same button has two modes set in `onLoadFinished`: label `get_arabic_search_db` ("Get Arabic Search Database") when the query was Arabic-script but the Arabic DB is absent, or `get_translations` when there are no downloaded translations at all. Tapping it either starts the Arabic DB download in-place or opens `TranslationManagerActivity`.
- Tapping a result opens the reader at that ayah (`jumpToResult`): straight into `PagerActivity` with extras `page`, `EXTRA_HIGHLIGHT_SURA`, `EXTRA_HIGHLIGHT_AYAH`, and `EXTRA_JUMP_TO_TRANSLATION` when appropriate; otherwise via `QuranDataActivity.openPageIntent(...)` when the reader isn't ready yet (`canOpenReaderDirectly()` checks `quranSettings.haveMigratedLegacyBookmarksToMobileSync()` and `ReaderReadinessTracker.isReady(pageType)`).
- Arabic queries open the result on the **mushaf image** (no translation jump); Latin/translated results open in **translation view** — decided per-result in `onLoadFinished` (`jumpToTranslation = !containsArabic || showArabicWarning`) and per-suggestion in `handleIntent`'s ACTION_VIEW branch.

**System search suggestions**: `res/xml/searchable.xml` sets `android:includeInGlobalSearch="true"`, `searchSuggestAuthority="@string/authority"` (generated per-variant as `$applicationId.data.QuranDataProvider` in `app/build.gradle.kts` `androidComponents.onVariants`), `searchSettingsDescription="@string/quranSearchType"` ("Verses of the Quran"), and hint "Search the Quran".

## 2. Architecture & key files

- `app/src/main/java/com/quran/labs/androidquran/SearchActivity.kt` -> legacy View/MVP-era screen (plain `AppCompatActivity`, no presenter): owns the `LoaderManager.LoaderCallbacks<Cursor?>` plumbing, download-receiver wiring, and result navigation. Injected deps: `QuranInfo`, `QuranDisplayData`, `QuranFileUtils`, `QuranSettings`, `ReaderReadinessTracker` (Metro field injection via `applicationComponent.inject(this)`).
- `app/src/main/java/com/quran/labs/androidquran/data/QuranDataProvider.kt` -> the read-only `ContentProvider` implementing the Android SearchManager contract. Two URI routes via `UriMatcher`: `content://$AUTHORITY/quran/search` (`SEARCH_VERSES`) and `SearchManager.SUGGEST_URI_PATH_QUERY` (`SEARCH_SUGGEST`); `insert/update/delete` throw `UnsupportedOperationException`. Authority string is flavor-generated (`BuildConfig.APPLICATION_ID + ".data.QuranDataProvider"`). Declared `android:exported="false"` in the manifest.
- `common/search/src/main/java/com/quran/common/search/` -> the reusable query-building seam:
  - `Searcher.kt` — interface with `getQuery(withSnippets, hasFTS, table, columns, searchColumn)`, `getLimit(withSnippets)`, `processSearchText(searchText, hasFTS)`, `runQuery(...)`.
  - `DefaultSearcher.kt` — SQL for FTS `MATCH` vs `LIKE`, `snippet()` generation, prefix wildcarding (`query*` vs `%query%`).
  - `ArabicSearcher.kt` — decorates `DefaultSearcher`; wildcard-normalizes the query, then re-filters rows in Kotlin with a diacritic/hamza-tolerant regex and builds its own highlighted snippets.
  - `arabic/ArabicCharacterHelper.kt` — hand-built lookup table mapping each hamza/ta-marbuta/ya variant to a character class for regex generation (e.g. `ا -> [آأإاى]`); explicitly noted as helping "rewayat Warsh".
  - `SearchTextUtil.kt` — `asSearchableString(string, isRtl)` (strips tashkeel, normalizes alif/waw-with-hamza for RTL; NFKD + lowercase for LTR) and `isRtl(s)` via `Character.getDirectionality`. Used by search-adjacent UI too (`ui/fragment/JumpFragment.kt`, `ui/translation/TranslationAdapter.kt`, `feature/downloadmanager SheikhAudioDownloadsActivity.kt`).
- `app/src/main/java/com/quran/labs/androidquran/database/DatabaseHandler.kt` -> opens one downloaded SQLite file (`SQLiteDatabase.openDatabase(path, null, NO_LOCALIZED_COLLATORS, DefaultDatabaseErrorHandler())`), cached in a static `databaseMap` keyed by filename with `clearDatabaseHandlerIfExists(name)` invalidation. Its `search(query, table, withSnippets, isArabicDatabase)` picks `DefaultSearcher` vs `ArabicSearcher`, reads `schema_version` from the DB's `properties` table to decide FTS vs LIKE (`useFullTextIndex = schemaVersion > 1 && !isArabicDatabase`), strips unbalanced quotes, and swallows exceptions returning `null`.
- `app/src/main/java/com/quran/labs/androidquran/util/QuranFileUtils.kt` -> `hasArabicSearchDatabase()` (existence check plus copy-back from the flavor-specific ayahinfo directory into the shared databases directory) and `arabicSearchDatabaseUrl` (= `databaseBaseUrl + QURAN_ARABIC_DATABASE + ".zip"`).
- `app/src/main/java/com/quran/labs/androidquran/service/QuranDownloadService.kt` -> foreground service that fetches and unzips the Arabic search DB (`DOWNLOAD_TYPE_ARABIC_SEARCH_DB = 4`).
- `app/src/main/java/com/quran/labs/androidquran/model/translation/ArabicDatabaseUtils.kt` and `model/translation/TranslationModelImpl.kt` -> adjacent consumers of the same `DatabaseHandler` (ayah text hydration for bookmarks/sharing; reading-mode verse fetches), showing search shares its storage layer with the rest of the reader.
- `common/translation/src/main/sqldelight/com/quran/mobile/translation/translations.sq` + `data/TranslationsDataSource.kt` + `app/.../database/TranslationsDBAdapterImpl.kt` -> catalog of downloaded translations consulted by the provider (`getTranslations(): Flow<List<LocalTranslation>>`, filtered by `quranFileUtils.hasTranslation(filename)`).

**Seams**: `Searcher` (strategy interface over SQL dialects), the `ContentProvider` URI contract (system-facing protocol), `LocalTranslation.languageCode` filtering policy, and the flavor-level `QuranFileConstants.ARABIC_DATABASE` constant (`app/src/madani|warsh|qaloon|naskh/java/.../QuranFileConstants.kt`; madani delegates to `pages/common/madani .../MadaniConstants.ARABIC_DATABASE = "quran.ar.uthmani.v2.db"`, warsh uses `"quran.ar.warsh.db"`, qaloon `"quran.ar.qaloon.db"`).

## 3. Data flow

**A. Query typed in the toolbar -> results list**
1. `SearchView` submits → framework fires `ACTION_SEARCH` with `SearchManager.QUERY` → `SearchActivity.onNewIntent`/`handleIntent` → `showResults(query)`.
2. `showResults` packs the query into a Bundle and restarts loader 0: `LoaderManager.restartLoader(0, args, this)`.
3. `onCreateLoader` builds `CursorLoader(this, QuranDataProvider.SEARCH_URI, null, null, arrayOf(query), null)` — the query travels as `selectionArgs[0]` (the searchable.xml `searchSuggestSelection="word MATCH ?"` placeholder slot); all SQLite work happens off-thread on the loader.
4. `QuranDataProvider.query()` lazily Metro-injects itself on first call (`applicationComponent.inject(this)` guarded by `didInject`), matches `SEARCH_VERSES`, and calls `search(selectionArgs[0])`.
5. `availableTranslations()` does `runBlocking { translationsDBAdapter.getTranslations().first() }` — blocking is acceptable because the provider already runs on the loader thread; it returns only translations whose file exists on disk.
6. Routing logic in `search(query, ...)`: `queryIsArabic = QuranUtils.doesStringContainArabic(query)` (codepoint range check in `util/QuranUtils.java`); `haveArabic = queryIsArabic && quranFileUtils.hasArabicSearchDatabase()`. Loop index starts at `-1` when `haveArabic` (i.e. search the Arabic mushaf DB first), otherwise at `0`. For each translation DB it skips when `queryIsArabic || languageCode == "ar"` — Arabic-script queries never hit translation DBs, and Arabic-language tafaseer are always excluded ("searching Arabic tafaseer causes a lot of noise"). Each candidate goes to `DatabaseHandler.search(query, wantSnippets=true, isArabicDatabase = name == QURAN_ARABIC_DATABASE)`; **the first DB returning >0 rows wins** and its cursor is returned.
7. `DatabaseHandler.search` builds SQL through the `Searcher`: for FTS DBs `select rowid as _id, sura, ayah, snippet(verses, '<font color=...>', '</font>', '<b>...</b>', -1, 64) FROM verses WHERE text MATCH ? <limit>`; otherwise the same shape with `LIKE ?` and `text` selected instead of `snippet()`. `processSearchText` appends `*` (FTS prefix match) or wraps in `%...%`.
8. Back in the activity, `onLoadFinished` computes `containsArabic`/`showArabicWarning`/`jumpToTranslation`, swaps the cursor into `ResultAdapter`, and binds rows (`Html.fromHtml` renders the injected font tags).

**B. System suggestion path**
1. Global/quick-box search hits `SEARCH_SUGGEST` → `getSuggestions(query)`.
2. Returns `null` for queries shorter than 3 chars, or when there is nothing searchable (no translations and either non-Arabic query or missing Arabic DB).
3. It searches each database with `wantSnippets=false` (`LIMIT 10` for DefaultSearcher; none for ArabicSearcher, which short-circuits at 6 accepted records), takes the first DB with hits, and copies **at most 5 rows** into a `MatrixCursor` with columns `_ID`, `SUGGEST_COLUMN_TEXT_1` (verse text), `SUGGEST_COLUMN_TEXT_2` ("Found in Surah … page N", computed with `quranInfo.getPageFromSuraAyah`), `SUGGEST_COLUMN_INTENT_DATA_ID` (the ayah rowid).
4. If the query is Arabic or more than 5 rows existed, it appends a synthetic row `id = -1` labelled `search_full_results` / `search_entire_mushaf`.

**C. Suggestion tapped -> reader**
1. System fires `ACTION_VIEW` on SearchActivity with `intent.data.lastPathSegment` = ayah id and `SearchManager.USER_QUERY` carried along (with an ICS-era workaround reading a `SpannableString` out of extras, `http://code.google.com/p/android/issues/detail?id=22978`).
2. `id == -1` → fall back to `showResults(query)` (full results). Otherwise validate `id in 1..quranInfo.getNumberOfAyahsInQuran()` and decode via `quranInfo.getSuraAyahFromAyahId(id)`.
3. Because `hasArabicSearchDatabase()` may copy files, the decision runs in a coroutine: `viewIntentJob = lifecycleScope.launch { val openAsArabic = isArabicQuery && withContext(Dispatchers.IO) { quranFileUtils.hasArabicSearchDatabase() }; jumpToResult(sura, ayah, jumpToTranslation = !openAsArabic); finish() }`. `cancelPendingViewIntentNavigation()` (called from `onStop` and every new intent) makes this single-flight so a stale suggestion can't navigate after a newer one.
4. `jumpToResult` computes the madani page and launches `PagerActivity` (or routes through `QuranDataActivity.openPageIntent` while downloads/bookmark migration are pending). `PagerActivity.onNewIntent` consumes `EXTRA_HIGHLIGHT_SURA/AYAH` via `readingEventPresenterBridge.setSelection(...)` and `EXTRA_JUMP_TO_TRANSLATION` to switch pager mode.

**D. Arabic search DB acquisition**
1. UI trigger: `btnGetTranslations` click → `downloadArabicSearchDb()` registers a `DefaultDownloadReceiver` for `QuranDownloadNotifier.ProgressIntent.INTENT_NAME` scoped to `DOWNLOAD_TYPE_ARABIC_SEARCH_DB`, then `startService(getDownloadIntent(...))` on `QuranDownloadService` with url `arabicSearchDatabaseUrl`, destination `getQuranDatabaseDirectory().absolutePath`, and `EXTRA_OUTPUT_FILE_NAME = QURAN_ARABIC_DATABASE + ".zip"`.
2. Silent trigger: `PagerActivity.downloadRequiredFiles()` also kicks the same download (bundled with the ayah-position/highlighting DB, notification title `highlighting_database` or `search_data`) whenever `!quranFileUtils.hasArabicSearchDatabase()` — i.e. the reader self-heals the dependency.
3. Service side (`downloadFileWrapper`/`startDownload`): WifiLock around transfer, retry loop with `urlUtil.fallbackUrl(url)` on retries, corruption gets exactly one extra attempt (`previouslyCorrupted` decrements `i`), critical errors (disk space, permissions) abort; on success any `*.zip` output is extracted via `ZipUtils.unzipFile(actualFile, File(path), ...)` and the archive deleted — leaving `databases/quran.ar.uthmani.v2.db`.
4. Progress/failure returns to `SearchActivity.handleDownloadSuccess/handleDownloadFailure(errId)` via the local broadcast receiver; success hides the warning and re-runs `handleIntent(intent)` to execute the original query against the freshly installed DB.

## 4. Storage & network

- **Per-translation SQLite files** under `QuranFileUtils.getQuranDatabaseDirectory()` (e.g. `<base>/databases/<filename>.db`). Expected schema (from `DatabaseHandler` constants and queries): `verses(rowid _id, sura, ayah, text[, extraData])`, plus a `properties(property, value)` table whose `schema_version` and `text_version` rows drive behavior. When `schema_version > 1` the verses table is an **SQLite FTS index**: queries switch from `LIKE '%q%'` to `MATCH 'q*'` and use `snippet(verses, startTag, endTag, ellipses, -1, 64)`. Older DBs silently degrade to full-table LIKE scans. The Arabic DB additionally carries `arabic_text` and `share_text` tables (used for display/share text, e.g. `ArabicDatabaseUtils.getVersesByIds` queries `ARABIC_SHARE_TABLE`), and basmallah handling constants live in `QuranFileConstants`/`ArabicDatabaseUtils.AR_BASMALLAH`.
- **Arabic search database**: one downloadable file named by flavor constant — `quran.ar.uthmani.v2.db` for madani/Hafs, `quran.ar.warsh.db`, `quran.ar.qaloon.db` for the other page types. Endpoint pattern: `https://android.quran.com/data/databases/<name>.zip` (madani `MadaniPageProvider.getDatabasesBaseUrl()` with `baseUrl = "https://android.quran.com/data"`; other flavors substitute their own provider base). Delivered as a zip through `QuranDownloadService`, which supports resume-style retries, fallback URLs, MD5-less corruption detection via re-download, and zip extraction.
- **Flavor quirk**: for non-Hafs flavors the Arabic DB historically shipped inside the ayahinfo directory; `hasArabicSearchDatabase()` copies it back into the shared `databases/` dir so it can be reused across flavors (`QuranFileUtils.hasArabicSearchDatabase`, lines ~537-564).
- **Translation catalog metadata** is separate SQLDelight storage (`common/translation .../translations.sq`, table `translations(id, name, translator, translatorForeign, filename, url, languageCode, version, minimumRequiredVersion, userDisplayOrder)`), read by `TranslationsDataSource.translations()` as a Flow and exposed synchronously to the provider through `runBlocking`. Only rows whose file exists pass `TranslationsDBAdapterImpl.getTranslations()`.
- **Caches & invalidation**: `DatabaseHandler.databaseMap` keeps open `SQLiteDatabase` handles keyed by filename; `clearDatabaseHandlerIfExists(fileName)` closes them when `TranslationManagerActivity` replaces/deletes a translation. No HTTP caching layer is involved — search is purely local; the only network is the one-shot DB download.
- **No preferences**: search stores no settings of its own; the only state is the presence/absence of database files on disk (checked with `File.exists()`), keeping "what's searchable" derivable at runtime rather than tracked.

## 5. Why it is built this way ON THIS PLATFORM

- **The ContentProvider + SearchManager contract is the platform's native extension point.** Implementing search as a provider with `searchable.xml` buys three things for free: in-app `SearchView` binding, Quick Search Box/global suggestions (`includeInGlobalSearch`), and intent-based result routing (`ACTION_VIEW` with `_id` in the data URI) — all standard OS machinery that works from the launcher, Google app, and widget without custom IPC. A platform without system-wide search providers would need its own suggestion service and share the results some other way.
- **Everything is offline-first because the corpus must be.** Page rendering is pre-baked mushaf images (per-width buckets), so Arabic script-as-text is not otherwise present in the app; searching the Quranic text therefore *requires* shipping/downloading a dedicated plain-text Arabic database (`quran.ar.*.db`). There is no server-side search API to call — queries run against local SQLite, so search works in airplane mode once assets exist, and the UX is built around gracefully acquiring them (warning banner + download button, silent prefetch from `PagerActivity.downloadRequiredFiles`).
- **Foreground-service download with notifications** exists because Android background-execution limits make a bare `AsyncTask` download unreliable across process death, and because users expect progress/cancel affordances for multi-MB archives. Reusing the single `QuranDownloadService` (which also serves pages/audio/ayahinfo) means search inherits retry, fallback-URL, Wi-Fi lock, and zip-extraction logic instead of duplicating it; the local-broadcast `DefaultDownloadReceiver` pattern lets the activity observe progress without holding the service.
- **LoaderManager/CursorLoader + CursorAdapter** is the classic lifecycle-safe way to keep a potentially slow multi-database query off the main thread while surviving rotation, and it composes naturally with the provider's Cursor contract. The newer Compose features in this repo use StateFlow/coroutines, but search predates them and the provider's synchronous Cursor API pins it to the older idiom.
- **FTS-vs-LIKE dualism is a data-versioning compromise, not a preference.** Translations are user-downloaded artifacts of varying vintage; the code cannot rebuild indexes locally (no writable guarantee, size cost), so `properties.schema_version > 1` gates `MATCH/snippet()` and old files keep working via LIKE. Similarly, Arabic search deliberately avoids relying on SQLite's tokenizer (historically poor for Arabic morphology): `ArabicSearcher` widens the SQL match with `_` wildcards and then applies a Kotlin regex with explicit hamza/ta-marbuta/ya equivalence classes (`ArabicCharacterHelper`), giving diacritic- and orthography-insensitive matching that also tolerates Warsh spelling differences — something an FTS tokenizer config alone would not deliver.
- **Provider-side `MatrixCursor` synthesis** exists because the OS expects a flat suggestion Cursor; joining "first matching DB, top 5 rows, plus a Full Results sentinel row (id=-1)" inside the provider keeps every consumer (global search box included) consistent without extra round-trips.
- **Metro DI in a ContentProvider requires manual injection** — providers are constructed by the OS, not by the graph, hence the `if (!didInject) applicationComponent.inject(this)` dance in `query()` rather than constructor injection like activities get.
- **Memory budget**: opening every translation DB eagerly would be wasteful, so `DatabaseHandler` instances are created lazily per filename and cached in a static map; the provider stops at the first database with hits for full results, and caps suggestions at 5 rows per query to bound cursor sizes sent to the system.

## 6. Edge cases & offline behavior

- **Short queries**: `getSuggestions` returns null below 3 characters; in-app, a null cursor renders `no_results` and, for Latin queries longer than 2 chars, offers the "Get Translations" button (`onLoadFinished`).
- **Nothing installed / fully offline first-run**: with zero translations and no Arabic DB, both provider methods return null; UI nudges toward `TranslationManagerActivity`. After downloading the Arabic DB mid-session, `handleDownloadSuccess` transparently re-runs the pending query.
- **Arabic query without the Arabic pack**: warning text + "Get Arabic Search Database" button; `jumpToTranslation` is forced true so any tafseer-derived match still opens somewhere readable. Conversely an Arabic query *with* the pack opens mushaf pages directly.
- **Corrupt/missing files**: `DatabaseHandler.init` rethrows `SQLiteDatabaseCorruptException` (logged via Timber) and `SQLException` when the file is absent; `search()` catches any exception and returns null so a bad DB degrades to "no results" instead of crashing search. `validDatabase()` guards every query.
- **Query sanitization**: unbalanced double quotes are stripped before query building (`DatabaseHandler.search` counts `"` occurrences and removes them when odd), preventing broken FTS phrase syntax.
- **Interrupted/retried downloads**: `downloadFileWrapper` retries with backoff (`WAIT_TIME` sleep), switches to the fallback URL, gives corrupted archives exactly one more chance, surfaces `ERROR_DISK_SPACE`/`ERROR_PERMISSIONS` as fatal, and reports cancellation; failures leave the previous DB intact since extraction only happens after a complete download and partial files carry a `.partial` extension.
- **Stale-navigation race**: multiple rapid suggestion taps are serialized through `viewIntentJob` replacement + `cancelPendingViewIntentNavigation()` (documented on the field: "Replacing this job prevents an older onNewIntent call from opening after a newer intent"), and cancelled in `onStop` so a backgrounded activity cannot navigate.
- **Ayah-id validation**: ACTION_VIEW ids outside `1..getNumberOfAyahsInQuran()` are dropped, protecting against malformed intents.
- **RTL/locale handling**: `QuranUtils.doesStringContainArabic` sniffs script per query (not device locale); `Html.fromHtml` rendering of highlighted snippets preserves RTL text direction inside `TextView`s; shared helper `SearchTextUtil.isRtl/asSearchableString` normalizes diacritics for the sibling jump-to-ayah dialog (`JumpFragment`) so Arabic input filters consistently there too. Arabic-language tafaseer DBs (`languageCode == "ar"`) are intentionally excluded from search results to avoid noisy duplicates.
- **Upgrade states**: legacy bookmark-migration gating (`haveMigratedLegacyBookmarksToMobileSync`) plus `ReaderReadinessTracker` decide whether tapping a result jumps straight to `PagerActivity` or routes through `QuranDataActivity` until page data is ready; old schema_version-1 translation DBs keep working via the LIKE path, and the flavor-copyback in `hasArabicSearchDatabase()` rescues Arabic DBs installed under old directory layouts.
- **Known limitation acknowledged in-code**: `ArabicSearcher.getLimit` returns `""` with a comment explaining that capping results made matches near the end of the mushaf unreachable, and that suggestions/results will eventually be unified since the underlying query is identical — i.e. Arabic full searches currently scan and filter the whole table client-side.
