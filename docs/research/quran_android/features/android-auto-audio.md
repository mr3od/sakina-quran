# Android Auto audio browsing
> How **Quran for Android (github.com/quran/quran_android)** implements this feature. Sources read from a shallow clone @ main (2026-08-23); repo-relative paths cited throughout.

## 1. What the user sees
On an Android Auto head unit the app appears as a media app with no activity UI at all: a browsable root shown as grid items containing "Recently played" and a Qaris section (`autoquran_qaris_title`), each qari expanding to 114 sura rows with per-sura artwork, track numbers, and the qari as artist; playback runs through the standard Auto transport controls, and voice search matches qari names.

## 2. Architecture & key files
This is a **separate application target**, not a screen in the phone app: `:autoquran` (`autoquran/build.gradle`, `applicationId "com.quran.labs.autoquran"`) has `uses-feature android.hardware.type.automotive required=true` and `appCategory="audio"` (`autoquran/src/main/AndroidManifest.xml`); it depends on the `:feature:autoquran` library, which is *also* compiled into the phone app (`app/build.gradle.kts` L243). The core is `feature/autoquran/src/main/java/com/quran/labs/feature/autoquran/service/QuranBrowsableAudioPlaybackService.kt`, a media3 `MediaLibraryService` with its own `ExoPlayer` and `MediaLibrarySession.Callback` implementing `onGetLibraryRoot/onGetItem/onGetChildren/onAddMediaItems/onSetMediaItems/onSearch/onGetSearchResult`. Tree construction is delegated to `common/BrowsableSurahBuilder.kt`; artwork to `common/QariArtworkContentProvider.kt` + `common/QariArtworkProvider.kt`; recents to `common/RecentQariManager.kt`. The service declares both `androidx.media3.session.MediaLibraryService` and legacy `android.media.browse.MediaBrowserService` intent filters with `foregroundServiceType="mediaPlayback"`.

## 3. Data flow
The tree uses string ids: `"__ROOT__"` -> [`"__RECENT__"` if non-empty, `"__QARI__"`], `"quran_<qariId>"` -> 114 x `"sura_<sura>_<qariId>"`. `BrowsableSurahBuilder.children()` runs on `Dispatchers.IO`, pulling `pageProvider.getQaris()` from the flavor's `PageProvider` (only `isGapless` qaris are listed under `__QARI__`). Selecting a sura hits `onSetMediaItems`, where `expandMediaItem()` expands it into the full 114-item playlist for that qari and positions at the chosen index — so next/previous continues across the mushaf. A `PlayerEventListener` feeds `RecentPlaybackRecorder` (handler-posted delay executor) which calls `RecentQariManager.recordQari(qariId, sura)` after real playback, then `notifyChildrenChanged` for both RECENT and ROOT (child count 2 vs 1) so Auto refreshes live. `onGetLibraryRoot` honors `params.isRecent` and hints `EXTRAS_VALUE_CONTENT_STYLE_GRID_ITEM` for browsables.

## 4. Storage & network
Audio is streamed, not downloaded: `makeSuraMediaItem` builds direct CDN URIs of `qari.url`/`qari.opusUrl + three-digit(sura) + extension`, choosing `MimeTypes.AUDIO_OPUS` vs `AUDIO_MPEG` via `AudioExtensionDecider`. Recents persist as Moshi JSON (max 5 entries) in SharedPreferences file `autoquran_recent`. Artwork is never fetched over the network: `QariArtworkContentProvider` (authority `${applicationId}.autoquran.artwork`, exported with URI grants) hands clients only `content://` URIs in `MediaMetadata`, then renders deterministic PNGs on demand behind a byte-sized `LruCache` and a bounded daemon `ThreadPoolExecutor` with `AbortPolicy`.

## 5. Why it is built this way ON THIS PLATFORM
Automotive requires a media-browser-only entry point — no launcher activity — hence a dedicated app module with its own store listing while sharing the audio/pageProvider code through `:feature:autoquran`. The service owns a fresh ExoPlayer rather than binding the phone app's `AudioService`, keeping queue/repeat semantics simple inside the session. Every callback wraps work in `runCatching` and always completes its `SettableFuture` — the code comments that failing to respond leaves Android Auto on an infinite spinner (L228). Injection failure is logged, not thrown (`Timber.e("Unable to inject ...")`), because a crashed service would remove the app from the head unit entirely.

## 6. Edge cases & offline behavior
The "Recently played" node disappears until something is played (root returns one child when recents are empty); malformed media ids parse to `-1` and yield empty results rather than crashes. Repeat transitions are ignored by the recorder, and playback must actually start before a recent is recorded. Search currently covers only gapless qari names (`// TODO: add sura search`). If streaming is unavailable offline, playback fails inside ExoPlayer with no download fallback — this module deliberately ships zero download logic, unlike the phone app's gapped/gapless strategies.
