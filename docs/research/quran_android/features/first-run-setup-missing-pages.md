# First-run data setup and missing page repair
> How **Quran for Android (github.com/quran/quran_android)** implements this feature. Sources read from a shallow clone @ main (2026-08-23); repo-relative paths cited throughout.

## 1. What the user sees
The launcher activity is `QuranDataActivity` (`app/src/main/AndroidManifest.xml`), a gate before `QuranActivity`. On first launch the user sees an indeterminate "migration" screen (`R.layout.migration_upgrade`, shown unconditionally via `showMigrationDialog()`), then — if page images are absent — a non-cancelable dialog offering to download them (`downloadPrompt` / `downloadTabletPrompt` / `downloadImportantPrompt` strings). Accepting starts the foreground download with its progress notification; refusing still opens the reader in a degraded mode. Failures show a retry/cancel dialog. Returning users normally see nothing but a brief spinner. Deep links (`ACTION_OPEN_PAGE`, shortcut jump actions) are honored by `targetIntent()` after checks pass.

## 2. Architecture & key files
Classic MVP split, per the class KDoc: `QuranDataActivity.kt` owns permissions, dialogs, and download intents; `presenter/data/QuranDataPresenter.kt` owns disk inspection and WorkManager scheduling; `service/QuranDownloadService.kt` performs interactive downloads. Supporting cast:
- `service/util/DefaultDownloadReceiver` registered in `onResume` filtered on `ProgressIntent.INTENT_NAME` for `DOWNLOAD_TYPE_PAGES`, with the activity itself as `SimpleDownloadListener`.
- `worker/PartialPageCheckingWorker.kt` (finds and deletes truncated images) chained ahead of `worker/MissingPageDownloadWorker.kt` (silent repair), both `CoroutineWorker`s created through Metro-injected `WorkerTaskFactory` impls nested in each worker.
- `common/upgrade`'s `LocalDataUpgrade` / `PreferencesUpgrade` run inside the presenter's check pipeline.

## 3. Data flow
`onCreate` injects and runs preference-schema upgrades; first `onResume` calls `checkPermissions()`: a custom storage location that is neither `filesDir` nor under `getExternalFilesDirs` requires legacy write permission — without it the app silently downgrades `appCustomLocation` to internal storage; on Android 11+ it instead migrates files internally via `quranFileUtils.moveAppFiles`. Then the presenter's Rx chain runs on `Schedulers.io`: `migrateLegacyBookmarks()` -> `supportLegacyPages()` -> `actuallyCheckPages()` -> `localDataUpgrade.processData/processPatch` -> `checkPatchStatus()`. `actuallyCheckPages` verifies all `numberOfPages` PNGs exist for `QuranScreenInfo.widthParam`, plus `tabletWidthParam` when in dual-page mode. Results are cached only when complete (`havePages() && patchParam == null`) because a cached "incomplete" could go stale while the user is away. Outcomes: missing pages + prior error pref -> error dialog; `shouldFetchPages` flag set -> auto-resume download; otherwise `promptForDownload()`. Patches (pages present but `.version` older than `PageProvider.getImageVersion()`) reuse the same dialog. `handleDownloadSuccess` marks partial-checking done for that page type and cancels the pending worker chain.

## 4. Storage & network
Interactive path: `actuallyDownloadQuranImages` picks one zip URL from `QuranFileUtils` — portrait-only, landscape-only, or a combined `widthParam+tabletWidthParam` pack — or a `getPatchFileUrl(patchParam, imagesVersion)` delta patch, and hands it to the download service into the images base directory. Silent repair path: `MissingPageDownloadWorker.doWork` scans pages 1..N for both widths against `QuranFileUtils.getPageFileName` (`pageNNN.png`, zero-padded), then downloads each individually through `QuranFileUtils.getImageFromWeb` (`imageBaseUrl + "width" + widthParam + "/" + filename`) using parallel Flow map over `Dispatchers.IO`. A weekly `AudioUpdateWorker` periodic task is also enqueued from `scheduleAudioUpdater()` here.

## 5. Why it is built this way ON THIS PLATFORM
Because rendering mushaf text was rejected in favor of pre-rendered page images bucketed by device width, the APK cannot ship usable pages for every device — so a first-run download gate is structurally unavoidable, and it must be robust enough that nobody is ever locked out of the Quran. Hence three layers of defense: the explicit prompt (interactive, observable, retryable), the silent `MissingPageDownloadWorker` (heals holes left by interrupted zips, cleared caches, or extraction bugs without nagging users), and `PartialPageCheckingWorker` (a half-written PNG renders as garbage, so size-anomaly detection deletes it for re-download rather than trusting file-existence alone). WorkManager constraints survive process death for background repair, while the foreground service gives progress UX for the big initial fetch. The `MISSING_PAGE_LIMIT = 50` guard exists so a systematically wrong directory (wrong width bucket, wrong page type) triggers nothing rather than thousands of one-off requests.

## 6. Edge cases & offline behavior
- Repair workers are enqueued once per page type (`didCheckPartialImages` pref) as unique work keyed `"${WorkerConstants.CLEANUP_PREFIX}$pageType"` with `KEEP`; they are skipped entirely for `*lines` page types.
- `MissingPageDownloadWorker` always returns `Result.success()` even when downloads fail — failures are logged, never surfaced or retried by WorkManager.
- `PartialPageCheckingWorker` bails if the stored page type changed since enqueue, retries once on deletion failure, tolerates over-limit partial sets.
- POST_NOTIFICATIONS denial (Android 13+) does not block downloading; `downloadQuranImages` proceeds anyway.
- The 100 ms-delayed `ACTION_RECONNECT` start-service call is wrapped in try/catch since some devices reject it as background start — progress simply resumes via normal notifications.
- No storage mounted -> `onStorageNotAvailable()` skips straight to the reader; declining a *patch* keeps the reader fully usable (`runListViewWithoutPages` only falls back when `PageContentType != Image`, switching `pageType` to the provider's fallback).
