# Audio recitation playback
> How **Quran for Android (github.com/quran/quran_android)** implements this feature. Sources read from a shallow clone @ main (2026-08-23); repo-relative paths cited throughout.

## 1. What the user sees

**Entry points into playback**
- Play button on the reader's action bar: `PagerActivity.onPlayPressed()` (`app/src/main/java/com/quran/labs/androidquran/ui/PagerActivity.kt`) starts from the first ayah of the current page; if several suras begin on that page it shows a multiple-choice prompt (`promptForMultipleChoicePlay`) instead of guessing.
- Long-press an ayah → ayah selection mode → the sliding bottom panel's audio tab (`AyahPlaybackFragment`, contributed via `AyahActionFragmentProvider` with `order = SlidingPagerAdapter.AUDIO_PAGE`). The panel (`app/src/main/res/layout/audio_panel.xml`) exposes:
  - start/end sura + ayah spinners (sura names localized, digits rendered via `QuranUtils.getLocalizedNumber`),
  - a "restrict to range" checkbox,
  - two number pickers — verse repeat and range repeat — each 1..25 plus an infinity entry (`MAX_REPEATS = 25`, mapped to `-1` internally),
  - a playback-speed picker over `SPEEDS = [0.5, 0.75, 1.0, 1.25, 1.5]` (`AyahPlaybackFragment.kt`), hidden entirely below Android M (`Build.VERSION.SDK_INT < M`),
  - an Apply button whose label flips between `play_apply` ("Play") when audio is already running and `play_apply_and_play` when starting fresh.
- Tapping the qari name on the stopped audio bar opens `QariListWrapper` (`feature/qarilist`) — a Compose `BottomSheetScaffold` with a search field, listing reciters grouped by `QariListPresenter.qariList()` into sections: *ready to play* (the requested range is already on disk), *qaris with downloads*, *gapless*, *gapped*. Selecting one calls `CurrentQariManager.setCurrentQari(id)`, which persists the `"defaultQari"` SharedPreferences key.
- Settings → "Audio manager" (`QuranSettingsFragment` starts `AudioManagerActivity`, `feature/downloadmanager`) lists downloaded shuyookh; tapping one opens `SheikhAudioDownloadsActivity` for per-sura download/removal, including the gapless timing database.

**Persistent controls**
- A Compose audio bar is docked under the pager (`AudioBarWrapper`, injected through `PagerActivityComponent.inject(audioBarWrapper)`). Its states (`feature/audiobar/.../state/AudioBarScreen.kt`: `Stopped`, `Loading`, `Playing`, `Paused`, `Downloading`, `Error`, `Prompt`, plus recitation states) render different bars in `ui/`: `StoppedAudioBar` (qari name + play + change-qari), `PlaybackAudioBar` (pause/play, stop, rewind, fast-forward, a `RepeatableButton` showing repeat count, a speed button, settings), `LoadingAudioBar`, `ErrorAudioBar`, `PromptingAudioBar`.
- While playing, a foreground media notification appears (channel `Constants.AUDIO_CHANNEL`) with previous / pause / next actions and `MediaStyle` compact views; when paused it swaps to play + stop actions. It deep-links back to `PagerActivity`. Headset/media buttons route through `MediaButtonReceiver` and the `MediaSessionCompat` callback.
- Playback follows reading: as the verse changes, `PagerActivity.onAudioPlaybackAyahChanged` calls `ensurePage(sura, ayah)` so the ViewPager snaps along with the reciter.
- Word-by-word highlight during gapless recitation is supported (`AudioRequest.wordHighlighting`, word timings surfaced as `currentWord` in `AudioStatus.Playback`).

## 2. Architecture & key files

- `app/src/main/java/com/quran/labs/androidquran/service/AudioService.kt` → the foreground `Service` and only owner of the Media3 `ExoPlayer`. Implements `Player.Listener`; runs all intent handling and position polling on a dedicated `HandlerThread("AyahAudioService")`; owns the `MediaSessionCompat`, both notification builders, and a 128 MB streaming `SimpleCache`. Actions: `ACTION_PLAYBACK/PLAY/PAUSE/SKIP/REWIND/STOP/CONNECT/UPDATE_SETTINGS` carrying an `EXTRA_PLAY_INFO` Parcelable.
- `app/src/main/java/com/quran/labs/androidquran/presenter/audio/service/AudioQueue.kt` → pure "virtual queue": given an `AudioRequest` it decides which sura/ayah plays next or previous while honoring verse repeats (`repeatInfo`), range repeats (`rangeRepeatInfo`), bounds enforcement, and basmallah insertion. Returns file URLs via `getUrl()`.
- `common/audio/src/main/java/com/quran/labs/androidquran/common/audio/model/playback/AudioRequest.kt` → Parcelable command object (start/end `SuraAyah`, `QariItem`, repeat counts, `enforceBounds`, `playbackSpeed`, `shouldStream`, `AudioPathInfo`, `wordHighlighting`). This Parcelable *is* the activity↔service protocol.
- `common/audio/.../model/playback/AudioPathInfo.kt` → `urlFormat` (printf pattern), `localDirectory`, `gaplessDatabase` path, `allowedExtensions`. One object encodes both gapped and gapless shapes.
- `common/audio/.../repository/AudioStatusRepository.kt` → app-scope singleton `MutableStateFlow<AudioStatus>`; the service writes, any UI collects. Decouples UI from intents entirely.
- `common/audio/.../repository/CurrentQariManager.kt`, `util/QariUtil.kt`, `model/QariItem.kt` → selected-qari state (pref-backed flow) and the qari catalog pulled from the flavor's `PageProvider.getQaris()` (`pages/madani/.../MadaniPageProvider.kt` ships exactly 3 qaris: Minshawi and Husary gapless, Basfar gapped).
- `feature/audiobar/src/main/kotlin/com/quran/mobile/feature/audiobar/` → Compose control bar: `presenter/AudioBarPresenter.kt` combines `audioStatusRepository.audioPlaybackFlow`, `currentQariManager.flow()`, download events (`DownloadInfoStreams`) and recitation flows into `AudioBarState`; `presenter/AudioBarEventRepository.kt` is a buffered `SharedFlow<AudioBarEvent>` from UI back up; `ui/*.kt` are the bar composables. Optimistic updates live here (e.g. `SetSpeed`/`SetRepeat` update state before the service confirms).
- `app/src/main/java/com/quran/labs/androidquran/feature/reading/bridge/AudioStatusRepositoryBridge.kt` → glue: maps `AudioBarEvent`s to `AudioBarListener` callbacks implemented by `PagerActivity`, and pushes `AudioStatus.Playback.currentAyah` into the page-snapping callback; also exposes `audioRequest()` used to build updated requests.
- `app/src/main/java/com/quran/labs/androidquran/feature/reading/presenter/AudioPresenter.kt` → pre-play decision engine: builds `AudioPathInfo` (`getLocalAudioPathInfo`), decides stream vs local by `haveAllFiles()`, and returns the download intent needed before playback can proceed (ayah-position DB → gapless timing DB → basmallah-only → missing verse files).
- `app/src/main/java/com/quran/labs/androidquran/ui/fragment/AyahPlaybackFragment.kt` → the range/repeat/speed panel described above.
- `feature/qarilist/` → `QariListWrapper` (Compose bottom sheet), `presenter/QariListPresenter.kt` (sections from `QariDownloadInfoSource.downloadQariInfoFilteringNonDownloadedGappedQaris()`).
- `feature/downloadmanager/` → `AudioManagerActivity`, `SheikhAudioDownloadsActivity`, `presenter/SheikhAudioPresenter.kt` (sura selection, batch download via the `Downloader` seam, deletion + cache invalidation).
- `app/src/main/java/com/quran/labs/androidquran/service/QuranDownloadService.kt` + `service/download/{DownloadStrategy,GappedDownloadStrategy,GaplessDownloadStrategy,SingleFileDownloadStrategy}.kt` → strategy-pattern file downloads (per-verse files vs per-sura files + timing zip) with progress-notification denominators from `fileCount()`.
- `app/src/main/java/com/quran/labs/androidquran/service/util/DownloadStarter.kt` → implements `common/download/Downloader.kt` (`@ContributesBinding(AppScope)`), translating feature-module requests into `QuranDownloadService` intents with `EXTRA_AUDIO_BATCH` and `AudioDownloadMetadata(qariId)`.
- `feature/audio/` → `api/AudioUpdateService.kt` (Retrofit `GET /data/audio_updates.php?revision=`), `AudioUpdater.computeUpdates`, `util/MD5Calculator`; scheduled by `app/.../worker/AudioUpdateWorker.kt` (periodic, 7 days, created via `core/worker/QuranWorkerFactory` DI).
- `app/src/main/java/com/quran/labs/androidquran/data/TimingRepository.kt` + `database/SuraTimingDatabaseHandler.kt` → reads the gapless timing SQLite (ayah start offsets, optional per-word CSV timings) behind an `LruCache(3)` keyed by (db path, sura).
- `autoquran/` → separate module exposing a browsable media service for Android Auto rather than extending `AudioService`.

**Seams worth noting**: `AyahActionFragmentProvider` (panel plug-in), `Downloader` + `@ContributesBinding` (downloadmanager never depends on :app directly), `AudioExtensionDecider` interface (`QuranAudioExtensionDecider` picks opus/mp3), `QariDownloadInfoSource` interface, and `AudioStatusRepository` as the single source of truth for playback state.

## 3. Data flow

1. **UI event** — e.g. tap play on `StoppedAudioBar` → sink in `AudioBarPresenter.eventListeners()` → `AudioBarEventRepository.tryEmit(AudioBarEvent.Play)` → collected by `AudioStatusRepositoryBridge` → `PagerActivity.onPlayPressed()`. (Or panel `apply()` → `context.playFromAyah(...)`.)
2. **Range resolution** — `PagerActivity.playFromAyah(start, end?, page, …)` fills a missing end via `AudioUtils.getLastAyahToPlay()` using the user's look-ahead preference (`quranSettings.preferredDownloadAmount`: page/sura/juz), then calls `audioPresenter.play(...)`.
3. **Decision** — `AudioPresenter.play()` computes `AudioPathInfo`; if `shouldStream` is set but files are missing locally it rewrites `urlFormat` to the remote URL (`audioUtil.getQariUrl(qari, extension)`, extension from `AudioExtensionDecider`); otherwise it keeps local paths. `proceedWithAudioRequest` asks `getDownloadIntent()`: non-null means prerequisites are missing.
4. **Optional download leg** — missing prerequisites trigger `screen.handleRequiredDownload(intent)`: Wi-Fi consent (`needsPermissionToDownloadOver3g` → `downloadInfoStreams.requestDownloadNetworkPermission()`, surfacing as the audiobar `Prompt` state) and POST_NOTIFICATIONS permission, then `startService(QuranDownloadService)`. Progress/error flows back as `DownloadInfo` events consumed by `AudioBarPresenter.toAudioBarState()`; success reaches `audioPresenter.onDownloadSuccess()` which replays the retained `lastAudioRequest`.
5. **Start service** — `handlePlayback(request)` does `startService(Intent(ACTION_PLAYBACK).putExtra(EXTRA_PLAY_INFO, request))`. `AudioService.handleIntent` rebuilds `AudioQueue(quranInfo, request, AudioPlaybackInfo(start, 1, 1, needsBasmallah))` and toggles playback.
6. **Media preparation** — `playAudio()` resolves the concrete URL with `audioQueue.getUrl()`; for gapless qaris it first suspends on `TimingRepository.timings(dbPath, sura)` on the service-handler coroutine dispatcher. `buildMediaSource()` wraps http(s) URLs in a `CacheDataSource` (stream cache); local paths go straight through. Basmalah/isti3atha overrides are played as raw resources (`android.resource://…R.raw.bismillah`) with `playerOverride = true`, chaining to the real file in `onPlayerCompleted`.
7. **Verse tracking loop** — for gapless audio `MSG_UPDATE_AUDIO_POS` ticks on the handler thread (`updateAudioPlayPosition()`): it maps player position → ayah via `SuraTimings.ayahTimings` (150 ms hysteresis against spurious switches), detects end-of-sura via the sentinel index `ayahTimings[999]`, advances/repeats through `AudioQueue.playAt()`, and schedules the next tick at `(timeDelta / playbackSpeed)`. Word highlighting derives its own next-tick delay from `wordTimings`.
8. **Publish** — every transition calls `updateAudioPlaybackStatus()` writing `AudioStatus.Playback(currentAyah, request, PLAYING|PAUSED|PREPARING, currentWord)` into `AudioStatusRepository`; the same call sites also refresh the notification title and `MediaMetadataCompat`.
9. **Render** — `AudioBarPresenter.transformAudioBarState()` folds status + qari into `AudioBarState`; `PlaybackAudioBar` recomposes; `AudioStatusRepositoryBridge.onPlaybackAyahChanged` snaps the pager.
10. **Commands back** — pause/skip/rewind/stop become plain service intents (`audioUtils.getAudioIntent(context, ACTION_*)`); repeat/speed edits go as `ACTION_UPDATE_SETTINGS` with a copied `AudioRequest`, handled by `audioQueue.withUpdatedAudioRequest(playInfo)` so playback position survives the change.
11. **Completion** — `Player.STATE_ENDED` → `onPlayerCompleted()` → `audioQueue.playNextAyah(false)`: same-file repeats seek via `getSeekPosition()`, sura transitions call `playAudio(playBasmallah)`, exhaustion calls `processStopRequest(true)` which stops foreground, releases ExoPlayer, and `stopSelf()` (service is `START_NOT_STICKY`).

## 4. Storage & network

**On-disk layout** (under the selectable audio root, `QuranFileManager.audioFileDirectory()`)
- Gapped qari `<qari.path>/<sura>/<ayah>.<mp3|opus>` — one small file per verse.
- Gapless qari `<qari.path>/<sura %03d>.<ext>` plus `<qari.path>/<dbname>.db` — a per-reciter SQLite timing database downloaded as a zip (`getGaplessDatabaseUrl()` = `getAudioDatabasesBaseUrl() + dbname + ".zip"`; madani base is `https://android.quran.com/data/databases/audio/`).

**URL patterns** (`AudioUtils.getQariUrl`)
- Gapless: `https://download.quranicaudio.com/quran/<reciter>/` + `%03d.<ext>`
- Gapped: e.g. `https://mirrors.quranicaudio.com/everyayah/Abdullah_Basfar_192kbps/` + `%03d%03d.<ext>` (sura+ayah)
- Format selection: `QuranAudioExtensionDecider` prefers `opus` whenever the qari has an `opusUrl`, but `allowedAudioExtensions()` accepts legacy `mp3` files too — downloads/streaming use opus, existing mp3 libraries keep working (`AudioQueue.getUrl()` falls back across extensions).

**Caching**
- Streaming cache: Media3 `SimpleCache` at `cacheDir/audio_stream_cache`, `LeastRecentlyUsedCacheEvictor(128 MB)`, `StandaloneDatabaseProvider`; cache keys are suffixed `"|$baseKey|audio_revision=<currentAudioRevision>"` (`streamCacheKeyFactory()`), so bumping the stored revision invalidates stale cached streams wholesale.
- Downloaded-file inventory: `QariDownloadInfoManager` (AppScope singleton) scans the audio directory once at startup into `QariDownloadInfoStorageCache` (an in-memory `MutableStateFlow`, not a database), then re-scans a single qari after each `DownloadInfo.FileDownloaded` event or `AudioCacheInvalidator.qarisToInvalidate()` emission. Derived models distinguish fully vs partially downloaded suras (`PartiallyDownloadedSura`), which drive the "ready to play" section and gapped-qari visibility filters.
- Gapless timings: `TimingRepository` LRU-caches three suras of `SuraTimings`; cleared on service destroy and when an audio update deletes a timing db (`AudioUpdateWorker` → `SuraTimingDatabaseHandler.clearDatabaseHandlerIfExists`).

**Preferences** (`app/.../data/Constants.kt`): `defaultQari`, `preferStreaming` (`PREF_PREFER_STREAMING`), `preferredDownloadAmount`, `currentAudioRevision`.

**Background maintenance network**: Retrofit `GET /data/audio_updates.php?revision=N` returns `AudioUpdates{current_revision, updates[]}` of per-file MD5 expectations; `AudioUpdater.computeUpdates` + `MD5Calculator` delete local files/databases that no longer match, forcing transparent re-download. Scheduled as `PeriodicWorkRequestBuilder<AudioUpdateWorker>(7, DAYS)` from `QuranDataPresenter`.

**Download management**: `QuranDownloadService` holds a WifiLock, retries/resumes partial transfers, dedupes recently failed URLs, and posts progress notifications; strategies compute `fileCount()` (verses +1 for basmallah, or suras +1 for the timing db) so progress bars have correct denominators. Every audio download carries `AudioDownloadMetadata(qariId)` in `EXTRA_METADATA` so post-download invalidation and the downloadmanager UI can filter events by reciter.

## 5. Why it is built this way ON THIS PLATFORM

- **Foreground service + notification is the only sanctioned background-audio vehicle on modern Android.** `setUpAsForeground()` promotes immediately on `ACTION_PLAYBACK`/media-button intents ("go to the foreground as quickly as possible"), uses a dedicated notification channel, and `PagerActivity.handleRequiredDownload` requests `POST_NOTIFICATIONS` before playback-with-download begins. `START_NOT_STICKY` reflects product intent: recitation should not resurrect itself after the system kills the process.
- **A hand-rolled command protocol (intents + Parcelable `AudioRequest`) instead of Binder/MediaController.** The service has no bound interface (`onBind` returns null) because its clients include notification `PendingIntent`s and headset media buttons that have no activity context; `startService` works uniformly from all of them. The newer reactive layer (`AudioStatusRepository` StateFlow + `AudioBarEventRepository` SharedFlow) was bolted alongside rather than replacing intents, letting the View-based shell and Compose leaf features share one truth without a Binder contract.
- **Legacy `MediaSessionCompat` paired with Media3 `ExoPlayer`.** The player is Media3, but session/notification plumbing is androidx.media (`MediaSessionCompat`, `androidx.media.app.NotificationCompat.MediaStyle`, `MediaButtonReceiver`) — a deliberate compatibility choice for the installed fleet (and Wear/Auto ecosystems) rather than migrating to `media3-session`.
- **One `HandlerThread` serializes everything.** Intent handling, position polling, and (via `serviceHandler.asCoroutineDispatcher()`) the suspend timing-database reads all run on `"AyahAudioService"`. That removes whole classes of races between `Player.Listener` callbacks, queue mutation, and polling — cheap insurance versus locking.
- **Gapped vs gapless is a storage/fidelity trade-off encoded in data, not code paths.** Per-verse mp3s make arbitrary verse-range playback, per-verse repeats, and resumption trivial (just switch files); single-file-per-sura recordings sound continuous but require a sidecar timing database to translate time→verse, hence the hysteresis, the `ayahTimings[999]` end-of-sura sentinel, and playing basmalah/isti3atha from bundled raw resources because gapless sura files handle them inconsistently (`AudioRequest.needsIsti3athaAudio()` special-cases minshawi).
- **Streaming-first with a bounded cache respects low-end devices.** Storage is the scarcest resource for an app whose page images already eat tens of MB, so `preferStreaming` streams on demand through a 128 MB LRU cache in `cacheDir`, while `AudioPresenter.play()` silently prefers local files whenever the requested range is fully downloaded regardless of the setting.
- **APK size discipline leaks into the player config**: a custom `RenderersFactory` instantiating only `MediaCodecAudioRenderer` lets R8 strip video/text renderers (comment cites the Media3 shrinking doc); the notification icon is generated off-thread with OOM guards and a 1×1 fallback bitmap for Wear.
- **WorkManager, not the service, owns maintenance.** MD5-based audio-refresh sweeps must run opportunistically whether or not the user listens; the playback service stays lean and dies when idle.
- **Android Auto gets its own module** (`autoquran`, browsable media service wired in `di/ServiceBindings.kt`) because Auto requires a `MediaBrowserService` contract and a driving-safe UX the phone service cannot assume.
- A platform with OS-level media sessions and download managers (e.g. iOS `MPRemoteCommandCenter`/background URLSession, or web MediaSession API) would push notification/state synthesis and transfer retry down to the OS; here Android offers neither a durable transfer queue suitable for thousands of tiny verse files nor a session abstraction that predates the app, hence the custom service, notifier, and cache layers.

## 6. Edge cases & offline behavior

- **Defensive service lifecycle**: null-intent crash guard in `onStartCommand`; a pause arriving while stopped is treated as stop (the `AudioIntentReceiver` wake-up case); `shouldStop` cancels playback whose prepare finished after the user pressed stop; `onPlayerError` tears down foreground and publishes `AudioStatus.Stopped`.
- **Missing/corrupt data**: `playAudio` checks `File.exists()` for local URLs and hard-stops otherwise; `AudioQueue.getUrl()` tries each allowed extension before giving up; corrupt timing databases are swallowed (`SQLException` logged, "don't crash the app if the database is corrupt") yielding empty timings.
- **Repeat/bounds semantics**: `-1` = infinite (picker value 26 maps to it); enabling a range repeat auto-checks restrict-to-range; with `enforceBounds`, out-of-range jumps wrap to the range start while range repeats remain and `getUrl()` returning null (out of bounds) triggers full stop — bounds are enforced twice, in the queue and again at URL generation.
- **Gapless timing quirks**: sub-150 ms deltas defer the ayah switch to avoid highlight flicker; the last ayah is deliberately not polled ("let the file complete on its own to avoid getCurrentPosition() bugs"); poll intervals divide by `playbackSpeed` so speed changes keep tracking accurate; seek-back-to-ayah-1 routes through `ayahTimings[0]` so the embedded basmalah replays.
- **Downloads**: interrupted transfers resume inside `QuranDownloadService`; `ERROR_CANCELLED` is distinguished in `SheikhAudioPresenter` (dialog dismissed, no error shown) while other errors map to `SheikhDownloadDialog.DownloadError` or the audiobar's `ErrorAudioBar`; deletion paths (`removeSuras`) differ per mode (recursive sura directories for gapped, padded `%03d` files plus optional `.db` for gapless) and always invalidate the inventory cache afterwards.
- **First run vs upgrade**: with no audio directory, `QariDownloadInfoManager.populateCache()` exits early leaving an empty list; gapped qaris that have a gapless alternative stay invisible until they own downloads (filtering duplicated in `AudioUtils.getQariList` and `downloadQariInfoFilteringNonDownloadedGappedQaris`); `currentAudioRevision` gates both the update worker and stream-cache keys so upgrades invalidate cleanly.
- **Locale/accessibility**: localized numerals everywhere (`NumberFormat` per locale, Arabic-Indic formatter and KFGQPC typeface sizing for Arabic pickers), localized sura-name arrays from `common/ui/core`; notification is `VISIBILITY_PUBLIC`. Notable gap: audiobar icons pass empty `contentDescription` strings (`ui/PlaybackAudioBar.kt`), so the Compose controls are effectively unlabeled for TalkBack.
- **Recitation bar states** (`RecitationListening/Playing/Stopped`) ship in the audiobar but are inert in open-source builds because `RecitationPresenterImpl.isRecitationEnabled()` returns false — the same pluggable seam noted for the recite-from-here feature; the audio half of the bar is unaffected.
