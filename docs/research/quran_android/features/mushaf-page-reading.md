# Mushaf page reading with ayah interaction
> How **Quran for Android (github.com/quran/quran_android)** implements this feature. Sources read from a shallow clone @ main (2026-08-23); repo-relative paths cited throughout.

## 1. What the user sees

The reading screen is `PagerActivity` (`app/src/main/java/com/quran/labs/androidquran/ui/PagerActivity.kt`), a full-screen `ViewPager` (`NonRestoringViewPager`, id `quran_pager`) whose pages are pre-rendered Madani mushaf images. Concrete behavior:

- **Swipe paging**: one ViewPager position = one mushaf page (604 pages); in landscape tablets/foldables, dual-page mode shows two pages per position via `TabletFragment` (left/right `AyahImageTrackerItem`s). Page↔position mapping goes through `QuranInfo.getPositionFromPage/getPageFromPosition`. Swiping past the selection's page drags the ayah toolbar with the finger: `onPageScrolled` rewrites the selection indicator with `withXScroll(-positionOffsetPixels)` / `(viewPager.width - positionOffsetPixels)` and clears the selection once you're >1 page away (`onPageSelected`, PagerActivity.kt:513-560).
- **Tap anywhere** (no active selection): toggles the immersive chrome. `ReadingEventPresenter.onClick()` → `onPageClicked()` → `toggleActionBar()`, which animates the top toolbar area and bottom audio bar away and hides system bars (`setUiVisibilityR/KitKat`, immersive flags; auto re-hide after a delay via `PagerHandler` MSG_HIDE_ACTIONBAR). A toast pops on page change showing juz'/rub3/Hizb quarter when `shouldDisplayMarkerPopup()` is set (`QuranDisplayHelper.displayMarkerPopup`).
- **Long-press an ayah**: selects it — a colored rectangle highlights every line the ayah spans, haptic feedback fires (`viewPager.performHapticFeedback(HapticFeedbackConstants.LONG_PRESS)`), and a floating context toolbar with a pointing "pip" appears anchored above/below the ayah bounds.
- **Subsequent taps on another ayah** extend to a range selection (`AyahSelection.AyahRange`) — long-pressing again replaces the anchor or extends the range depending on order (`AyahTrackerPresenter.updateAyahRange`). Double-tap clears the selection. Back press also ends selection (`onClearAyahModeBackCallback`).
- **Per-ayah context toolbar** (`common/toolbar/.../AyahToolBar.kt`, menu `common/toolbar/src/main/res/menu/ayah_menu.xml`): bookmark (heart toggle), share submenu (share link via quranapp.com, share ayah text, copy), view translation (opens the sliding bottom panel to the translation page), play from here (audio picker), and recite-from-here (hidden unless recitation is enabled; ships disabled in OSS builds). Long-pressing any toolbar button shows its label as a toast (`longPressLambda`). The bookmark icon reflects live bookmark state (`AyahToolBarPresenter` queries `BookmarksDao.isSuraAyahBookmarked` on a CONFLATED channel + `Dispatchers.IO`).
- **Sliding panel**: below the pager sits a `SlidingUpPanelLayout` (`initAyahActionPanel`) hosting `SlidingPagerAdapter` — core panels TRANSLATION_PAGE (0) and AUDIO_PAGE (1) plus module-contributed `AyahActionFragmentProvider` panels sorted by `order`, reversed positions under RTL (`getPagePosition`).
- **Other visible layers drawn onto the page image**: header/footer overlay text rendered by `HighlightingImageView.overlayText` (sura name top-right/left, localized page number bottom-center, juz' + rub3 + manzil text) — this is why `PageCoordinates` page bounds are needed even when you never tap. Bookmark highlights, audio-follow highlight, night-mode color filter, and display-cutout padding are all baked into the same `HighlightingImageView`.
- **Settings that change this screen**: night mode + brightness sliders (`imageView.setNightMode(...)` applies an inverted `ColorMatrixColorFilter`), page-info overlay toggle (`quranSettings.shouldOverlayPageInfo()` gates `getPageCoordinates(wantBounds=true)`), highlight-bookmarks toggle, marker popups, volume-key navigation, orientation lock, dual-page mode, and split quran+translation mode.

## 2. Architecture & key files

- `app/.../ui/PagerActivity.kt` — shell: owns `QuranPageAdapter`, wires `ReadingEventPresenterBridge`/`AudioStatusRepositoryBridge`, hosts `AyahToolBar` (injected via `AyahToolBarInjector.injectToolBar` from `PagerActivityComponent`), handles all ayah-menu item clicks (`AyahMenuItemSelectionHandler`), shares/copies verses, and manages immersive UI visibility.
- `app/.../ui/helpers/QuranPageAdapter.kt` — FragmentStatePagerAdapter choosing `QuranPageFragment` / `TabletFragment` / `TranslationFragment` per `PageMode`; honors an injected `PageViewFactory` (`Map<String, PageProvider>` seam) so alternate page types like :feature:linebyline can replace image pages.
- `app/.../ui/fragment/QuranPageFragment.kt` — one page: builds `QuranImagePageLayout` + `HighlightingImageView` programmatically (no XML content view), implements `PageController` (touch callbacks in), `QuranPageScreen` (bitmaps/coordinates in), and `AyahInteractionHandler` (supplies tracker items). Gets per-page DI via `pagerActivityComponent.quranPageComponentFactory().generate(pages)` (`di/component/fragment/QuranPageComponent.kt`, Metro `@GraphExtension(QuranReadingPageScope)` + `@QuranPageScope` — one component instance per visible page, carrying the `pages: IntArray`).
- `app/.../presenter/quran/QuranPagePresenter.kt` — RxJava3 presenter: loads page bitmaps (`QuranPageLoader.loadPages`) and ayah coordinates (`CoordinatesModel`), pushes results to the screen, surfaces download errors as retry strings, retries coordinate loading on `refresh()`.
- `app/.../presenter/quran/ayahtracker/*` — the interaction core:
  - `AyahTrackerPresenter` (@QuranPageScope): subscribes three flows — `ReadingEventPresenter.ayahSelectionFlow`, `AudioStatusRepository.audioPlaybackFlow`, `bookmarksDao.bookmarksForPage(page)` — and fans out to per-page `AyahTrackerItem`s; also routes touch events (`handleTouchEvent`), computes selections, defers unhandled highlights into `pendingHighlightInfo` until coordinates arrive, and adapts recitation popups/highlights.
  - `AyahTrackerItem` (base) → `AyahImageTrackerItem` (holds `coordinates: Map<String, List<AyahBounds>>` + `pageGlyphsCoords: PageGlyphsCoords`, does hit-testing and toolbar positioning) → `AyahScrollableImageTrackerItem` (adds smooth-scroll-to-highlighted-ayah logic for landscape scrollable pages). `AyahTranslationTrackerItem`, `AyahSplitConsolidationTrackerItem` serve translation/split modes; `NoOpImageTrackerItem` for blank slots.
- Seams (interfaces):
  - `ui/util/PageController.kt` — fragment-level input contract (`handleTouchEvent`, `handleRetryClicked`, `onScrollChanged`, `handleLongPress`, `endAyahMode`).
  - `presenter/quran/QuranPageScreen.kt` + `ui/helpers/QuranPage.kt` — view contracts the fragment implements.
  - `pages/common` types: `PageCoordinates`, `AyahCoordinates`, `AyahBounds`, `PageGlyphsCoords`, `com.quran.page.common.draw.ImageDrawHelper` — the pluggable draw pipeline injected as a `Set<ImageDrawHelper>`.
  - `common/data/model/selection/AyahSelection` + `SelectionIndicator` — platform-neutral selection model shared by app, toolbar, recitation, and sync features.
  - `common/reading/ReadingEventPresenter.kt` — @ActivityScope event bus/state holder (`clicksFlow`, `quranClicksFlow`, `detailsPanelFlow`, `ayahSelectionFlow: StateFlow<AyahSelection>`, plus `selectNextAyah/selectPreviousAyah` used by keyboard/volume navigation).
  - `common/toolbar/AyahToolBar.kt` + `AyahToolBarPresenter` + `AyahSelectionReactor` — reusable toolbar module that only knows about `AyahSelection` and `BookmarksDao`, not the pager.
- Highlight rendering: `app/.../view/HighlightingImageView.java` (state: `SortedMap<HighlightType, Set<AyahHighlight>> currentHighlights`, animation `ValueAnimator`) delegating pixels to `app/.../view/HighlightsDrawer.kt` (an `ImageDrawHelper` instantiated twice: clipping passes COLOR+HIDE before `super.onDraw`, rect passes HIGHLIGHT+BACKGROUND+UNDERLINE after).
- Data sources: `app/.../data/AyahInfoDatabaseProvider.kt` → `AyahInfoDatabaseHandler.java` (raw SQLite `glyphs` table per width bucket); `app/.../model/quran/CoordinatesModel.kt` (bounds normalization math); `app/.../ui/helpers/QuranPageLoader.kt` + `QuranDisplayHelper.getQuranPage` (bitmap load/download).

## 3. Data flow

1. **Gesture → event type**: `QuranImagePageLayout.setPageController` attaches a `GestureDetector.SimpleOnGestureListener` (`PageGestureDetector`) to the `HighlightingImageView`; `onSingleTapUp/onDoubleTap/onLongPress` map to `AyahSelectedListener.EventType.{SINGLE_TAP,LONG_PRESS,DOUBLE_TAP}` and call `pageController.handleTouchEvent(event, type, pageNumber)` → `QuranPageFragment.handleTouchEvent` → `AyahTrackerPresenter.handleTouchEvent(activity, event, eventType, page, ayahCoordinatesError)`.
2. **Routing rules** (AyahTrackerPresenter.kt:259-285): DOUBLE_TAP → clear selection; LONG_PRESS or any press while a selection exists → if coordinates are missing, `checkCoordinateData` offers the "download required files" dialog, else `handleAyahSelection`; SINGLE_TAP during a recitation session → word-level `handleTap`; otherwise plain `readingEventPresenter.onClick()` (chrome toggle).
3. **Hit-testing**: `getAyahForPosition` → `AyahImageTrackerItem.getAyahForPosition(page, x, y)` → `ImageAyahUtils.getAyahFromCoordinates`: converts screen→page coords through the ImageView's `imageMatrix` (`getPageXY`), returns the exact `"sura:ayah"` key whose `AyahBounds` contains the point, else falls back to nearest line then nearest x-bound of that line (RTL-aware because it works purely on stored glyph rectangles, not text layout).
4. **State update**: `handleAyahSelection` emits `readingEventPresenter.onAyahSelection(AyahSelection.Ayah(result, getToolBarPosition(...)))` where the toolbar position is a `SelectionIndicator.SelectedItemPosition(firstItem, lastItem)` computed from the ayah's consolidated bounds mapped through the image matrix plus padding/dual-page x-offset (`AyahImageTrackerItem.getToolBarPosition` → `ImageAyahUtils.getToolBarPosition`). Range long-presses produce `AyahSelection.AyahRange` via `updateAyahRange` + `SuraAyahIterator`.
5. **Fan-out**: `AyahTrackerPresenter.onAyahSelectionChanged` clears `HighlightTypes.SELECTION` when the ayah changed, then calls `item.onHighlightAyah(...)` (single) or intersects the iterated range with `quranDisplayData.getAyahKeysOnPage(page)` and calls `onHighlightAyat` (range, so only ayahs physically on the visible page light up). `AyahImageTrackerItem` forwards to `ayahView.highlightAyah(...)` + `invalidate()`.
6. **Painting**: next frame, `HighlightingImageView.onDraw` runs `clippingHighlightsDrawer.draw` (COLOR re-draws clipped regions of the bitmap through a `PorterDuffColorFilter`; HIDE clip-outs rects), then `super.onDraw` (the page bitmap), then `highlightsDrawer.draw` which maps each `AyahBounds` through `imageMatrix.mapRect` and draws colored rects (or a 3dp underline strip). Paints come from a static `PaintCache` keyed by (mode, colorResId) shared across pages.
7. **Toolbar reaction**: `AyahToolBarPresenter` observes the same `ayahSelectionFlow`, sends the new sura:ayah down `bookmarkToCheckChannel` (conflated, IO-thread lookup), and calls `reactor.onSelectionChanged(selectionIndicator, reset)` → `AyahToolBar.onSelectionChanged` hides/shows itself, recomputes pip side (`SelectedAyahPlacementType.TOP/BOTTOM`), and positions via `translationX/Y` including an RTL correction branch in `updatePosition`/`onLayout`.
8. **Menu action → effect**: click bubbles to `PagerActivity.AyahMenuItemSelectionHandler.onMenuItemClick`, which reads `readingEventPresenter.currentAyahSelection()` and either opens a sliding panel (`showSlider(SlidingPagerAdapter.TRANSLATION_PAGE)`), starts audio (`playFromAyah` → download checks → `AudioService` intent), shares text (`arabicDatabaseUtils.getVerses` off the Arabic search DB) or a quranapp:// link (`quranAppUtils.getQuranAppUrlObservable`), opens the Compose `showAyahBookmarkSheet`, or starts recitation — then `endAyahMode()` sets `AyahSelection.None`.
9. **Audio follow-highlight loop**: `audioStatusRepository.audioPlaybackFlow` → `onAudioSelectionChanged` highlights the playing ayah with `HighlightTypes.AUDIO` (scroll-only), and *after* highlighting the new ayah un-highlights the previous one — ordering deliberately preserves the float animation. In `HighlightingImageView.highlightFloatableAyah` a `TransitionAyahHighlight(source->destination)` is animated over 500 ms with `HighlightAnimationTypeEvaluator` + `NormalizeToMinAyahBoundsWithGrowingDivisionStrategy` interpolating intermediate bounds each frame; mid-animation ayah changes cancel and restart from the current animated value.
10. **Late data**: if a highlight is requested before `setAyahCoordinatesData` lands, `pendingHighlightInfo` replays it the moment non-empty coordinates arrive (`AyahTrackerPresenter.setAyahCoordinates`). Scrolling a landscape page re-emits the selection with `withYScroll(-y)` (`QuranPageFragment.onScrollChanged`) so the toolbar tracks the ayah.

## 4. Storage & network

- **Page images**: files `pageNNN.png` (zero-padded, `Locale.US` NumberFormat, `QuranFileUtils.getPageFileName`) under `<storage>/quran_android/warsh|madani.../width{W}/`, decoded with `BitmapFactory.Options.inPreferredConfig = ALPHA_8` — 1 byte/pixel monochrome, roughly a quarter the memory of ARGB_8888 for a full-page bitmap. Downloaded lazily from `{imagesBaseUrl}width{widthParam}/{filename}` (Madani base `https://android.quran.com/data`, `MadaniPageProvider.getImageBaseUrl`; `imageBaseUrl` resolves through the flavor's `PageProvider`). `getImageFromWeb` streams via OkHttp with a Glide/Picasso-style `ExceptionCatchingSource` wrapper (because `decodeStream` silently returns null on truncated downloads), writes to disk, and retries exactly once before returning `ERROR_DOWNLOADING_ERROR`.
- **Width bucketing**: `QuranScreenInfo.widthParam` asks the flavor's `PageSizeCalculator.getWidthParameter()` (e.g. `_512`, `_1024`, `_1280`) so devices get a pre-scaled image pack; dual-mode falls back to `tabletWidthParam` when a bitmap fails to decode (`QuranPageLoader.loadImage`). Image packs have a version (`MadaniPageProvider.getImageVersion() = 8`) driving patch zips `{patchBaseUrl}{toVersion}/patch{width}_v{toVersion}.zip`.
- **Ayah coordinates DB**: one SQLite file per width, `ayahinfo{_width}.db` downloaded as `{ayahInfoBaseUrl}ayahinfo{width}.zip` into the databases dir; opened read-only via `SQLiteDatabase.openDatabase` and cached in a static map keyed by filename, invalidated wholesale when `getQuranAyahDatabaseDirectory()` changes (SD-card migration). Table `glyphs` columns include `page, line, sura_number, ayah_number, position, min_x, min_y, max_x, max_y` (+ nullable `glyph_type`); newer builds add an `ayah_markers` table (detected at runtime via sqlite_master count) for sura headers/verse markers, and glyph_type enables word-level `PageGlyphsCoords` (used for word tap targets in recitation and word-range selection).
- **Derived geometry cache**: none persisted — `CoordinatesModel.normalizePageAyahs` recomputes consolidated multi-line `AyahBounds` on Schedulers.computation each time a page binds (merging line fragments using a 1.5%-of-page-width threshold), trading CPU for simplicity since it runs once per visible page.
- **Bookmarks**: SQLDelight `Bookmark.sq` behind `BookmarksDao`; `AyahTrackerPresenter.subscribe` collects `bookmarksDao.bookmarksForPage(trackerItem.page)` reactively so adding/removing a bookmark repaints `HighlightTypes.BOOKMARK` without manual refresh (subject to `quranSettings.shouldHighlightBookmarks()`).
- **Network endpoints touched by the ayah toolbar**: share-link shortener `https://quranapp.com/` (util/QuranAppUtils.kt builds `quranapp://`/https links with a signed key), verse text from local Arabic DB (no network), audio from quranicaudio.com/everyayah mirrors (see `MadaniPageProvider.getQaris`).
- **Caching/invalidation**: bitmaps are not LRU-cached globally — each `QuranPageFragment` holds its own decoded bitmap until `cleanup()` nulls the drawable on destroy; re-entry re-reads from disk (fast ALPHA_8 decode). Coordinate handler caching is per-process static; missing individual pages are repaired opportunistically by `worker/MissingPageDownloadWorker` (scans `1..numberOfPages` for absent `pageNNN.png`, parallel flow download, capped at MISSING_PAGE_LIMIT).

## 5. Why it is built this way ON THIS PLATFORM

- **Images instead of text**: rendering Uthmani script faithfully with correct ligatures, ayah markers, and justification across hundreds of Android text stacks was infeasible in 2010-era Android and still risks font fragmentation; shipping rasterized pages guarantees pixel-perfect mushaf typography offline. The cost is the entire support apparatus: first-run page downloads, width buckets, SD-card/scoped-storage migration, patch zips per image version, and hit-testing done against database rectangles rather than a text layout. `:feature:linebyline` exists precisely as the Compose-rendered alternative page type plugged in via `PageViewFactory`.
- **Memory budget**: full-page bitmaps at tablet sizes are enormous; `ALPHA_8` decoding, `window.setBackgroundDrawable(null)` to kill overdraw, `NonRestoringViewPager` (skips hardware-layer snapshotting of pages), and per-fragment bitmap ownership freed in `destroyItem → cleanup()` are all direct memory-pressure mitigations, with an explicit `OutOfMemoryError` catch-and-retry at alternate width in `QuranPageLoader.loadImage`.
- **Foreground interactivity, no background need**: everything here is view-layer work bound to fragment lifecycle (`bind/unbind` pairs swap the coroutine scope on every start/stop because a cancelled scope can't be reused — comment in AyahTrackerPresenter). Heavy lifting (DB reads) uses Rx `Schedulers.computation/io` off the main thread; nothing needs WorkManager except repair/update jobs that must outlive the UI.
- **Event-bus decoupling instead of a ViewModel**: `ReadingEventPresenter` is a @ActivityScope singleton holding `StateFlow<AyahSelection>`; multiple legacy MVP presenters, the View-based `AyahToolBar`, Compose panels, and the recitation stack all observe one source of truth without the activity shuttling state. That's what lets incremental Compose features (audiobar, ayahbookmark) participate in a View-era selection model.
- **Immersive reading**: `setUiVisibilityR/KitKat` maintain two generations of system-ui APIs, use inset listeners (`Insetter` in `HighlightingImageView`) to pad for display cutouts so no glyph is hidden, and auto-hide after `DEFAULT_HIDE_AFTER_TIME` — mushaf pages should be chrome-free, which also explains the tap-to-toggle gesture consuming plain clicks.
- **Offline-first**: the reader assumes zero connectivity; the only network paths are lazy single-page fetches (retry-once), the coordinate DB zip, and optional sharing. Errors surface inline on the page (`setPageDownloadError` swaps in an error string + tap-to-retry) rather than blocking dialogs.
- **A different platform would differ mainly in rendering**: iOS/web would likely keep the same image+coordinate-DB approach (it's the data that's expensive, not the code), but could use Core Text/Canvas overlays or SVG glyph paths for selection; a web client would need the same width bucketing for bandwidth reasons, while a native-text renderer (like :feature:linebyline) eliminates downloads entirely at the cost of typographic fidelity.

## 6. Edge cases & offline behavior

- **Missing images**: `QuranPagePresenter.downloadImages` maps error codes to `sdcard_error`, `download_error_network`, or `download_error_general`; `QuranPageFragment.setPageDownloadError` shows the message and makes the whole page tappable to retry (`onPressIgnoringSelectionState` → onClick). Empty/non-existent pages are filtered with `quranInfo.isValidPage` (Shemerly mushaf odd page counts leaving a blank slot in dual mode).
- **Missing coordinate data**: `ayahCoordinatesError` triggers `checkCoordinateData` on first touch, offering `showGetRequiredFilesDialog()`/`downloadRequiredFiles()` when either `haveAyaPositionFile()` or `hasArabicSearchDatabase()` is false; `QuranPagePresenter.refresh()` re-runs the coordinate query after errors. Highlights requested before coordinates arrive are parked in `pendingHighlightInfo`.
- **Hit-test fallback**: taps landing between lines resolve to the closest line then the closest x-extent (`ImageAyahUtils.getAyahFromCoordinates` fallback path, logged as "fell back to closest ayah"), so sloppy taps still select something sensible; taps on empty margins select nothing and just toggle chrome.
- **Degenerate bounds**: `CoordinatesModel.consolidate/normalizeAyahBounds` handle ayahs spanning 1..n lines, overlapping fragments, and the >4-fragment case by deduplication — needed because raw glyph rows give one rect per line segment and highlights must look continuous.
- **RTL/locale**: page swipe direction and toolbar placement work purely from coordinates, so RTL locales need no mirroring of the mushaf itself; explicit handling exists for the toolbar (`layoutDirection == LAYOUT_DIRECTION_RTL` translationX fixups in `AyahToolBar.updatePosition/onLayout`), for `SlidingPagerAdapter.getPagePosition` reversing panel order, `QuranUtils.isRtl()` wiring, localized page numbers/rub3/juz strings (`QuranUtils.getLocalizedNumber`), and `LeftToRightLinearLayout` for cases where auto-mirroring breaks layouts.
- **Night mode**: color inversion via `ColorMatrixColorFilter` with a log-scaled text brightness (`nightModeTextBrightness = 50*ln(1+backgroundBrightness)+textBrightness`, capped at 255) so the black ink stays legible without washing the paper texture; the filter is reset whenever a new drawable arrives (`setImageDrawable` override).
- **Animation safety**: `unHighlight(type)` cancels the running `ValueAnimator` for transition-animated types (guarding the "stopped before animation setup" case), and `alreadyHighlightedContains` suppresses double-painting when a transition's source or destination is already highlighted.
- **Lifecycle/rotation**: saved instance state keeps last page, translation mode, actionbar visibility, and prior dual-page flag; crossing device-fold or orientation changes remaps page numbers (`mapSinglePageToDualPage`/`mapDualPageToSinglePage`). Selection survives rotation because it lives in the retained-scoped `ReadingEventPresenter`, but is dropped if you swipe >1 page away.
- **Accessibility**: weak spot — interactions are pure touch geometry with no TalkBus semantics; long-press tooltips via `longPressLambda` toast and haptics on selection are the main affordances. Keyboard/volume-key ayah stepping exists (`selectNextAyah/selectPreviousAyah`, `onKeyDown` navigate-with-volume-keys setting).
- **First run vs upgrade**: fresh installs see the page-download flow before anything renders; upgrades hit `MadaniDataUpgrade`/`MadaniPreferencesUpgrade` and image-version patches, and the recitation menu item stays hidden (`isRecitationEnabled() == false` in OSS builds) so the toolbar degrades gracefully to four actions.
