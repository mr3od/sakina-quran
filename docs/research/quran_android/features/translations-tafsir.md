# Translation & tafsir manager
> How **Quran for Android (github.com/quran/quran_android)** implements this feature. Sources read from a shallow clone @ main (2026-08-23); repo-relative paths cited throughout.

## 1. What the user sees

The manager is a classic View-based `AppCompatActivity` (`app/src/main/java/com/quran/labs/androidquran/ui/TranslationManagerActivity.kt`) laid out by `res/layout/translation_manager.xml`: a `Toolbar` titled `prefs_translations` / `menu_translation`, a `SwipeRefreshLayout` wrapping a `RecyclerView` fed by `TranslationsAdapter` (`ui/adapter/TranslationsAdapter.kt`). The list is one flat RecyclerView with two row types:

- **`TranslationHeader` separator rows** (`R.layout.translation_sep`) split the list into "Downloaded translations" (sorted by display order) and "Available translations" — built in `generateListItems()` via `allItems.partition { it.exists() }`.
- **`translation_row` items** show `displayName` plus a subtitle line that prefers the localized translator name (`translatorForeign`), falling back to `translator`, and hiding itself when both are blank. Downloaded rows hide the download icon; rows whose local version is behind the server version show an `ic_download` icon with the text "update available" (`needsUpgrade()`).

Interactions, all visible in code:

- **Tap a non-downloaded or outdated row** → starts a download (row click listener only fires `onClickDownloadSubject` when `!item.exists() || item.needsUpgrade()`).
- **Swipe to refresh** → `refreshTranslations(forceDownload = true)`, re-fetching the catalog over the network.
- **Long-press a downloaded row** → contextual `ActionMode` with menu `res/menu/downloaded_translation_menu.xml`: move up (`dtm_move_up`), move down (`dtm_move_down`), delete (`dtm_delete`). Reordering is live-previewed; orders are persisted when the action mode is destroyed (`updateTranslationOrdersIfNecessary()` normalizes to 1..n). Delete asks for confirmation in an `AlertDialog` ("remove_dlg_msg") before deleting the file and DB row.
- **Progress/errors** come as notifications and as a `Snackbar` (`error_getting_translation_list`) when the catalog itself fails to load.

Entry points into the screen:

- Settings: `QuranSettingsFragment` opens it from the `PREF_TRANSLATION_MANAGER` preference row (`ui/fragment/QuranSettingsFragment.kt:81`).
- `QuranActivity.launchTranslationActivity()` (`ui/QuranActivity.kt:453`), used by the menu and by `showTranslationsUpgradeDialog()` — an un-dismissable dialog shown on launch when `EXTRA_SHOW_TRANSLATION_UPGRADE` is set because downloaded translations have newer server versions (`QuranDataActivity.targetIntent()` propagates `haveUpdatedTranslations()`); answering "later" clears the flag.
- `PagerActivity.startTranslationManager()` (`ui/PagerActivity.kt:1291`) — including the case where the user switches to translation mode with nothing installed.
- `SearchActivity.kt:142` offers it when no searchable translation database exists.

Outside this screen the same feature surfaces as: a **multi-select translation spinner in the reading toolbar** (`TranslationsSpinnerAdapter`, wired in `PagerActivity.updateActionBarSpinner()` and `AyahTranslationFragment.onTranslationsUpdated()`) that writes `quranSettings.activeTranslations`; per-ayah rendering of all active translations with expandable footnote spans (`ui/translation/TranslationAdapter.kt`, `TranslationViewRow`); and settings like `PREF_TRANSLATION_TEXT_SIZE`, `PREF_AYAH_BEFORE_TRANSLATION` and `PREF_SPLIT_PAGE_AND_TRANSLATION` (`data/Constants.kt`).

## 2. Architecture & key files

- `app/src/main/java/com/quran/labs/androidquran/ui/TranslationManagerActivity.kt` — MVP-ish view: owns list state (`allItems`, `currentSortedDownloads`, `originalSortedDownloads`, `translationPositions` SparseIntArray), Rx `Disposable`s for adapter click subjects, `DefaultDownloadReceiver` for download broadcasts, `ActionMode.Callback` (`ModeCallback`) for reorder/delete.
- `app/.../presenter/translation/TranslationManagerPresenter.kt` — `@SingleIn(AppScope)` Metro singleton; catalog fetching/caching, merge of server + local state, persistence of item updates/ordering. Injects `OkHttpClient`, `QuranSettings`, `TranslationsDBAdapter`, `QuranFileUtils`.
- `app/.../dao/translation/{Translation,TranslationItem,TranslationList,TranslationHeader,TranslationRowData}.kt` — Moshi-codegen DTO `Translation(id, minimumVersion, currentVersion, displayName, downloadType, fileName, fileUrl, saveTo, languageCode, translator, translatorForeign)` and UI-facing wrapper `TranslationItem(translation, localVersion, displayOrder)` with copy helpers `withDisplayOrder`, `withLocalVersionAndDisplayOrder`, `withTranslationRemoved`, `asLocalTranslation()`.
- `common/translation` module — shared persistence layer:
  - `src/main/sqldelight/com/quran/mobile/translation/translations.sq` — SQLDelight `TranslationsDatabase`, table `translations`.
  - `kotlin/com/quran/mobile/translation/data/TranslationsDataSource.kt` — reactive DAO exposing `StateFlow<List<LocalTranslation>?>` from sqldelight `asFlow().mapToList(Dispatchers.IO)`.
  - `model/LocalTranslation.kt` — cross-module record incl. `resolveTranslatorName()` fallback chain; `mapper/LocalTranslationMapper.kt`; `di/TranslationDataModule.kt` — Metro `@BindingContainer @ContributesTo(AppScope)` providing the `AndroidSqliteDriver` for `translations.db`.
- `app/.../database/TranslationsDBAdapter.kt` (interface) + `TranslationsDBAdapterImpl.kt` — seam between app presenters and the common module; filters rows by `quranFileUtils.hasTranslation(filename)` so ghost rows for deleted files never surface, assigns next `displayOrder` via `maximumDisplayOrder()+1`, splits updates into upserts and deletes.
- `app/.../presenter/translationlist/TranslationListPresenterImpl.kt` — sorts by `displayOrder` and pushes titles to readers (`registerForTranslations`).
- `app/.../presenter/translation/BaseTranslationPresenter.kt`, `TranslationPresenter.kt`, `InlineTranslationPresenter.kt` + `app/.../model/translation/TranslationModelImpl.kt` — consumption side: load verses from each active translation database.
- `app/.../database/DatabaseHandler.kt` — raw-`SQLiteDatabase` handler opened per downloaded file (static cache map + `clearDatabaseHandlerIfExists`), reads `properties` table (`schema_version`, `text_version`) and `verses` rows, expands hyperlinked tafsir entries.
- `app/.../util/TranslationUtil.kt` — regex post-processing (inline ayah refs `«{﴿…﴾}»`, footnotes `[[…]]`, `MINIMUM_PROCESSING_VERSION = 5`).
- `app/.../service/QuranDownloadService.kt` + `service/util/DefaultDownloadReceiver.java`, `ServiceIntentHelper`, `QuranDownloadNotifier` — actual transfer machinery, shared with page/audio downloads.

Seams worth noting: the `TranslationsDBAdapter` interface hides SQLDelight behind an app-level API; `TranslationItem.exists()`/`needsUpgrade()` are the single source of truth for download state; the schema-version handshake lives entirely inside data files' `properties` tables rather than any app-side migration code; DI wiring is Metro (`@Inject`, `@SingleIn(AppScope)`, `ApplicationComponent.inject(activity)` at `di/component/application/ApplicationComponent.kt:80`).

## 3. Data flow

Catalog refresh (open manager):

1. `onCreate` → `refreshTranslations()` → `presenter.getTranslations(false)` collected in a `MainScope()` launched Flow.
2. Presenter decides staleness: `System.currentTimeMillis() - lastUpdatedTranslationDate > MIN_TRANSLATION_REFRESH_TIME` (1 hour). Fresh → `merge(cachedTranslationList(), remoteTranslationList()).take(1)` (cache only); stale → merged flow emits cache first, then network result.
3. `cachedTranslationList()` parses `<db dir>/translations.v5.cache` with a lazily built Moshi `TranslationList` adapter; `remoteTranslationList()` does a blocking OkHttp `GET host + "data/translations.php?v=5"` on `Dispatchers.IO`, then `writeTranslationList()` atomically rewrites the cache file and stamps `lastUpdatedTranslationDate`.
4. Every emission passes through `mergeWithServerTranslations(...)`: reads `translationsHash()` (rows whose files exist) and the db directory listing; for files present but missing DB rows it opens the file with `DatabaseHandler.getVersionFromDatabase()` to recover `(textVersion, schemaVersion)`; detects corrupt files (`exists && !item.exists()` → `dbFile.delete()`); detects schema downgrades/mismatches (`override = TranslationItem(translation.withSchema(...))`); writes accumulated diffs via `translationsDBAdapter.writeTranslationUpdates(updates)`; finally flips `haveUpdatedTranslations` if any item `needsUpgrade()`.
5. Back in the activity `onTranslationsUpdated` builds the id→index sparse array and calls `generateListItems()` which partitions, sorts by `displayOrder`, inserts headers, and pushes to the adapter.

Download flow:

1. Tap → `downloadItem()`: guards against redundant work, stores `downloadingItem`, invalidates cached `DatabaseHandler` (`clearDatabaseHandlerIfExists(fileName)`), renames an existing DB file to `<fileName>.old` (backup), registers a `DefaultDownloadReceiver` for `QuranDownloadNotifier.ProgressIntent.INTENT_NAME` on `LocalBroadcastManager`, then `startService(getDownloadIntent(...))` targeting `QuranDownloadService.DOWNLOAD_TYPE_TRANSLATION (=3)` with key `TRANSLATION_DOWNLOAD_KEY` and `EXTRA_OUTPUT_FILE_NAME` (`.zip` appended when the url ends in zip).
2. Service side: promotes itself to foreground immediately (`notifyDownloadStarting()`), dedupes against `successfulZippedDownloads`/`recentlyFailedDownloads`, resumes via `Range: bytes=` on a `.partial` file, checks free disk space, unzips with `ZipUtils.unzipFile` when needed, and reports progress/error/success through notification intents.
3. Success broadcast → `handleDownloadSuccess()`: deletes `.old`, computes `lastDisplayOrder + 1`, persists with `updateItem()` (which first `deleteTranslationByFileName` when `minimumVersion >= 5` to avoid duplicate ids across schema changes, then `writeTranslationUpdates`), appends the filename to `settings.activeTranslations`, rebuilds the list.
4. Failure broadcast → `handleDownloadFailure()`: renames `.old` back if the destination is gone, else deletes it — the previous translation keeps working after a botched upgrade.

Reorder/delete flows go straight from adapter Rx subjects (`UnicastSubject<TranslationRowData>` for download/remove/rankUp/rankDown) to activity methods, mutating `currentSortedDownloads` locally and persisting through `presenter.updateItemOrdering()` / `updateItem()` on `Dispatchers.IO`.

Reading flow (multi-translation): `PagerActivity.requestTranslationsList()` → `TranslationListPresenterImpl.translations()` (sqldelight StateFlow sorted by display order) → spinner multi-select writes `activeTranslations` → `BaseTranslationPresenter.getVerses()` filters+orders filenames by display order (empty selection falls back to *all* downloaded translations), fans out one `async` per translation through `TranslationModelImpl.getTranslationFromDatabase(verseRange, db)` under a `SupervisorJob`, pads missing ayat via `ensureProperTranslations`, aligns every translation per ayah in `combineAyahData`, and returns `ResultHolder(translations, ayahInformation)` rendered by `TranslationAdapter`.

## 4. Storage & network

- **Catalog index (network)**: `GET https://quran.app/data/translations.php?v=5` (`Constants.HOST` + `WEB_SERVICE_ENDPOINT`). Response JSON deserialized into `TranslationList` → `Translation` records carrying absolute `fileUrl`s. The upstream content is curated from quranenc (README.md credits quranenc, King Saud University and tanzil), but the app never talks to quranenc directly — it consumes this project-hosted normalized index (a mild correction to the feature brief).
- **Catalog cache**: `translations.v5.cache` (Moshi JSON) inside the Quran databases directory; invalidated by the 1-hour TTL pref `PREF_LAST_UPDATED_TRANSLATIONS`, rewritten wholesale on each successful fetch, deleted on write failure.
- **Metadata DB**: SQLDelight `translations.db` via `AndroidSqliteDriver` (`common/translation/src/main/kotlin/com/quran/mobile/translation/di/TranslationDataModule.kt`), table `translations(id INTEGER PRIMARY KEY, name, translator, translatorForeign, filename NOT NULL, url NOT NULL, languageCode, version DEFAULT 0, minimumRequiredVersion DEFAULT 0, userDisplayOrder DEFAULT -1)`; named queries `all`, `update` (`REPLACE INTO`), `greatestDisplayOrder`, `deleteById`, `deleteByFileName`. Migrations `1.sqm`–`4.sqm` run under `verifyMigrations.set(true)`; v4 recreates the table to add `userDisplayOrder` ("updated in v3.0.2").
- **Content DBs**: one SQLite file per translation/tafsir in `QuranFileUtils.getQuranDatabaseDirectory()` (under the app-internal base dir), containing `verses(sura, ayah, text, …)`, `arabic_text`, `share_text`, and a `properties(property, value)` table storing `schema_version` and `text_version`. These are downloaded artifacts, not app assets — their internal version numbers are read at runtime instead of relying on SQLite `user_version`.
- **Preferences** (`util/QuranSettings.java`, keys in `data/Constants.kt`): `PREF_ACTIVE_TRANSLATIONS` (StringSet of filenames, stored in `perInstallationPrefs`, migrated from legacy singular `PREF_ACTIVE_TRANSLATION`), `PREF_LAST_UPDATED_TRANSLATIONS`, `PREF_HAVE_UPDATED_TRANSLATIONS`, `PREF_TRANSLATION_TEXT_SIZE`.
- **Download management**: `QuranDownloadService` handles resume (byte ranges onto `.partial`), zip extraction, disk-space pre-check, cancel, per-type notification ids on the progress channel, and in-memory success/failure caches so repeated intents don't re-download; the manager observes results only while alive via `DefaultDownloadReceiver` registered in `onCreate`-time setup and unregistered in `onStop`.

## 5. Why it is built this way ON THIS PLATFORM

- **Foreground service for downloads.** A translation DB can be many MBs and Android will kill silent background work, so transfers run in `QuranDownloadService`, which calls `startForeground()` before enqueueing (`onStartCommand`), holds a `WifiLock`, posts progress notifications, and survives the activity being backgrounded. The activity learns outcomes through `LocalBroadcastManager` + `DefaultDownloadReceiver` and re-registers/unregisters across lifecycle transitions — a deliberate decoupling of UI lifetime from transfer lifetime. On platforms with system-managed background transfer APIs you'd delegate resumability and retry to the OS instead of owning it in-process.
- **One file per translation.** Independent SQLite files make install/remove/upgrade atomic (`File.renameTo`/`delete`), let `DatabaseHandler` open only what's being read (bounded memory, static handler map), keep the APK small (store-policy friendly: no bundled megabytes of text), and allow the server to ship schema variants of the same tafsir. It also means corruption is quarantined per file — `mergeWithServerTranslations` deletes just the bad file and the row disappears thanks to the `hasTranslation` filter.
- **Schema negotiation without app releases.** `minimumRequiredVersion`/`schema_version`/`text_version` form a handshake between CDN data and installed app: the server can republish a tafsir targeting schema v5 and older clients simply see "update available" but cannot parse it until upgraded (`MINIMUM_PROCESSING_VERSION` gates footnote/ayah-reference parsing). This lets translation data evolve independently of Play release cadence.
- **Cache-first reactive catalog.** Merging the cached list ahead of the network list gives instant paint on slow connections while still refreshing within the same collection; the 1-hour TTL prevents hammering the endpoint on every app start (`checkForUpdates()` is called once per session from `QuranActivity.updateTranslationsListAsNeeded()`). Offline-first by construction: everything except the catalog refresh works with zero connectivity.
- **Hybrid threading/DI eras coexist.** The presenter uses coroutine Flows on `Dispatchers.IO` and sqldelight's reactive queries, while the adapter↔activity channel is still RxJava3 `UnicastSubject`s and the download service is callback/intent based — incremental modernization around a stable service core. DI is Metro (`dev.zacsweers.metro`), not Dagger as older write-ups claim.
- **Scoped storage.** Databases live under the app-internal directory, avoiding permission prompts and SAF complexity; that's also why deletion is a plain `File.delete()` and why storage-migration features elsewhere in the app operate on whole directories.

## 6. Edge cases & offline behavior

- **Interrupted downloads**: resumed with HTTP `Range` requests against a `.partial` sibling; zipped payloads double-check space for archive + extracted size; cancellation flags mid-stream.
- **Failed upgrades**: existing file renamed to `.old` before overwrite and restored on failure, so users never lose a working tafsir; on success the backup is deleted.
- **Duplicate-row bug around schema v5**: old and new ibn-kathir-style files can share a filename but change id, so `updateItem`/`mergeWithServerTranslations` explicitly `deleteTranslationByFileName` before writing when `minimumVersion >= 5` (commented workaround in `TranslationManagerPresenter.kt`).
- **Corrupt/truncated files**: detected as "server says exists, local version unknown" (`exists && !item.exists()`), triggering `dbFile.delete()` so the next sync treats it as never-downloaded.
- **Bad upstream data**: `ensureProperTranslations` pads missing verse records (e.g. ibn kathir gaps in suras 5, 17, 87) so multi-translation alignment never shifts rows; `combineAyahData` substitutes empty text when one translation lacks an ayah, keeping columns aligned.
- **Empty/degenerate selections**: if all active translations were unchecked or point at deleted files, `getVerses` falls back to every downloaded translation rather than showing nothing; `AyahTranslationFragment` shows an explicit empty state with a "get translations" button wired to the manager.
- **Legacy upgrades**: rows without `languageCode` are rewritten during merge; the singular `PREF_ACTIVE_TRANSLATION` string is folded into the new StringSet on read; SQLDelight migrations recreate the metadata table preserving ids.
- **Network failure UX**: catalog errors surface as a Snackbar and leave the cached list usable; download errors arrive as notifier intents with error codes and the Android notification shade as the durable record; the service suppresses duplicate error notifications via `recentlyFailedDownloads` unless `EXTRA_REPEAT_LAST_ERROR` is set.
- **Locale/RTL & accessibility**: localized translator names (`translatorForeign`) take precedence for display and `resolveTranslatorName()` degrades gracefully to filename; Arabic content uses a dedicated `ArabicSearcher` with highlighting markup; the adapter nulls `contentDescription` on decorative icons and uses `itemView.isActivated` for ActionMode selection state. Edge-to-edge insets (system bars + display cutout) are applied manually to root padding and list bottom padding.
