# Quran for Android - Feature Design Analysis

> Index for the feature-analysis set on **github.com/quran/quran_android**, cloned @ `main` on **2026-08-23**. Each linked doc below is a self-contained deep dive citing repo-relative paths (`app/src/main/java/com/quran/labs/androidquran/...`, `common/*`, `feature/*`, `pages/*`) read directly from that clone.

## 1. Intro

Quran for Android (`com.quran.labs.androidquran`) is a long-lived, GPL3, multi-module Kotlin reader whose central design decision is made before any code runs: **mushaf pages are pre-rendered images, never laid-out text**. Everything else in the app — first-run downloads, width-bucketed image packs, per-width glyph-coordinate databases, SD-card/scoped-storage migration, missing-page repair, an alternate Compose line-by-line page type — exists to support or work around that decision. The app pairs this with offline-first persistence for translations, tafsir, bookmarks, and audio, cloud sync against quran.com accounts, Android Auto media browsing, and a plugin-style module system.

Scope of this set: **20 feature deep-dives** covering the reading core (image pager, translation mode, dual/split layout, night mode), navigation (jump dialog, resume, index tabs), content management (translation manager, downloads, first-run setup/repair, mushaf variants), interaction (ayah selection/share/copy, search), user data (bookmarks, tags, reading bookmarks, backup import/export, cloud sync), audio (playback, Android Auto), and platform surface (settings/accessibility, home-screen widgets). Analysis was performed on the codebase's own terms — Android platform constraints, memory budgets, and the project's typography-fidelity philosophy — with discrepancies between prior assumptions and the actual code called out inside each dive.

## 2. Architecture overview

**Module layout.** The root Gradle project splits into:

- **`:app`** — the UI shell and everything View-era: `PagerActivity`/`QuranActivity`, the two foreground Services (`service/QuranDownloadService.kt`, `service/AudioService.kt`), WorkManager workers, classic RxJava3 MVP presenters under `presenter/*`, raw-SQLite adapters under `database/*`, and `data/Constants.kt` enumerating every preference key.
- **`:common/*` (~20 libraries)** — reusable, app-independent domains: `analytics`, `audio` (incl. app-scoped `AudioStatusRepository`, `QariDownloadInfoManager` inventory cache), `bookmark` (SQLDelight declarations + DAO impls + legacy migration + import normalization), `data` (dao interfaces, `QuranInfo` math tables), `di`, `download` (`DownloadInfoStreams` SharedFlow + `Downloader` interface), `drawing`, `linebyline:data|ui`, `mapper`, `networking` (OkHttp BOM 5.x + dnsjava DoH in `NetworkModule`), `pages`, `preference`, `reading` (`ReadingEventPresenter` selection state), `recitation` (interface only), `search` (`Searcher` seam: FTS/LIKE `DefaultSearcher` + `ArabicSearcher`), `toolbar` (`AyahToolBar` + presenter), `translation`, `upgrade`, `ui:core`.
- **`:feature/*`** — pluggable units that may not depend on `:app`: `audio`, `audiobar`, `ayahbookmark`, `downloadmanager`, `qarilist`, `recitation`, `sync`, `linebyline`, `autoquran`, and analytics `noop`/`firebase-analytics` alternatives.
- **`:pages`** — `madani` page-image provider plus `pages:data:madani` / `pages:data:warsh` metadata sources; each contributes a `PageProvider` into an injected `Map<String, PageProvider>` keyed by mushaf type.

**DI.** Metro (`dev.zacsweers.metro`, pinned 1.4.2 in `gradle/libs.versions.toml`) — the Dagger migration is complete; no Dagger bindings remain. Root graph: `di/component/application/ApplicationComponent.kt` (`@SingleIn(AppScope)`), with `ActivityComponent` → `QuranActivityComponent` / `PagerActivityComponent` → per-visible-page `QuranPageComponent` (`@GraphExtension`, `@QuranPageScope`, built via `generate(pages: IntArray)`). Feature modules contribute through injected provider sets rather than hard dependencies: `ExtraScreenProvider` (menu items in `QuranActivity.onCreateOptionsMenu`), `ExtraPreferencesProvider` (rows in `QuranSettingsFragment`, sorted by `order`), `AyahActionFragmentProvider` (panels assembled in `ui/helpers/SlidingPagerAdapter.kt`), the `Map<String, PageProvider>` multibinding, `RecitationPresenter`, and `AnalyticsModule`; `@ContributesBinding` wires implementations like `DownloadStarter` and `QuranSyncRepositoryProvider`.

**State & threading.** Deliberately hybrid. Legacy screens are MVP presenters driven by RxJava3 (`CompositeDisposable`, `Schedulers.io` → `AndroidSchedulers.mainThread`): index tabs, search, translation flows, download receiver, backup import/export. Newer leaf features are Compose + StateFlow/MVI, some produced by running presenters under Molecule (`AyahBookmarkPresenter.present()`) instead of ViewModels. The bridge between eras is app/activity-scoped state holders: `ReadingEventPresenter.ayahSelectionFlow: StateFlow<AyahSelection>` (consumed by `AyahTrackerPresenter`, `AyahToolBarPresenter`, audio follow-highlighting, and Compose panels simultaneously), `AudioStatusRepository` (commands still travel as `startService` intents carrying a Parcelable `AudioRequest`; state flows back out through the repository), `LatestPageTracker`, and `QariDownloadInfoManager`. Threading follows the same split: Rx on legacy paths, coroutines (`Dispatchers.IO/Main`, AppScope scope) elsewhere, and sync owns a `SupervisorJob` scope in `feature/sync/QuranSyncManager.kt`.

**Data layers.** Four coexisting persistence regimes, each chosen for its domain:

1. **SQLDelight 2.x** declarations in `common/bookmark/src/main/sqldelight` (`Bookmark.sq`, `Tag.sq`, `BookmarkTag.sq`, `LastPage.sq`) behind DAOs (`BookmarksDaoImpl`, `RecentPagesDaoImpl`, `ReadingBookmarksDaoImpl`) exposed via `common/data/dao` interfaces — now largely *migration source*, since live bookmark/read-state persistence was swapped onto the quran.com Kotlin-multiplatform database (below).
2. **Legacy raw SQLite** in `app/.../database`: `AyahInfoDatabaseHandler` (per-width `glyphs` tables driving hit-testing and highlights), `SuraTimingDatabaseHandler` (gapless audio timings), `DatabaseHandler` (the downloadable Arabic search DB and each downloaded translation file, cached per filename). Each downloaded translation is its own SQLite file with a `properties(property,value)` table carrying `schema_version`/`text_version`.
3. **Kotlin-multiplatform shared library**: `com.quran:mobile-sync` (`com.quran.shared.auth/.persistence/.pipeline`) owns collections/bookmarks/highlights/reading sessions and all merge protocol; the app reaches it only through DAO interfaces bound at the `MobileSyncRepositoryProvider` seam by `feature/sync`.
4. **SharedPreferences** wrapped by `QuranSettings`/`SettingsImpl` behind the `Settings` dao — including a `StringSet` of active translations and per-installation education flags.

Networking is minimal and mostly CDN-shaped: page images/audio/coordinate zips from the project's own hosts, a normalized translation catalog JSON (hourly TTL cache), `quranapp.com` for share links, and quran.com infrastructure (ktor + OIDC) exclusively inside the sync feature.

## 3. Cross-cutting design patterns

| Pattern | Where seen | Significance |
|---|---|---|
| Pre-rendered images + geometry databases as the substrate | Mushaf reading (`ImageAyahUtils` hit-testing over `ayahinfo{_width}.db` `glyphs` rows), search (separate downloadable Arabic-text DB because images carry no text), share/copy (`ArabicDatabaseUtils.getVerses`), bookmark/audio highlight rendering, dual-page mode | One decision radiates outward: width-bucketed image packs, first-run downloads, `.version` patch zips, scoped-storage migration, `MissingPageDownloadWorker` repair, and `ALPHA_8` bitmap memory discipline are all consequences of "pages are pixels, not text." |
| Provider-set plugin architecture (Metro multibindings) | Settings rows (`Set<ExtraPreferencesProvider>` sorted by `order`), menu items (`ExtraScreenProvider`), ayah panels (`AyahActionFragmentProvider` in `SlidingPagerAdapter`), mushaf types (`Map<String, PageProvider>`), recitation/analytics bindings | `:feature` modules extend menus, settings, panels, and page types with zero app-code edits and no reverse dependency; adding a mushaf or analytics backend is a binding container, not a refactor. |
| Shared StateFlow instead of ViewModel-owned state | `ReadingEventPresenter.ayahSelectionFlow` (tracker + toolbar + audio highlight + Compose), `AudioStatusRepository` (service ↔ notification/media button/UI), `LatestPageTracker` (resume), `BookmarksDao` flows (reactive bookmark repaints, widget updates) | An activity-scoped event/state bus decouples View-era MVP, androidx Views, and new Compose surfaces from one source of truth, enabling incremental Compose adoption without rewriting the shell. |
| Two UI generations coexisting deliberately | Bookmarks tab (MVP + Rx undo timer) vs ayah bookmark sheet (Compose + Molecule MVI); `TranslationsAdapter` Rx click channel vs coroutine `getVerses()` engine; `AudioService` (legacy started service + `MediaSessionCompat`) vs Compose `AudioBar` | Modernization is confined to leaf modules that plug into the View-based shell through injection seams, so neither generation blocks shipping. |
| Offline-first with graceful degradation | `pendingHighlightInfo` until coordinates arrive; tap-to-retry page error overlay; "Get Translations"/"Get Arabic Search Database" prompts on null cursors; silent repair workers always returning `Result.success()`; downloader resuming `.part` files with HTTP Range and promoting fallback URLs | Every layer assumes absent data is normal: failures degrade to prompts, retries, or parked state rather than dead ends, and destructive operations back up first (`.old` restore for failed translation upgrades). |
| Feature enablement by configuration, not flavor split | `RecitationPresenterImpl.isRecitationEnabled() == false` (hides "recite from here"), blank `oauth.properties` client id → hidden Account row, disabled pull-to-sync, finished sync activity; Warsh binding container living outside the OSS repo | Closed-source or unconfigured capabilities ship as inert pluggable seams in the open build; the same codebase serves both distributions. |
| Migration-not-rewrite persistence | `@Deprecated BookmarksDBAdapter` + `LegacyBookmarksMigrator` (pref-gated, Mutex-guarded, never deletes source rows) funneling into `com.quran:mobile-sync`; `last_pages` SQLDelight table seeded from a legacy preference; widget list provider self-migrating in `onDataSetChanged` | Old schemas stay read-only forever as migration inputs; new systems take over at DAO seams so callers never see two worlds. |
| Foreground Service for interactivity, WorkManager for maintenance | `QuranDownloadService` (serialized HandlerThread, WifiLock, zip extraction, resume, progress notifications + LocalBroadcast replay via cached `lastSentIntent`) vs `AudioUpdateWorker` (7-day MD5-verified re-download) and `PartialPageCheckingWorker` → `MissingPageDownloadWorker` unique-name chain, both injected through `QuranWorkerFactory` | User-visible transfers need progress and control (foreground); hygiene tasks need survival across process death (WorkManager) — and repair workers fail silently by design. |
| Behavior encoded as data, negotiated at runtime | Gapped vs gapless reciters expressed as `AudioPathInfo.urlFormat` shapes (+ optional timing DB); translation catalog `minimumVersion`/`schema_version` gating (`TranslationUtil.MINIMUM_PROCESSING_VERSION = 5`); version-tolerant backup JSON with `LegacyBackupStringAdapter` and epoch-seconds/millis auto-detection | Content and formats evolve independently of Play release cadence; the app adapts to what it finds on disk and on the server instead of hard-coding code paths. |
| Optimistic UI with bounded undo windows | 4 s delete-undo in bookmarks (Rx timer + optimistic list prediction), `PendingMove` page-star machine force-confirmed on `unbind()`, 3 s `LastPlaceWarningBanner` before dropping a bookmark's last location, 5–9 s movable-bookmark undo snackbar | Destructive writes are deferred a few seconds behind reversible affordances rather than soft-delete columns, with lifecycle hooks guaranteeing pending intents land before teardown. |

## 5. Notable observations

### Clever tricks

- **Memory discipline as architecture.** Full-page bitmaps decode as `ALPHA_8` (1 byte/pixel), `NonRestoringViewPager` (a vendored ViewPager fork) skips hardware-layer snapshots, `window.setBackgroundDrawable(null)` kills overdraw, and `QuranPageLoader.loadImage` catches `OutOfMemoryError` and retries at `tabletWidthParam`. Bitmap ownership is per-fragment and freed in `cleanup()`.
- **Hit-testing without text.** Taps convert screen coordinates through `HighlightingImageView.imageMatrix` onto `"sura:ayah" -> List<AyahBounds>` rows, with a closest-line-then-closest-x fallback in `ImageAyahUtils.getAyahFromCoordinates` — RTL-correct for free because it works purely on stored rectangles. Word-level targets come from a nullable `glyph_type` column.
- **Two-pass highlight drawing.** `HighlightingImageView.onDraw` runs `HighlightsDrawer` twice: COLOR/HIDE modes mutate the bitmap itself before `super.onDraw` (PorterDuff SRC_ATOP recoloring, clip-out rects), then HIGHLIGHT/BACKGROUND/UNDERLINE draw matrix-mapped rects after; paints come from a static `PaintCache` shared across pages, and audio highlights animate between ayahs via `TransitionAyahHighlight` + `ValueAnimator` interpolating normalized bounds over 500 ms.
- **Crash-safe download resume, hand-rolled.** OkHttp streams to `<file>.part` (flushed per 8 KB chunk) then renames; a pre-existing `.part` becomes an HTTP Range header. Retries swap to `UrlUtil.fallbackUrl` after first failure and permanently promote it via static `fallbackByDefault`.
- **Replay-able download progress.** The `DefaultDownloadReceiver` ecosystem caches `lastSentIntent` so an `ACTION_RECONNECT` broadcast can replay exact state to a UI that re-attaches mid-download.
- **Silent-repair guardrail.** `MISSING_PAGE_LIMIT = 50` makes `MissingPageDownloadWorker` do nothing when too many pages are absent — protecting against systematically wrong directories triggering thousands of one-off requests — and every worker returns `Result.success()` so failures stay invisible.
- **Never-blank translation pages.** `BaseTranslationPresenter.getVerses` pads missing ayat with blanks (documented ibn Kathir gaps), tolerates per-translation failure, and falls back to *all* installed translations when the user's active set resolves to nothing.
- **Footnote span safety.** `[[...]]` footnote ranges are folded in descending order so earlier indices stay valid while superscript spans are inserted.
- **Auto reliability contract.** Every `MediaLibrarySession` callback wraps work in `runCatching` and always completes its `SettableFuture` ("failing to respond leaves Android Auto on an infinite spinner"); artwork is generated locally as deterministic PNGs by `QariArtworkContentProvider` behind an LruCache and bounded pool.
- **Foldable-aware book logic.** Dual mode treats an open vertically-held foldable as a book even though Android reports portrait, and `isQuranOnRight = (pageNumber + quranInfo.skip) % 2 == 1` keeps odd/even sides correct despite skipped front matter.

### Divergences between similar features

- **Two bookmark systems, different invariants.** Ayah bookmarks allow membership in many collections (deleting a tag header merely untags members; they resurface under "Not tagged"), while the reading bookmark is *singular by design* — saving moves it, and the sheet enforces "keep in at least one place" with a 3 s warning banner instead of applying.
- **Search routes by script, not by index.** Arabic queries hit only the mushaf DB (Arabic tafaseer always skipped as noise); Latin queries try each non-Arabic translation DB in order until one hits — two very different strategies behind one `Searcher` seam.
- **Jump dialog vs Juz tab.** Contrary to common assumption, `JumpFragment` has *no juz field* (page + sura-autocomplete/ayah only); juz navigation lives in the separate `JuzListFragment` tab with 240 quarter rows.
- **Same DAO, two dialects of reactivity.** The bookmarks tab caches results in an app-scoped presenter singleton with Rx timers; the ayah sheet produces state by running `present()` under Molecule into a StateFlow with assisted injection — no ViewModel anywhere.
- **Gapped vs gapless audio.** Per-verse files make verse-range/repeat trivial; gapless requires a polling `HandlerThread` mapping position→ayah with 150 ms hysteresis, an end-of-sura sentinel, and bundled basmalah resources papering over inconsistent sura openings.

### Engineering warnings

- **Known bug, acknowledged:** `isSpaceAvailable` measures the wrong volume (`Environment.getExternalStorageDirectory()`) before large downloads — flagged with a TODO in the service.
- **Accessibility gaps:** audio-bar Compose icons pass empty `contentDescription` strings (unlabeled for TalkBack); mushaf interactions are pure touch geometry with no accessibility semantics beyond haptics and long-press toasts; speed control is hidden below API 23.
- **Blocking legacy network call:** the quranapp.com link shortener uses a plain `HttpURLConnection` POST over `http://` on `Schedulers.io`, with a literal TODO to migrate to OkHttp.
- **Client-side scan cost:** Arabic full-text search filters the entire table in Kotlin after matching (`getLimit` returns empty), so large queries scan everything.
- **OSS build is thinner than it looks:** only 3 qaris ship via `MadaniPageProvider` despite the multi-qari picker UI; at `main` there are *no* qaloon/naskh product flavors (`app/build.gradle.kts` creates only `madani`, no flavor dimension) and nothing binds `"warsh"` — Warsh libraries exist but their binding container is outside the repo.
- **Sync gaps:** highlight sync plumbing has no UI consumers yet, and there is no periodic sync worker — cadence lives entirely inside the mobile-sync engine.
- **Half-migrated media stack:** Media3 is used purely as the player engine; session and notification plumbing remain androidx.media `MediaSessionCompat`.
