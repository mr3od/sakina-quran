# How the RN/Expo Community Verifies Upgrades — iOS, Android, Web

> **As of 2026-08-24.** Every claim below was read directly from primary sources on this date: official Expo/React Native docs and changelogs, GitHub Actions YAML files in the named repositories (fetched raw), GitHub issues/PRs, and first-party vendor documentation for Maestro, Detox, Firebase, AWS, Sentry, Apple, and Google Play. Nothing is cited from search snippets or third-party summaries. Where a coverage class has no real practice to find, that is stated explicitly.

---

## Headline summary

| Approach | Platforms covered | Gate criteria | Cadence | Representative adopters |
|---|---|---|---|---|
| Dependency alignment (`expo install --fix` + `expo-doctor` + changelog review) | All three, statically | Tool exit codes + human changelog reading | Every upgrade PR | Prescribed by [Expo](https://docs.expo.dev/workflow/upgrading-expo-sdk-walkthrough/) and echoed by [RN docs](https://reactnative.dev/docs/upgrading) |
| Manual QA matrix with screenshots | iOS native, Android native, web ×2–3 browsers | Human sign-off per platform cell; screenshots/videos required as PR evidence | Upgrade PRs and release PRs | [Expensify](https://github.com/Expensify/App/pull/51475) |
| Scheduled device E2E (Maestro CLI) on GitHub-hosted sim/emulator | iOS simulator + Android emulator | Maestro suite exit status; artifacts (logs, diagnostics) uploaded `if: always()`; Slack alert on failure only | Nightly cron | [Bluesky](https://github.com/bluesky-social/social-app/blob/main/.github/workflows/nightly-e2e.yml) |
| Dispatch-gated Detox **and** Maestro suites, label-overridable | iOS simulator + Android emulator | Commit statuses via TSIO reporting; `E2E/Override` label forces green without running | Per-PR on demand (bot-dispatched), plus release runs recorded in Zephyr Scale | [Mattermost](https://github.com/mattermost/mattermost-mobile/blob/main/.github/workflows/e2e-detox-pr.yml) |
| Shard-based Maestro E2E behind an environment approval, required check at the end | iOS + Android emulators/simulators | Required check `e2e-result`; shard preflight skips shards untouched by the diff | Per-PR (gated), AVD caches seeded from develop | [Rocket.Chat](https://github.com/RocketChat/Rocket.Chat.ReactNative/blob/develop/.github/README.md) |
| Production soak tied to payment/deploy hold | All platforms in production | Bounty paid only after production deploy + due date; deploys held while "QA is ongoing" | Per release cycle | [Expensify](https://github.com/Expensify/App/issues/75120) |
| Store-side percentage rollouts + crash telemetry thresholds | Production users, per-platform | Halt/pause on bad signals (crash-free %, velocity alerts) | Post-release, continuous | Google Play / App Store / Sentry / Crashlytics (see §4) |

The pattern across all of it: **cheap static checks run every PR; real-device verification is deliberately expensive and therefore scheduled or gated; production telemetry is the final gate.**

## 1. Official guidance

Expo's own [upgrade walkthrough](https://docs.expo.dev/workflow/upgrading-expo-sdk-walkthrough/) prescribes almost no runtime verification: install `expo@^<next>`, "Upgrade all dependencies to match the installed SDK version", then "run `expo-doctor` command to check for common problems", plus reading the SDK changelog's "Upgrading your app" section. There is no testing checklist — no mention of testing on iOS, Android, or web after upgrading, no dev-client rebuild step, no manual QA list. The closest thing to runtime validation is regenerating native projects (`npx expo prebuild`, `npx pod-install`) and building.

The [SDK 57 changelog](https://expo.dev/changelog/sdk-57) adds two concrete verification steps: "Check for any possible known issues with Expo Doctor" after `npx expo install expo@^57.0.0 --fix`, and for dev-client users, "Create a new development build after upgrading." For CNG projects it says to delete stale `android`/`ios` directories; for bare projects it points at `npx pod-install` and the Native project upgrade helper. The [SDK 56 changelog](https://expo.dev/changelog/sdk-56) enumerates the breaking changes you are expected to verify against your own app (async `copy()`/`move()` in expo-file-system, `expo/fetch` becoming `globalThis.fetch`, the React Navigation fork with its codemod `npx expo-codemod sdk-56-expo-router-react-navigation-replace`, minimum Xcode 26.4 / iOS 16.4) and thanks beta testers retrospectively.

That beta program is Expo's actual community-verification mechanism. The [SDK 56 beta announcement](https://expo.dev/changelog/sdk-56-beta) states "the SDK 56 beta period begins today and will last approximately two weeks", asks developers to run `npx expo install expo@next --fix`, build natively (EAS Build or `npx expo prebuild --clean` then `npm run ios` / `npm run android`), and "test out the SDK and ensure that the new release does not introduce any regressions for their particular systems" — reporting via GitHub issues with a minimal repro, flagged as SDK 56 beta so they get prioritized, with Discord office hours during the window. Expo's [release-statuses doc](https://docs.expo.dev/more/release-statuses/) formalizes this: beta means "feature-complete and undergoing final validation before a stable release". A first-party [expo/fyi troubleshooting doc](https://github.com/expo/fyi/blob/main/troubleshooting-sdk-upgrades.md) adds process hygiene: use development builds because "Expo Go is limited in how it can simulate the functionality of your standalone app" and it "will give you a good baseline for comparing between old and new versions"; start on a separate git branch and merge only "once you've confirmed everything is working"; upgrade one SDK version at a time; clear Metro cache with `npx expo start -c`; and reduce bugs to a fresh `create-expo-app` reproduction before filing.

On the React Native side, the [official upgrading doc](https://reactnative.dev/docs/upgrading) makes diff review the primary verification tool: pick versions in the Upgrade Helper ([react-native-community.github.io/upgrade-helper](https://react-native-community.github.io/upgrade-helper)), click "Show me how to upgrade!", apply the diff file-by-file ("If there aren't other changes then you only need to rebuild the project"), and for cache-related weirdness install `react-native-clean-project`. It also relays Expo's advice that "upgrading SDK versions incrementally, one at a time... will help you pinpoint breakages".

React Native core validates its own releases through a volunteer Release Crew documented in the [react-native-releases working group](https://github.com/reactwg/react-native-releases). The [release-testing guide](https://github.com/reactwg/react-native-releases/blob/main/docs/guide-release-testing.md) is the most concrete artifact: a four-cell matrix — RNTester×iOS, RNTester×Android, RNTestProject (community template)×iOS, RNTestProject×Android — executed manually on macOS ("Currently, this flow can only be done on macOS machines") using `npx rn-release-automator@latest test-release --version <version>`, which verifies CI prebuilds and prints the four matrix commands. Manual testing "only requires manual testing for RC0, RC1, RC4, and stable". Pass/fail is human judgment recorded as a Test Report issue cross-checked against a Google Sheets test-case list, prioritizing debugging, the developer menu, TextInput, Lists, and keyboard interactions — because Meta's internal e2e tests "don't capture interactive capabilities or developer experience workflows". The [RC guide](https://github.com/reactwg/react-native-releases/blob/main/docs/guide-release-candidate.md) automates branch cutting and nightlies ("Some partners are integrating with the nightlies jobs") but specifies no minimum RC soak time and no numeric promotion criteria.

**Verdict:** official guidance is strong on dependency alignment and weak on everything else — it gets you to a state where the *build* should work and leaves behavioral verification to a small human-run matrix (RN's own release program included). It is good for catching version-skew errors cheaply; it breaks down exactly where breakage is behavioral (layout, gestures, native modules), which is why every large app below invents its own gate.

## 2. Large OSS RN apps' actual practice

**Bluesky** runs device E2E nightly, not per-PR. Its [`nightly-e2e.yml`](https://github.com/bluesky-social/social-app/blob/main/.github/workflows/nightly-e2e.yml) fires on `cron: "0 4 * * *"`, runs iOS on `macos-26-xlarge` booting an iPhone 17 simulator (iOS 26.5) and Android on a repository-managed `Linux-x64-32core` runner creating an AVD from `system-images;android-34;google_apis;x86_64` on a `pixel_6` profile — API 34 chosen over 35 for headless CI stability, with `-gpu swiftshader_indirect -feature -Vulkan` to dodge silent qemu crashes. Maestro CLI is pinned (`MAESTRO_VERSION: "2.6.1"`), downloaded with a SHA256 checksum, and run locally — "Maestro Cloud is not used". Builds come from a shared reusable EAS action with `profile: e2e`. Artifacts upload with `if: always()` and `retention-days: 7`, and a report job posts one aggregated Slack message only on failures. [`docs/testing.md`](https://github.com/bluesky-social/social-app/blob/main/docs/testing.md) documents the local equivalent (mock server on port 3000 via `adb reverse`, Metro on 8081) and Flashlight performance measurement driven by a Maestro scroll flow. The move to Maestro was explicit: [PR #3983](https://github.com/bluesky-social/social-app/pull/3983) removed Detox entirely in May 2024 because "it's generally faster than detox, easier to run, easier to write tests for, and importantly it works (Detox had completely broken)".

**Mattermost** keeps both frameworks and gates them behind dispatch. [`e2e-detox-pr.yml`](https://github.com/mattermost/mattermost-mobile/blob/main/.github/workflows/e2e-detox-pr.yml) is workflow_dispatch-only, invoked by their Matterwick bot with inputs for commit SHA, platform, and five test-server URLs; a policy job checks for an `E2E/Override` label and, if present, "skips all testing when set, posting success statuses instead so merges aren't blocked". iOS simulator apps are built via Fastlane (`bundle exec fastlane ios simulator`), Android produces both a Detox debug APK and a Maestro release APK, with fingerprint-scoped S3 build caching (`DETOX_AWS_S3_BUCKET: "mattermost-detox-report"`). The nested [`e2e-maestro-template.yml`](https://github.com/mattermost/mattermost-mobile/blob/main/.github/workflows/e2e-maestro-template.yml) pins device targets ("Keep Maestro device targets identical to detox/.detoxrc.json": iPhone 17 Pro / iOS 26.2), reports pass counts as GitHub commit statuses via TSIO, records results into Zephyr Scale for release/main runs, and emits structured outputs (PASSES/FAILURES/PERCENTAGE). Their [`compatibility-matrix-testing.yml`](https://github.com/mattermost/mattermost-mobile/blob/main/.github/workflows/compatibility-matrix-testing.yml) shows release-time thinking: each app build (iOS, Android Detox, Android Maestro) happens once and is reused "across every server-version leg of the matrix".

**Rocket.Chat** wires E2E into PR CI but behind gates. Its [.github/README.md call graph](https://github.com/RocketChat/Rocket.Chat.ReactNative/blob/develop/.github/README.md) maps `pull_request` → lint/tests → Android+iOS store builds → an `e2e-shards` preflight that narrows "to the sniffler-impacted shards, or skips the stage on a confident-zero diff" → parallel Maestro Android/iOS shards → a required check named `e2e-result`. The [`maestro-android.yml`](https://github.com/RocketChat/Rocket.Chat.ReactNative/blob/develop/.github/workflows/maestro-android.yml) shard template restores an Android SDK + emulator image cache (~1 GB) seeded only by pushes to develop, pins `android-emulator-runner@v2.37.0` by commit SHA with `-no-window -gpu swiftshader_indirect -noaudio -no-boot-anim -camera-back none -accel on` and a 900 s boot timeout, and even maintains a dedicated keyboard-enabled AVD for shard 14.

**Expensify** verifies upgrades with humans and money rather than devices-in-CI. RN bumps are tracked as umbrella issues with sub-issues per dependency — e.g. ["Upgrade RN to 0.83"](https://github.com/Expensify/App/issues/75120) closed "11 / 11 issues completed" with solution bullets "Upgrade React Native to latest version and update dependencies", "Audit and remove unnecessary patches", "Conduct thorough testing for stability." The gate that matters: the issue carries an "Awaiting Payment" label, described as "Auto-added when associated PR is deployed to production", plus a "[Due for payment 2026-03-31]" title — bounty payment is deferred until the upgrade has soaked in production. The [RN 0.76 upgrade PR](https://github.com/Expensify/App/pull/51475) shows the author checklist: "I ran the tests on all platforms & verified they passed on: Android: Native, Android: mWeb Chrome, iOS: Native, iOS: mWeb Safari, MacOS: Chrome / Safari, MacOS: Desktop"; "I included screenshots or videos for tests on all platforms"; offline testing; "Verify that no errors appear in the JS console" under both Tests and QA steps; and High Traffic account testing against staging/production. Deploys were held by their bot because "QA is ongoing", and maintainers noted "QA did full regression testing" pre-merge. Their [regression-test guide](https://github.com/Expensify/App/blob/main/contributingGuides/REGRESSION_TEST_BEST_PRACTICES.md) confirms the regression suite is manual steps executed by "a third party" QA firm, accumulated bug-fix by bug-fix.

**The rest of the cohort has left RN or dissolved**, which is itself a finding:

- **Zulip mobile**: README states plainly it is a "legacy, unsupported" codebase — "On 2025-06-07, we launched a new Zulip mobile app with Flutter" — with the repo pending archival. Its last [`ci.yml`](https://github.com/zulip/zulip-mobile/blob/main/.github/workflows/ci.yml) ran on `ubuntu-latest` with JDK 17 + Android SDK and `tools/test --all`: Android-only; iOS was never in PR CI.
- **WordPress gutenberg-mobile**: archived (verified via GitHub API); its tree retains `__device-tests__/` and `jest_ui.config.js` remnants of its device-test infrastructure, while editor development moved into WordPress/gutenberg.
- **Element X**: the RN prototype `element-hq/element-x-rn` no longer resolves (404 on fetch); Element X Android is Kotlin-dominant per the GitHub languages API — Element shipped native instead.
- **Bitwarden**: `bitwarden/mobile` is retired and was MAUI/Xamarin, not RN.
- **Home Assistant companion**: `home-assistant/android` is Kotlin and `home-assistant/iOS` is Swift — no RN practice exists to survey here.

**Verdict:** this class proves there is no community-standard upgrade gate — Bluesky trusts a nightly, Mattermost trusts bot-dispatched dual-framework suites, Rocket.Chat trusts shard preflight + a required check, Expensify trusts paid humans and production soak. Device E2E never runs naively per-PR anywhere sampled; cost control (caches, sharding, gating, build-once-reuse) is half the engineering effort. And the attrition list is a warning about extrapolating any single team's practice forward.

## 3. E2E/device tooling around upgrades

**Maestro** is the framework most adopters converged on. It describes itself as "the simplest and most effective framework for painless mobile and web UI automation using intuitive YAML flows", with CI scaling "by integrating with CI Platforms like GitHub Actions to run parallel tests" ([docs.maestro.dev](https://docs.maestro.dev/)). Screenshot support is first-class: `takeScreenshot` "saves a screenshot of the current screen as a PNG file" into "the `takeScreenshot` folder of the Flow's artifact bundle", supports `cropOn` element cropping, and pairs with a separate `assertScreenshot` command for visual comparison ([command reference](https://docs.maestro.dev/reference/commands-available/takescreenshot.md)). Notably, none of the three big adopters above use Maestro Cloud — all pin the CLI and run it on their own runners.

**Detox** remains in production at Mattermost. Its official CI guide ([19.x, marked "generally out of date"](https://wix.github.io/Detox/docs/19.x/guide/running-on-ci/)) prescribes testing a release build rather than debug (`detox build --configuration ios.sim.release`, then `detox test ... --cleanup` so Detox "exits cleanly by shutting down the simulator"); the CLI reference adds `--headless`, `--take-screenshots failing`, `--record-logs failing`, and `--retries`. Bluesky's abandonment of Detox entirely ([PR #3983](https://github.com/bluesky-social/social-app/pull/3983), quoted in §2) is the counterpoint.

**Cloud device farms have no visible RN-community practice in the sampled repos.** Firebase Test Lab offers "a cloud-based app testing infrastructure" exercising apps "on devices installed and running in a Google data center", with Robo tests that "do not require a pre-written test", instrumentation/XCTest/Game Loop types, and matrices of "devices, OS versions, locales, and screen orientations" ([overview](https://firebase.google.com/docs/test-lab)). AWS Device Farm offers "2,500+ devices", Appium/Espresso framework support, remote manual access, and generates "videos and logs" ([overview](https://aws.amazon.com/device-farm/)). Neither appears in any sampled RN app's CI; the community's center of gravity stayed on self-hosted-emulator GitHub Actions.

**Web (react-native-web)** verification is a thin export-and-smoke pattern. Margelo's [`react-native-mmkv` harness-web.yml](https://github.com/mrousavy/react-native-mmkv/blob/main/.github/workflows/harness-web.yml) runs on `ubuntu-latest` for PRs and pushes touching library source, path-filtered, driving a browser harness against the web bundle via Playwright Chromium. The recipe is minimal by design — export a web bundle, serve it, assert rendering with zero page errors in headless Chromium — which is the same shape as this repo's existing web-export check rather than a heavier framework investment.

**Verdict:** the tooling market has consolidated around Maestro-on-GitHub-runners for new investment, with Detox surviving as legacy mass at scale shops; visual regression exists (`assertScreenshot`, Detox screenshot flags) but nobody sampled enforces pixel-diff gates on upgrades. Device clouds are real products with essentially zero observable adoption in this cohort — the cost/benefit crossover evidently sits above OSS budgets.

## 4. Release-engineering safety nets

**Google Play staged rollouts**: "your update reaches only a percentage of your users, which you can increase over time"; percentages never rise automatically ("your app's staged rollout percentage won't increase automatically"); halting stops further distribution but "users who already received the app version in your staged rollout version will remain on that version" — there is no rollback, only halt-plus-forward-fix; Google's own monitoring advice is "closely monitor crash reports and user feedback" ([staged rollout help](https://support.google.com/googleplay/android-developer/answer/6346149)).

**Apple phased release**: updates roll out "gradually over 7 days" on the fixed schedule 1% → 2% → 5% → 10% → 20% → 50% → 100%, to "a random sample of users with automatic updates on eligible devices", while "apps and app updates in phased release can be manually downloaded from the App Store by anyone at any time"; you may "pause the release for up to 30 days" (resuming picks up where it left off), and "Release to All Users" ends it irreversibly for that version ([App Store Connect help](https://developer.apple.com/help/app-store-connect/update-your-app/release-a-version-update-in-phases/)).

**TestFlight** functions as the internal canary tier: up to 100 internal testers from App Store Connect roles with optional auto-distribution of new builds, up to 10,000 external testers once the first build passes review-for-TestFlight, crash reports delivered automatically, and testers able to submit marked-up screenshots — "Filter feedback by platform or OS version to get additional insight" ([Apple TestFlight](https://developer.apple.com/testflight/)). Bluesky operationalizes this in CI: [`build-submit-android.yml`](https://github.com/bluesky-social/social-app/blob/main/.github/workflows/build-submit-android.yml) exposes a `testflight-android` build profile and a boolean to auto-submit to Google Play.

**EAS Update rollouts** bring staged-delivery semantics to OTA: publish with `eas update --rollout-percentage=10` so "the update will only be available to 10% of your end users", adjust via `eas update:edit`, revert with `eas update:revert-update-rollout` (which "will republish the control update" or create "a rollback-to-embedded update" sending clients back to their embedded build), with branch-based equivalents via `eas channel:rollout` — one rollout per branch/channel at a time ([docs](https://docs.expo.dev/eas-update/rollouts/)). There is no built-in health dashboard gating this; monitoring is bolted on. Bluesky's [`bundle-deploy-eas-update.yml`](https://github.com/bluesky-social/social-app/blob/main/.github/workflows/bundle-deploy-eas-update.yml) shows the wiring: on push to main, a fingerprint baseline decides whether changes ship as OTA or force a native build ("A version bump forces a native build even if the fingerprint is unchanged").

**Crash telemetry closes the loop.** Sentry release health tracks sessions, "crash-free sessions" ("the percentage of sessions in the specified time range not ended by a crash"), crash-free users, and release adoption classified hourly "based on a threshold of 10%" into Adopted/Low Adoption/Replaced; teams configure alerts "when your crash free percentage for either sessions or users falls below a specific threshold" ([Sentry docs](https://docs.sentry.io/product/releases/health/)). Crashlytics velocity alerts default to firing "at 1% of sessions and 25 users" within a 30-minute window, opt-in, once per issue per app version ([Firebase docs](https://firebase.google.com/docs/crashlytics/velocity-alerts)). Bluesky ships with Sentry DSN and Bitdrift keys injected at CI build time (visible in `build-submit-android.yml`'s secrets).

**Feature-flag strategies during risky bumps:** I found no primary evidence in these repos of feature flags being used specifically to de-risk dependency upgrades — the sampled safety mechanisms are staged delivery (store percentages, OTA rollouts) and deploy-hold QA instead (Expensify's OSBotify holding deploys while "QA is ongoing"). Treat flag-based upgrade mitigation as plausible but UNVERIFIED practice in this cohort.

**Verdict:** the store-side nets are the only mechanisms with guaranteed reach — they catch what CI cannot see (real devices, real networks), at the price of exposing some users. Their shared blind spot: Play halts and Apple pauses stop *new* damage but cannot undo installed builds, so OTA (EAS Update rollback-to-embedded) is the only true reverse gear in the stack — and it applies only to JS-side regressions.

## 5. CI wiring patterns

Three cadence tiers recur across the sample:

1. **Every PR (cheap):** lint/typecheck/unit tests plus *buildability* proof. Expensify's per-PR set includes `lint.yml`, `typecheck.yml`, `test.yml`, and `buildAndroid.yml`/`buildIOS.yml`/`buildWeb.yml` (workflow names verified in the repo's `.github/workflows/` listing); Rocket.Chat runs lint+tests+store builds per PR. Nobody runs device tests unconditionally per PR.
2. **Gated or scheduled (expensive):** Bluesky's nightly cron on `macos-26-xlarge` + `Linux-x64-32core`; Mattermost's Matterwick-dispatched suites with label override; Rocket.Chat's environment-approval-gated shards whose preflight skips shards untouched by the diff.
3. **Release-time:** Mattermost tags runs `run_type: RELEASE`, records results in Zephyr Scale, and its compatibility-matrix workflow reuses one build across all server-version legs.

Cost-control techniques observed in the YAML: AVD + SDK package caches seeded by a long-lived branch and restored read-only elsewhere ("Saves each shard re-downloading ~1 GB" — Rocket.Chat); S3-cached Detox build artifacts scoped per branch so "PR builds can't leak across scopes" (Mattermost); concurrency groups with `cancel-in-progress` everywhere; pinned runner images and SHA-pinned actions. The economics push toward Linux: the android-emulator-runner README notes Ubuntu runners are "2-3 times faster than the macOS ones" and recommends them, requiring KVM enabled via udev rules on Linux ([README](https://github.com/reactivecircus/android-emulator-runner)); GitHub bills macOS runners at $0.062/min versus $0.006/min for 2-core Linux — roughly 10×, acknowledged qualitatively as "jobs that run on Windows and macOS runners hosted by GitHub cost more to run than jobs on Linux runners" ([GitHub billing docs](https://docs.github.com/en/billing/concepts/product-billing/github-actions)). EAS offers an alternative lane: EAS Workflows define `.eas/workflows/*.yml` pipelines triggered on GitHub push, and the deploy template "builds and submits a new production build when there are native changes" or "publishes an over-the-air update when a matching build already exists" — fingerprinting deciding which ([get-started](https://docs.expo.dev/eas/workflows/get-started/)).

Screenshot-artifact assertion is consistent where it exists: Bluesky uploads per-platform artifacts with `if: always()` and a `summarize-maestro.mjs` job converts them into a single Slack failure message; Maestro flows write PNGs into the artifact bundle's `takeScreenshot` folder; Detox captures with `--take-screenshots failing`. In all cases screenshots are *diagnostic evidence*, not enforced visual gates.

**Verdict:** the wiring pattern is mature and copyable — Linux-first, cached, gated, artifact-heavy. What the pattern does not give you is per-PR confidence on devices: everything device-shaped is either deferred to a nightly or requires a human to pull the lever, which is a deliberate trade of latency for runner spend.

## Application notes for sakina-quran

This repo already implements tier 1 well (jest/lint/prebuild/web-export per PR on ubuntu) and has an experimental deep-link-screenshot workflow spanning a GH-hosted Android emulator and iOS simulator — matching the community's shape. To align it: promote that workflow to a nightly cron plus manual dispatch rather than per-PR, pin the Maestro CLI version + checksum and the emulator image (API 34, not 35, per Bluesky's headless-instability finding), upload artifacts `if: always()`, and keep both legs' concurrency groups cancellable. Since the host is Linux with no local iOS sim, treat the iOS leg as the canary and lean on EAS Update rollout-percentage + rollback-to-embedded, plus a crash-free-session threshold (Sentry-style) as the post-upgrade gate. Add `npx expo-doctor@latest` to upgrade PRs specifically, mirroring the SDK 57 changelog prescription.
