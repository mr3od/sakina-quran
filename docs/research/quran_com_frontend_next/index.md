# Quran.com Web Frontend (quran/quran.com-frontend-next) - Feature Design Analysis

## 1. Intro

Quran.com's frontend is the web client behind one of the most-used Quran reading sites: a Next.js 14 app (React 18, TypeScript strict) styled with SCSS modules over Radix UI primitives, backed by the quran.com API v4. It serves the continuous-scroll reader, per-surah knowledge layers (tafsir, qiraat, hadith, related verses), audio recitation with repeat/radio modes, personal study tooling (bookmarks, collections, notes, pinned verses, goals/streaks), search with voice and a command bar, i18n across 18+ locales including RTL, seasonal campaigns, an embeddable ayah widget, and a Remotion-powered verse video/image maker.

Clone date: **2026-08-23**, shallow clone at `main`. Scope: 24 feature deep-dives under `features/*.md`, each grounded in code actually read (repo-relative paths cited throughout), plus this architecture index. Analysis was done on the codebase's own terms — a web platform where SEO drives discovery, there is no private device storage beyond localStorage/service-worker caches, and the URL is the sharing primitive. Where our starting assumptions disagreed with the code, the code won and the discrepancy is noted (e.g. the app uses the **Pages Router** (`src/pages/_app.tsx`), not the App Router).

## 2. Architecture overview

**Routing/rendering.** Nearly everything is statically generated. Routes under `src/pages/` are thin `getStaticProps` wrappers: they run `Promise.all` fetches against API v4 through `src/api.ts` (which wraps the quran.com API host with caching helpers like `fetchAndCacheWithFallback`), then return the responses *keyed by their request URL* so client-side SWR calls hit warm cache instead of the network. Chapter/verse routes use `fallback: 'blocking'` with roughly one-week ISR revalidation; errors return `notFound` with a short error-revalidation window and a Sentry-logged transaction name. Only genuinely dynamic surfaces (`embed/v1`, personal dashboards) use `getServerSideProps` or pure client hydration. CMS content (learning-plan marketing, changelog) comes from Sanity; course/lesson data does not — it flows through authenticated API v4 endpoints.

**State.** Redux Toolkit in `src/redux/store.ts` with redux-persist whitelisting ~23 slices into localStorage (`QURAN_READER_STYLES`, `READING_PREFERENCES`, `TRANSLATIONS`, `TAFSIRS`, `THEME`, `BOOKMARKS`, `READING_TRACKER`, `PINNED_VERSES`, ...). Three deliberate carve-outs shape the design: `AudioPlayerState` and `CommandBar` have their own persist configs (the latter blacklisting only ephemeral fields like `isExpanded`), and `notifications` is excluded entirely because Novu is always refetchable. Locale-dependent defaults live in `src/redux/defaultSettings/` and are applied by `defaultSettingsMiddleware`; version migrations sit in `src/redux/migrations.ts`; hydration completion is surfaced app-wide via `GlobalPersistGateHydrationListener`.

**Server sync of user state.** There is no local database. Guests keep small local records (redux-persist maps, a single validated `guestBookmark.ts` reading position); logged-in users' settings are canonicalized server-side. The chokepoint is `hooks/auth/usePersistPreferenceGroup.ts`: every settings change dispatches optimistically to Redux, then POSTs the whole group (`addOrUpdateUserPreference(key, value, group, mushafId)`) to the account backend, with `mushafId` recomputed from current `quranFont`+`mushafLines` because preference validity depends on mushaf layout. `src/utils/auth/preferencesMapper.ts` whitelists which slice fields belong to which `PreferenceGroup`; each slice merges its group back through `extraReducers` when `Provider.tsx` pulls preferences at login/boot. Guest bookmarks reconcile server-side via `syncUserLocalData`.

**Media and complex logic.** Playback is modeled as XState actors under `src/xstate/actors`: a single ~1150-line `audioPlayerMachine.ts` wrapped around one always-mounted hidden `<audio>` element, spawning child actors for repeat cycles (`repeatMachine`, `rangeCycleMachine`) and radio (`radioMachine`). Voice search uses the browser SpeechRecognition API behind a module-level singleton; the sole worker-like artifact is an AudioWorklet helper feeding the microphone visualizer.

**Background/platform services.** Offline support is exactly the next-pwa service worker configured by `pwa-runtime-config.js` (Workbox runtime caching; MP3 caching deliberately removed). Notifications delegate to `@novu/headless` with cookie-derived subscriber hashes. Video rendering leaves the browser entirely: Remotion previews locally, Remotion Lambda renders downloadable files. Observability/SEO are first-class: Sentry instrumentation, `logEvent` analytics calls, `NextSeoWrapper` per page, OG image generation in `src/lib/og`, sitemaps via `next-sitemap.js`, and standalone `/embed/*` iframe pages.

## 3. Cross-cutting design patterns

| Pattern | Where seen | Significance |
|---|---|---|
| Dual persistence: local-for-guests, server-canonical-for-users | `usePersistPreferenceGroup` (settings, themes, audio, translations), bookmarks/collections, notes, goals, calendar progress | One mental model covers nearly every feature: optimistic Redux first, best-effort server push second, undo/rollback toast on failure. Guests stay functional offline; accounts get cross-device continuity without any client-side merge logic except bookmark reconciliation. |
| SSR seeds SWR fallback by URL key | `src/pages/[chapterId]/index.tsx`, `[chapterId]/tafsirs/[tafsirId].tsx`, knowledge-layer routes, `/my-quran`, `/search`, `/radio` | `getStaticProps` returns fetched payloads keyed by exact request URLs, so client hooks hydrate from cache with zero refetch while page 2+ goes to network. Makes SEO-complete HTML and cheap clients the same mechanism rather than competing goals. |
| Optimistic mutation with explicit rollback | Pinned verses (local rollback + Retry toast + Sentry metadata), collection creation ('temp-'+timestamp ids swapped by `mutateAllData()`), preference sync (Undo toast), notes feed injection | Failures are user-visible and recoverable, never silently dropped; temporary identifiers are a first-class concept swapped atomically after server confirmation. |
| Derive, don't store | Word-by-word display mode (set membership of INLINE/TOOLTIP), `isUsingDefault` recomputed via `areArraysEqual`, revelation-order boolean reshuffling navigation, study mode emerging from collapsed-by-default content | Invalid configurations become unrepresentable and slices stay tiny (revelationOrder.ts is 51 lines). State that can be computed from other state is never persisted. |
| Enum-discriminated single surface | `QuranReaderDataType` (one reader for chapter/juz/hizb/rub/page/range routes), `ReadingPreference` selecting TranslationView vs ReadingView, `MyQuranTab`, `SettingsView` drawer swap | Route explosion is absorbed by one parameterized component; adding an entry point means adding a thin wrapper plus an enum value and a URL builder, not a new screen. |
| URL as state | Share/copy/embed all producing URLs, `/media` mirroring every setting into query params, `?tab=` shallow replaces, WBW locale pushed as `QueryParam.WBW_LOCALE`, `embed/[...slug]` redirect shim to canonical query form | On the web the URL is both persistence and sharing transport; shareable configurations need no backend storage and survive default evolution server-side. |
| Don't persist what you can refetch | notifications slice excluded from persist whitelist, CommandBar blacklists `isExpanded`, study mode deliberately ephemeral, radio sessions unpersisted (TODO) | Storage budget goes to expensive-to-recompute user choices; view/ephemeral state stays in memory or gets its own narrowed persist config. |
| Platform-workaround clusters with explanatory comments | Safari `onWaiting` simulation + drift tolerance + stall-vs-end guard in audioPlayerMachine; Firefox MP3 range-request fix in pwa-runtime-config.js; Chrome iOS base64 prefetch and Safari clipboard split-flow in MediaMaker | Browser quirks are handled at one chokepoint per problem domain and documented inline, so the reasoning survives the engineers. |
| Hydration-race discipline around redux-persist | `selectIsPersistGateHydrationComplete` gating SWR request keys, synchronous `'persist:root'` read as `preloadedState` for theme, hydration-gated guest-bookmark modal | The team treats async rehydration as a real failure mode with dedicated fixes rather than incidental flashes — the reader even documents the blank-verse bug in a long comment. |

## 5. Notable observations

**Clever tricks**

- **Sync-before-render theme hydration**: rather than fighting redux-persist's async REHYDRATE, `getStore()` synchronously parses localStorage key `'persist:root'` — with a deliberate double `JSON.parse` because redux-persist stringifies each slice individually — and passes the theme as `preloadedState` before first render. A comment warns that `PERSIST_KEY` must track `persistConfig.key`.
- **Infinity cannot travel through JSON**: repeat counts use `Infinity` at runtime but persist `-1` as a sentinel (`REPEAT_INFINITY` in `src/redux/types/AudioState.ts`, converters in `RepeatAudioModal.helpers.ts`) — the kind of serialization detail that silently corrupts naive ports.
- **Dedupe-by-arithmetic pagination**: the reader never has a load-more; `useDedupedFetchVerse.ts` computes `pageNumber = floor(verseIdx/perPage)` per rendered cell so Virtuoso's row-level hooks collapse into one network request per API page.
- **Radio as a mode, not a product**: stations are `(reciterId, surah)` pairs sampled with lodash, played through the normal audio pipeline with a random seek timestamp to fake liveness — no streaming infrastructure exists client-side.
- **Embed longevity by diffing**: `ayahWidget.ts` persists only overrides over server-computed defaults, so shipped iframes stay short and future default changes don't break old embeds.

**Divergences between similar features**

- Notes look local (a Redux slice exists) but the slice holds only `{isVisible}` — contrast with pins/bookmarks where local state is real and synced. Same platform constraint, opposite resolutions based on data sensitivity.
- Both radio and the reader track "where you are", but only the reader persists position; radio carries an explicit TODO to continue from last session.
- Knowledge-layer routes share one template yet `layers.tsx` alone is per-ayah (`chapterId+verseNumber`, validated by `isValidVerseKey`) while its siblings are per-surah — an inconsistency worth knowing before modeling.
- Goal units are PAGES/SECONDS/RANGE only — no distinct "verses" unit despite the streak UI talking about days read.

**Engineering warnings**

- **Range arithmetic bug**: `lodash.range(1, 114)` and `range(78, 114)` in `curatedStations.ts` are end-exclusive, so Surah 114 (An-Nas) never plays in either the popular-reciters or Juz-Amma stations.
- **Documented hydration race**: font/mushafLines-dependent SWR keys generated before redux-persist rehydration mismatch persisted keys and blank out verses; fixed by gating on `selectIsPersistGateHydrationComplete` while keeping SSR alive via `fallbackData`. Any consumer of persisted settings faces the same trap.
- **Service worker vs range requests**: cached MP3s broke Firefox audio downloads ("A ServiceWorker intercepted the request..."), so `.mp3` is carved out of the cross-origin CacheFirst rule — evidence that blanket runtime caching of media is hazardous.
- **Dead weight**: a `GUEST_ENROLLMENT` entry survives the persist whitelist with no registered reducer; radio sessions are unpersisted pending a TODO; the bulk server-side merge of guest bookmarks was not found within read budget and remains explicitly unverified.
- **Brief-vs-code discrepancies to carry forward**: Pages Router (not App Router); settings UI under `src/components/Navbar/SettingsDrawer/`; courses come from API v4, not Sanity; the note editor is a plain TextArea (Milkdown serves only Q&A/calendar prompts); no SSO flag anywhere in `src/`.
