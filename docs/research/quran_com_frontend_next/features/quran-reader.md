# Continuous-scroll Quran reader
> How **Quran.com frontend (github.com/quran/quran.com-frontend-next)** implements this feature. Sources read from a shallow clone @ main (2026-08-23); repo-relative paths cited throughout.

## 1. What the user sees
One reader surface for every entry point: a whole surah (`/[chapterId]`), a single ayah (`/[chapterId]/[verseId]`), an arbitrary verse range, a juz (`/juz/[juzId]/index.tsx`), hizb (`/hizb/[hizbId]/index.tsx`), rub' (`/rub/[rubId]/index.tsx`) or mushaf page (`/page/[pageId].tsx`). Scrolling never hits a "next page" button — content keeps appending until an `EndOfScrollingControls` block offers to continue into the next surah/juz. Each verse carries an inline action toolbar (play audio, bookmark, pin, copy, share, open tafsir), and a left sidebar navigation lists surahs/juz/pages for jumping.

## 2. Architecture & key files
- The discriminator is `QuranReaderDataType` (`Chapter | Verse | ChapterVerseRanges | Ranges | Tafsir | SelectedTafsir | Hizb | Juz | Rub | Page`) in `types/QuranReader.ts`; every route is a thin `getStaticProps` wrapper that passes `initialData`, `id`, and its `quranReaderDataType` into one component, `src/components/QuranReader/index.tsx`.
- `index.tsx` only composes chrome: `ContextMenu`, `Notes`, `ReaderTopActions`, pinned-verses offsets, tajweed padding (when mushaf is `Mushaf.QCFTajweedV4`), and the floating fundraising banner.
- The actual body is chosen in `src/components/QuranReader/QuranReaderView.tsx`: redux `readingPreference === Translation` renders `TranslationView` (verse cards); any Arabic reading mode renders `ReadingView` (mushaf pages), dynamically imported with `next/dynamic`.
- Both views are `react-virtuoso` windows over the same data model: `TranslationView/index.tsx` virtualizes verses with `useWindowScroll`, `increaseViewportBy={1000}` and `initialItemCount={1}` so SSR still emits one row; `ReadingView/index.tsx` virtualizes mushaf *pages* using ranges from `hooks/useFetchPagesLookup.ts`.

## 3. Data flow
SSR hands page 1 of verses as `initialData`; it seeds `apiPageToVersesMap` state in `TranslationView/index.tsx`. As Virtuoso mounts each verse cell, `TranslationViewVerse/hooks/useDedupedFetchVerse.ts` computes `pageNumber = floor(verseIdx / perPage)` and builds a request key with `getTranslationViewRequestKey` (`src/components/QuranReader/api.ts`). That function switches URL builder per reader type — `makeJuzVersesUrl`, `makeHizbVersesUrl`, `makeRubVersesUrl`, `makePageVersesUrl`, `makeByRangeVersesUrl` — and embeds font-dependent params via `getDefaultWordFields`/`getMushafId`. Because several adjacent verse cells map to the same API page, their `useSWRImmutable` calls dedupe into one network request; results are written back into `apiPageToVersesMap`, which feeds deep-link scrolling in `hooks/useScrollToVirtualizedVerse.ts`. Reciter/translation/wbw values come from URL query params or redux through `useGetQueryParamOrXstateValue`/`useGetQueryParamOrReduxValue`.

## 4. Storage & network
No local database: verse payloads live in SWR's runtime cache keyed by full API URL (so changing font, translations or reciter naturally produces new keys and refetches). Redux-persist keeps UI state (`PINNED_VERSES`, notes, sidebar state) in localStorage; `hooks/useSyncReadingProgress.ts` records the last-read verse so users resume where they stopped. The next-pwa service worker (`pwa-runtime-config.js`) adds Workbox runtime caching on top of quran-api v4 responses, while chapter routes are ISR-cached server-side with `revalidate: ONE_WEEK_REVALIDATION_PERIOD_SECONDS` and `fallback: 'blocking'` (`src/pages/[chapterId]/index.tsx`).

## 5. Why it is built this way ON THIS PLATFORM
The web's currency is URLs and SEO, so every slicing dimension (surah, juz, hizb, rub', page, range) is its own statically generated, individually addressable route feeding one shared reader — cheap discovery, no in-app router state to lose. Window-scroll virtualization (`useWindowScroll`) preserves native browser behaviors users expect on the web: find-in-page, scroll restoration, middle-click, shareable scroll positions. Server rendering the first page plus client-side dedupe-per-API-page gives search engines complete HTML while keeping TTFB and payload low on flaky mobile connections — the dominant access mode for this audience.

## 6. Edge cases & offline behavior
`useDedupedFetchVerse.ts` documents (in a long comment) a real hydration race: before redux-persist rehydrates, locale-default settings (e.g. `mushafLines: 16_lines`) generate a different SWR key than the user's persisted ones (15_lines), causing blank verses; the fix gates request-key generation on `selectIsPersistGateHydrationComplete` while keeping SSR alive via `fallbackData`. When URL params disagree with saved preferences, `QueryParamMessage` asks which to keep. `onCopyQuranWords.ts` rewrites copied QCF-glyph text back to canonical ayah text. Offline, previously fetched chapters replay from the service worker/SWR cache, but unvisited pages need network — there is no pre-packaged offline mushaf.
