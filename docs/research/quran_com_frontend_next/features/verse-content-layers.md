# Per-surah knowledge layers
> How **Quran.com frontend (github.com/quran/quran.com-frontend-next)** implements this feature. Sources read from a shallow clone @ main (2026-08-23); repo-relative paths cited throughout.

## 1. What the user sees
From a verse's action menu, users branch into dedicated deep-dive screens keyed by `chapter:verse`: qira'at differences (`/[chapterId]/[verseId]/qiraat.tsx`), related/connected verses (`related-verses.tsx`), hadith mentioning the ayah (`hadith.tsx`), video lessons (`lessons.tsx`), community Q&A (`answers/index.tsx` + `answers/[questionId].tsx`), and the "layers" linguistic view (`layers.tsx`). Separately, the sidebar surah list can be re-sorted by revelation order, with a `RevelationOrderNavigationNotice` banner explaining the non-mushaf ordering while it is active.

## 2. Architecture & key files
Each layer is its own statically generated Next page under `src/pages/[chapterId]/`, all following one template: `NextPage` component + `NextSeoWrapper` (canonical, hreflang alternates via `getLanguageAlternates`, OG image from `src/lib/og`) + `getStaticPaths` returning empty paths with `fallback: 'blocking'`. `qiraat.tsx` fetches through `getQiraatMatrix`/`makeQiraatMatrixUrl(verseKey)`; `related-verses.tsx` uses `makeRelatedVersesByKeyUrl(verseKey, locale, 1)`; `hadith.tsx` uses `getAyahHadiths`; `layers.tsx` uses `getLayeredTranslationByVerse` / `makeLayeredTranslationByVerseUrl` and mounts `StudyModeSsrContainer` inside an `<SWRConfig value={{ fallback }}>`. Revelation-order browsing is not a page but a redux flag: `src/redux/slices/revelationOrder.ts` holds a single boolean, `isReadingByRevelationOrder`, consumed by `SidebarNavigation/SurahList.tsx` (sorting) and `EndOfSurahSection`/`EndOfScrollingControls` (computing which surah comes next in revelation sequence; `utils/navigation.ts` branches on it when building next-chapter links).

## 3. Data flow
Every layer's `getStaticProps` runs its resource fetch and the base verse/pages-lookup fetch concurrently — e.g. `related-verses.tsx` line ~127 does `await Promise.all([fetcher(relatedVersesUrl), verseData, versesData, pagesLookupResponse])` — then returns the responses keyed by their request URLs as `fallback`. On the client the same URL strings become SWR keys, so components render instantly from `SWRConfig.fallback` without refetching, then paginate normally (page 2+ goes over the network). The revelation-order toggle dispatches `setIsReadingByRevelationOrder`; because the slice's `extraReducers` listens to `syncUserPreferences` under `PreferenceGroup.READING`, logging in overwrites local state with the account's stored value.

## 4. Storage & network
Content itself is never persisted client-side beyond SWR's in-memory cache plus the next-pwa service worker's runtime caching of API responses; each page is ISR-cached server-side for a week (`ONE_WEEK_REVALIDATION_PERIOD_SECONDS`) with a short `REVALIDATION_PERIOD_ON_ERROR_SECONDS` retry window and `logErrorToSentry` tagged per route (`transactionName: 'getStaticProps-RelatedVersesPage'`, etc.). The only durable client state is the revelation-order boolean, whitelisted into localStorage by redux-persist and mirrored to the backend preference groups via `hooks/auth/usePersistPreferenceGroup.ts` for cross-device sync.

## 5. Why it is built this way ON THIS PLATFORM
Each knowledge layer is long-tail SEO gold — queries like "qiraat of 2:255" or "hadith about verse X" land directly on a pre-rendered, self-contained page with full meta tags, which is impossible to serve from a purely client-side SPA. Fetching at build/revalidate time also hides API latency and third-party content (hadith collections, lesson metadata) behind CDN-cached HTML. Modeling "layers" as sibling routes rather than tabs inside the reader keeps each surface's bundle small and lets `EndOfScrollingControls`-style navigation link between them. The one-slice-per-concern redux shape (a 51-line file for revelation order) reflects a web app where most state is ephemeral and only user preferences are worth persisting.

## 6. Edge cases & offline behavior
Discrepancy vs the brief: `layers.tsx` is *per-ayah*, not per-surah — its props carry `chapterId` + `verseNumber` and it validates the verse key with `isValidVerseKey` before rendering, redirecting bad keys rather than listing chapter resources. All routes use `fallback: 'blocking'` so first requests build on demand; failures fall into the short-revalidate error path instead of caching a broken page. Deep-linked resources depend on network on first visit; the service worker only replays what was previously fetched, so offline access to a given layer requires having opened it before. Anonymous users keep settings locally until login, when guest preferences merge with remote ones.
