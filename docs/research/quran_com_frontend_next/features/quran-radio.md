# Quran Radio Stations
> How **Quran.com frontend (github.com/quran/quran.com-frontend-next)** implements this feature. Sources read from a shallow clone @ main (2026-08-23); repo-relative paths cited throughout.

## 1. What the user sees
- On the home page, a "Listen to Quran Radio" button (`src/components/HomePage/PlayRadioButton.tsx`) that starts playing immediately without any surah picker; it picks a *random* curated station via `getRandomCuratedStationId()` and shows `RadioInformation` (current station/track) next to it.
- A dedicated SEO page at `src/pages/radio.tsx` — a Pages Router page with `GetStaticProps` that server-fetches reciters through `getAvailableReciters` and renders two sections: `CuratedStationList` (four banner stations) and `ReciterStationList` (one station per available reciter).
- Playback surfaces in the same global bottom audio player used for surah audio; the player bar swaps in a radio-specific control (`src/components/AudioPlayer/RadioPlaybackControl.tsx`).

## 2. Architecture & key files
There is no radio backend. Station definitions are pure code: `src/components/Radio/curatedStations.ts` exports a `Record<string, CuratedStation>` built at module load by generators — station 1 "popular recitations" cross-joins four hard-coded popular reciter ids (`['7','3','10','4']`) with chapters, station 4 is Juz Amma (chapters 78+), station 3 is Surah Al-Kahf across all four reciters, station 2 is a hand-written Yaseen/Waqiah/Mulk list. Titles/descriptions are translation keys resolved by next-translate. Playback logic is a deliberately tiny machine, `src/xstate/actors/radio/radioMachine.ts`: a single `on` state handling only `PLAY_STATION` and `TRACK_ENDED`. It has no audio element of its own — it exists as a child actor spawned into `audioPlayerMachine` context (`radioActor`), making radio a mode of the existing player rather than a parallel system.

## 3. Data flow
The home button sends `PLAY_RADIO {stationId, stationType}` to the parent machine, whose `forwardPlayToRadioMachine` action spawns `createRadioMachine()` if needed and forwards `PLAY_STATION`. The radio actor's `generateRadioAudioTrack` action picks a track with `lodash.sample` — either from `curatedStations[id].audioTracks` or, for reciter stations, `{reciterId: id, surah: random(1, 114)}` — then emits `sendParent({type:'PLAY_RADIO_TRACK', shouldPlayFromRandomTimeStamp: true, reciterId, surah})`. The parent treats that exactly like a user-initiated surah play: fetch chapter audio for that reciter, set the `<audio>` src, but seek to a random timestamp so a full-surah file feels like a live stream. When playback ends, `forwardEndedToRadioMachine` sends `TRACK_ENDED`, and `generateNextAudioTrack` repeats the sampling with `shouldPlayFromRandomTimeStamp: false`, chaining tracks forever.

## 4. Storage & network
Nothing about radio persists: no queue in redux-persist, no "recently played", no server sync — each session starts fresh (the code even carries `// TODO: handle continue radio from last saved session`). The only network calls are the same per-surah audio-file API used everywhere else (`getChapterAudioData` via `executeFetchReciter` in `audioPlayerMachineHelper.ts`); MP3s stream from CDN and are intentionally not service-worker cached. The `/radio` page ships reciters as static props at build time.

## 5. Why it is built this way ON THIS PLATFORM
A web app cannot bundle audio or run background audio sessions, so "radio" is synthesized on top of assets the site already serves: whole-surah MP3s plus verse timestamps. Shuffle-plus-random-seek is the cheap substitute for HLS/streaming playlists or an audio CDN, and it inherits every player capability for free (MediaSession lock-screen controls, playback rate). Modeling it as a spawned XState actor inside `AudioPlayerMachineContext` means the station survives client-side navigation between home, `/radio`, and reader pages — essential on the web where there is no app process to own playback. The static `/radio` page exists because discovery flows through search engines, unlike a native tab.

## 6. Edge cases & offline behavior
Offline, radio simply cannot start: track resolution requires the API, then the MP3. Notable quirks found in code: the track generators use lodash `range(1, QURAN_CHAPTERS_COUNT)` / `range(78, 114)`, which are end-exclusive, so Surah 114 (An-Nas) never appears in the popular-recitations or Juz Amma stations even though Juz Amma includes it. Changing reciter mid-radio is intercepted by the `isRadioActive` guard and forwarded to the radio actor as a new reciter station rather than reloading the current surah (`forwardChangeReciterToRadioMachine`). MediaSession next/previous are remapped to `NEXT_AUDIO_TRACK` → `TRACK_ENDED` when a radio actor exists. `CLOSE_RADIO` stops the actor outright, and any `PLAY_AYAH`/`PLAY_SURAH` event runs `exitRadio` first so verse playback and radio can never interleave.
