# Audio Recitation Player
> How **Quran.com frontend (github.com/quran/quran.com-frontend-next)** implements this feature. Sources read from a shallow clone @ main (2026-08-23); repo-relative paths cited throughout.

## 1. What the user sees
- A sticky bottom player bar (`src/components/AudioPlayer/AudioPlayer.tsx` renders `AudioPlayerBody`) with play/pause, prev/next verse, a seek slider showing buffered vs elapsed time, and an overflow menu.
- A reciter picker (`Buttons/SelectReciterMenu.tsx`), playback-rate menu (`Buttons/AudioPlaybackRateMenu.tsx`), volume control, and a repeat button opening `RepeatAudioModal/RepeatAudioModal.tsx`: single-verse or verse-range mode, "play range" and "repeat verse" steppers (an infinity option appears past `infinityThreshold: 8`), plus a 0.5-step inter-verse delay multiplier.
- `Buttons/DownloadAudioButton.tsx` sits in the overflow menu with a spinner while the MP3 downloads; OS/lock-screen controls appear via the MediaSession API. Space/arrow keys work through `AudioKeyboardListeners.tsx`.

## 2. Architecture & key files
The whole feature is one hidden `<audio>` DOM element bridged into an XState machine. `AudioPlayer.tsx` keeps a always-mounted, `display:none`, `autoPlay preload="auto"` element (comment cites Safari's gesture requirement) and forwards every native event as a machine event. The brain is `src/xstate/actors/audioPlayer/audioPlayerMachine.ts` (~1150 lines), instantiated once in `src/xstate/AudioPlayerMachineContext.tsx` so any page can send it events. It spawns two child actors into context: `repeatActor` (`src/xstate/actors/repeatMachine/repeatMachine.ts`) for repeat loops and `radioActor` (`radioMachine.ts`). Pure UI lives under `src/components/AudioPlayer/`; helpers/selectors in `audioPlayerMachineHelper.ts` / `selectors.ts`.

## 3. Data flow
`PLAY_SURAH`/`PLAY_AYAH` transitions to `VISIBLE.LOADING_RECITER_DATA`, which invokes the `fetchReciter` service → `executeFetchReciter` → `getChapterAudioData(reciterId, surah, true)` from `src/api.ts` (quran.com API v4), returning `{ audioUrl, duration, verseTimings[] }`. Actions then set `audioPlayer.src` and seek `currentTime` to `verseTimings[ayahNumber - 1].timestampFrom` (or a random timestamp when radio set `shouldPlayFromRandomTimeStamp`). Every `timeupdate` runs `setElapsedTime`, which maps currentTime back to the active ayah and word position via `getActiveVerseTiming`/`getActiveWordLocation` (200 ms tolerance for mobile Safari's timestamp drift); those context values drive reader highlighting/auto-scroll (consumed downstream by e.g. `useActiveVerseTiming` and the ReadingView scroll hooks — the exact scroll trigger was outside my read budget). On `END` the guards decide: advance ayah, let `repeatActor` re-loop, or forward `TRACK_ENDED` to the radio actor.

## 4. Storage & network
Audio is streamed MP3 from CDN URLs supplied per-surah by the API; nothing is cached offline (the next-pwa config deliberately excludes MP3s). Downloading is client-side only: `download()` in `DownloadAudioButton.tsx` does an XHR with `responseType:'blob'`, derives the filename from the URL substring before `?`, and clicks a temporary `<a download>` object-URL link — no offline library. Preferences (reciterId 7 default, `playbackRate`, `volume`, `repeatSettings`) persist through redux-persist's separate AudioPlayerState config and, for logged-in users, are pushed cross-device by `usePersistPreferenceGroup` under `PreferenceGroup.AUDIO` — note the modal saves `Infinity` as `-1` via `toPersistedValue` because JSON/redux-persist can't hold `Infinity` (`REPEAT_INFINITY = -1` in `src/redux/types/AudioState.ts`).

## 5. Why it is built this way ON THIS PLATFORM
Browsers give you exactly one sanctioned audio primitive, so all complexity is state-machine modeling around a single `<audio>` element rather than a playlist engine. XState earns its keep here: buffering, seeking, ending, media-key presses and reciter swaps arrive concurrently from the DOM and OS, and each needs deterministic recovery. Lock-screen controls are only possible on web via `navigator.mediaSession` — implemented inside the machine as the long-running `initMediaSession` service that sets `MediaMetadata` (title "Surah N", artist = reciter name, Quran.com artwork) and maps `play/pause/previoustrack/nexttrack/stop` handlers to machine events. Repeat settings sync to a server account instead of a local database because this is a web app whose users expect continuity across devices.

## 6. Edge cases & offline behavior
Safari fires `ENDED` instead of `WAITING` when the buffer runs dry, so `AudioPlayer.tsx` simulates WAITING/CAN_PLAY from `timeupdate` + `buffered` (2 s tolerance), and the machine's `continueFromLastTimestamp` hack rewinds to `elapsed - 0.0001` and replays; the `isAudioAlmostEnded` guard (3 s before duration) prevents treating a genuine end as a stall. Any load/API failure lands in `FAILED`, which auto-hides the player after 500 ms. Boundary guards `isNotLastVerse`/`isNotFirstVerse` stop track-hopping at surah edges, `normalizeVerseRange` swaps reversed ranges, and persisted from/to verse keys are validated against the current chapter (`isVerseInChapter`) so stale settings can't reference nonexistent verses. Offline there is nothing to play unless the browser HTTP cache happens to still hold the MP3; the modal's delay uses an XState `after` timer (`delays.VERSE_DELAY`) that is cancelled if the tab dies mid-delay.
