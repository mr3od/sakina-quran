# Translation and tafsir selection
> How **Quran.com frontend (github.com/quran/quran.com-frontend-next)** implements this feature. Sources read from a shallow clone @ main (2026-08-23); repo-relative paths cited throughout.

## 1. What the user sees
In the reader's settings drawer (`src/components/Navbar/SettingsDrawer/` — note the drawer lives under `Navbar/`, not at `components/SettingsDrawer/` as the brief stated), a `SelectionCard` summarizes the current choice ("Saheeh International and 2 others", localized via `toLocalizedNumber`). Tapping it swaps the drawer body to a full picker view (`TranslationSelectionBody.tsx` / `TafsirSelectionBody.tsx`, driven by `setSettingsView(SettingsView.Translation|Tafsir)` from `src/redux/slices/navbar`). Each section also has a font-size `Counter`. Full tafsir text opens on its own crawlable URL, `/[chapterId]/tafsirs/[tafsirId]`, rendered as a study-mode modal above the chapter reader.

## 2. Architecture & key files
- State: `src/redux/slices/QuranReader/translations.ts` (`selectedTranslations: number[]`) and `tafsirs.ts` (`selectedTafsirs: string[]` of slugs) — two nearly identical RTK slices.
- UI: `TranslationSection.tsx`, `TafsirSection.tsx`, plus the shared drawer shell `SettingsDrawer.tsx` and `Section` primitives.
- Route: `src/pages/[chapterId]/tafsirs/[tafsirId].tsx` (also `src/pages/[chapterId]/[verseId]/tafsirs.tsx`).
- Types: `QuranReaderDataType.Tafsir | SelectedTafsir` in root-level `types/QuranReader.ts`.

## 3. Data flow
Both slices compute an `isUsingDefaultTranslations`/`isUsingDefaultTafsirs` flag on every change by comparing against locale-aware defaults (`getTranslationsInitialState(locale)` / `getTafsirsInitialState(locale)` in `src/redux/defaultSettings/util`), with an explicit comment about the reversed-array corner case handled by `areArraysEqual`. The drawer lists come from SWR through `DataFetcher` with `makeTranslationsUrl(lang)` → `/resources/translations?language=` and `makeTafsirsUrl(lang)` → `/resources/tafsirs` (`src/utils/apiPaths.ts`). The tafsir page's `getStaticProps` fetches tafsir content, tafsir list, verse data and `getPagesLookup(...)` in one `Promise.all` via `fetcher`/`getPagesLookup` from `src/api.ts`, then seeds `<SWRConfig value={{ fallback }}>` so the client never refetches; `getStaticPaths` returns no paths with `fallback: 'blocking'` (on-demand ISR). The page mounts `StudyModeSsrContainer` with `initialTab={StudyModeTabId.TAFSIR}` plus a `QuranReader` for context.

## 4. Storage & network
Selections persist locally because `TRANSLATIONS`/`TAFSIRS` are redux-persist whitelisted in `src/redux/store.ts`; both slices also handle `resetSettings` (back to locale defaults) and `syncUserPreferences` which overlays `PreferenceGroup.TRANSLATIONS`/`TAFSIRS` payloads fetched from the account backend. Font scale changes go through `usePersistPreferenceGroup().onSettingsChange(key, value, action, undoAction, PreferenceGroup.QURAN_READER_STYLES)` (`src/hooks/auth/usePersistPreferenceGroup.ts`) — every dispatch carries its inverse action so logged-in users get server-side persistence with undo, anonymous users just get local state. Every change is instrumented with `logEvent`/`logValueChange` analytics.

## 5. Why it is built this way ON THIS PLATFORM
SEO is the driver: tafsir content is a discovery surface, so it gets static generation with one-week `revalidate`, per-locale canonical URLs (`getCanonicalUrl`, `getLanguageAlternates`), `NextSeoWrapper` metadata and generated OG images (`getChapterOgImageUrl` from `src/lib/og`) — things a native app never needs. Because there is no local database, "which translations do I read" is just a small persisted Redux array of API resource IDs; the dozens-of-translations catalog is fetched live from quran.com API v4 `/resources/*` endpoints rather than bundled, keeping the JS bundle small and letting the CMS add translations without releases. Locale-aware defaults exist because next-translate serves 18+ locales and each needs sensible default translations/tafsirs.

## 6. Edge cases & offline behavior
Invalid verse keys short-circuit to `notFound: true` via `isValidVerseValidator`'s `isValidVerseKey(chaptersData, verseKey)` — note `[chapterId]` here is actually a full verse key like `2:255`. Any fetch failure in `getStaticProps` logs to Sentry (`logErrorToSentry` with transaction metadata) and returns not-found with a short `REVALIDATION_PERIOD_ON_ERROR_SECONDS` retry window. Stale selections referencing removed translations are filtered client-side before display (`availableTranslations = selectedTranslations.filter(...)` in `TranslationSection.tsx`). The service worker (pwa-runtime-config.js Workbox runtime caching of API responses) can serve cached tafsir responses offline; beyond that there is no tafsir download story — consistent with the repo deliberately disabling MP3 caching.
